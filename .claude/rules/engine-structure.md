# 計算エンジンの構造

- **レイヤーを混ぜない**: 総合力（`power.ts`）/ ゲーム内表示のスコアボーナスとユニットスコア（`displayScore.ts`）/ 順位づけに後から掛かる倍率（`optimize.ts` の `ScoreModifierBreakdown` — イベントスコアボーナスだけ。ロジックはあるがアプリからは未接続 — `pending.md` 10「イベントスコアボーナスの適用位置」。黄の楽曲スコアボーナスはボード欄に入る側で `songBoardRaw` が持ち、後掛けしない）/ ライブ中のアクティブスキルの発動タイミング（`liveSkillTimeline.ts` + `liveFrequencyOptimizer.ts`。ADR-007）/ 実ライブスコアそのもの（未実装。将来の別エンジン）は別モデルとして型・関数・定数を分ける（ADR-004 / 005 / 006）。表示モデル専用の推定値（`ACTIVE_PROBABILITY`）を「将来共有するかもしれない」共通の置き場に出さない — 同じ値になる保証がない。
- **使われなくなった近似モデルは残さず削除する**: `legacy` 名で隔離せず消し、必要になったときゼロから作り直す（検証されていない近似を「エンジン」の名前で残さない）。削除の前に `rg` で参照（UI・Worker・テスト）を確認し、報告に file / symbol / 理由を書く。
- **名前は実体に合わせる**: 意味がずれた型・関数・定数を放置しない（順位づけの値は実ライブの期待スコアではないので `adjustedUnitScore`、`scoreModifierFactor`、`songBonus`）。
- **丸め・整数化の規則もレイヤーごとに分ける**: スコアボーナス欄は 0.1% 単位の切り上げ（`toScoreBonusPermil`。実機 20 ケースで四捨五入 15/20 → 切り上げ 20/20）、総合力・ユニットスコア・パラメータは各々の確定した丸め。片方の規則を他方へ流用しない。浮動小数のずり上がりを防ぐ epsilon は許容するが、実機値へ寄せる補正は入れない。
- **派生する欄の値は、表示済みの丸め値ではなく raw 中間値から計算し、最後に 1 回だけ量子化する**（2026-09-11 ユーザー指示「必ず可能な限り既存の表示前 raw 値を使って計算すること」）。黄ボードの増分を表示済みの値から求めると丸め境界が合わず、`finishDisplay` の raw から `songBoardRaw` → 量子化の順で実機 8 点がそろった。UI へ出す値を次の計算に入れない。
- **おまかせの候補は ★5 だけ**（ADR-022）: `prepareRunSearch` が固定していない ★4（`star4Pool.ts` の `autoExcludedStar4Ids`）を両方の除外に足し、「組み直すと」の候補プール（`rankingPool`）・仮想ガチャの ★5 プールは `star5Cards` を使う。**例外はリーダーのおまかせで、ホロメンで指定したリーダー（`leaderCandidateIds`。おかゆモードも）のそのホロメンの ★4 と、★5 を 1 枚も使えない（`excludedCardIds` で全部外れている）ホロメンの ★4（`star4LeaderFallbackIds`）はリーダーの候補に残し、メンバーの除外にだけ足す**（2026-10-09 ユーザー指示。「組み直すと」の `rankingPool` も同じ。ティア表の仮想アカウントは ★4 も除外して渡す）。リーダーの指定・メンバーの固定に置いた ★4 はそのまま解決して評価する（評価の経路は ★5 と同じ。`star4Pool.test.ts`）。
- **ティア表の評価は探索そのもの**（`tier.ts`。ADR-024 とその Update）: 全カード前提（`tierBaseRequest`）で、**段は仮想アカウント法の採用率**（★5 から所持 20〜50 枚のアカウントを均衡配置で 3,034 件作り、それぞれで `runOptimize` のおまかせを回して、持っていたアカウントのうち最高編成に入った割合。ラウンド数 1,100 は 95% 信頼区間 ±3 pt から — `ACCOUNT_DESIGN`）。そのカードを固定した最良 ÷ 全体の最良は参考の観点として残す。独自の点数式を足さない。全部で 4 コア約 1 時間かかるので `scripts/tier/build.mjs`（`pnpm tier`。`pnpm tier -- --accounts` は仮想アカウントだけ）で事前計算して `src/data/tierList.json` に置き、`tierFingerprint`（★5 カード・ホロメン・ボードのマス・`TIER_MODEL_VERSION`・`ACCOUNT_DESIGN`）が変わると `tier.test.ts` が作り直しを求める。**評価の式（`displayScore` / `power` / 探索の順位づけ）を変えたら `TIER_MODEL_VERSION` を上げて `pnpm tier` を回す**。説明文の「強み」の順位づけ（`src/ui/tier.ts`）はエンジンの量（`linearRaw`・SP の係数）を読むだけで、評価には使わない。
- **依頼の解決と探索は 1 本にする**: カード ID・マス ID から「開花・ボードを解決して `optimize` を呼ぶ」までは `request.ts` の `prepareRunSearch`（`runOptimize` と、分担する各 Worker が通る）だけが持ち、Web Worker（`worker.ts` / `searchWorkerHandler.ts`）はメッセージの受け渡しに専念する。6 枠すべて決まっている編成（お気に入りの再評価）は組合せが 1 通りなので、同じ関数を UI スレッドから同期で呼ぶ。
- **最適化の各段が編成を繰り返し測る評価は `createTeamScorer`（`request.ts`）の 1 つ**（ADR-018）。組み直しプラン 1 回で数千回測るので、**値を変えずに計算を省く**: 全ホロメンにまたがる量（緑・黄）は鍵（依頼の順のホロメン・その色のマス・配置の中身）が前と同じなら作り直さず、変わったときは `runOptimize` と同じ関数を同じ並びで呼ぶ / 赤はリーダーのホロメンの分だけ / カードの解決と評価の結果は入力が同じなら使い回す。評価そのものは `optimize.ts` の `scoreTeam`（探索の正確な評価と同じ 1 本）。カードの数値表現（`compileMember` / `compileDisplayMember`）はカードごとに覚える（カードは作ったあと書き換えない）。**覚えた値を使っても 6 枠固定の `runOptimize` と 1 点も違わないこと**を `teamScorer.test.ts` で固定する。**配置の器はコネクトの最適化がその場で書き換えるので、同じかどうかは器ではなく中身で見る**（盤面の `HolomenBoards` は readonly で、器が同じなら中身も同じ）。覚えた値は評価器ごと捨てる（組み直しプラン 1 回・「組み直すと」の 1 編成ごと）。近似や評価の順番は変えない — 速くするための変更で推奨が変わったら、それは不具合。
- **近似を入れるなら厳密な比較経路も持つ**: 探索を近似（上限値での shortlist）にしたら、小規模で真の上位と突き合わせられる厳密探索（`exactSearch.ts`）と比較テストを同時に維持する（ADR-005）。未確定の単調性に依存する枝刈りは使わない（`game-facts.md`）。**shortlist の上限値は「同時候補の正規化 `max(1, Σp)` を入れた値」にする** — 正規化を無視した線形和は青を開けたアカウントで 1.3 倍近く緩み、おまかせ探索が固定メンバーの探索より低い結果を返した。上限を変えたら `shortlistSize` を絞った `optimizeShortlist.test.ts` で実データの厳密探索と突き合わせる。
- **探索は何本の Worker に分けても 1 本と同じ結果にする**（ADR-018）。分担は組合せの 1 枚目のプール内の添字の余り（`SearchPartition`）で、分担ごとに上限値の上位 `shortlistSize` 件を集め、全体の上位はそれらの和から選ぶ（`selectShortlist`）。**同点の決め方を見つけた順に頼らない**: shortlist の境目と正確に評価する順は「上限値の高い順、同じなら番号（組合せの辞書順の番号 × クラス数 + クラス）の小さい順」、結果の並びは `compareRanked`（順位づけの値 → 上限値 → 番号 → クラスの中のリーダーの順）。足切りは「最下位**未満**なら捨てる」で、同じ上限値はヒープの比較（番号）で決める。手順（数える → 全体の上位を選ぶ → 分担ごとに正確に評価してまとめる → 要れば 2 パス目）は `optimize.ts` の `searchInProcess` と `useOptimizer` の 2 か所にあるので、片方を変えたらもう片方も変え、`searchPartition.test.ts` / `useOptimizer.test.ts` で 1 本の結果と突き合わせる。葉ごとに全リーダーグループをまとめた上限 1 つで先に足切りする案は速くならなかった（まとめた上限が緩い）ので入れていない。
- **ライブ最適化（`live*.ts`）は表示モデルへ依存しない**: `liveSkillTimeline.ts` / `liveFrequencyOptimizer.ts` から `displayScore.ts` を import しない。基礎発動確率も `LIVE_ACTIVE_PROBABILITY` として独自に持つ — 値が同じでも評価対象が別（実ライブの発動 vs 表示欄の評価器）で、片方の反証・訂正でもう片方を自動的に動かさないため（ADR-007）。時刻は実数の秒で扱い、1 秒刻みの離散化や整数秒への丸めを推測で入れない。
- **発動頻度マスの目的関数は 3 つあり、モデルは混ぜない**: ライブ側の 2 つ（期待値 / 理論最大 — `liveFrequencyOptimizer.ts`）と、表示ユニットスコアを最大にする 1 つ。3 つとも最適化の**頻度の段**（`frequencyStage.ts`。ADR-015）が持ち、候補（メンバーごとの頻度マスの部分集合とその盤面）を作るのはこの段で、評価は各モデルが自分の式で行う（表示側の評価は `createTeamScorer` を使う `frequencyStage.ts` 側に閉じ込める）。推奨のユニットスコアは頻度マス込みの値を出し、`W_blue` を通る近似であることは脚注に書く。**頻度の固定は頻度マスの数（0〜3）で行う**（実効 % はコネクトも同じ実行で変わると実行前に決まらない）。固定で候補を絞ると `FrequencyPlan.choice` の添字が変わるので、案を引くのは絞ったあとのメンバー（候補の同一性で元の添字へ戻す）。**候補を「発動率 % / 発動頻度 % が同じだから」と畳まない** — 青ボードには P/T/S のマスが並び（`src/data/blueBoard.ts`）、どの頻度マスへ行くかで経路上に拾うパラメータが変わる（2026-09-16 ユーザー指摘）。畳んでよいのは**解放マスの集合が同じ候補だけ**（ライブ側は P/T/S を見ないので畳み方が違う — これも「混ぜない」理由）。経路は前の段の盤面から追加のボードPt が最小のもの（`BoardGraph.planUnlock`。コネクトの明示解放を含む）だけで、遠回りして P/T/S を多く拾う開け方は探索していない — UI の脚注にもそう書く。**ホロメンランクの Pt は超えない**: 足りない候補は経路を必須にしたまま、そのホロメンの 4 色のマスから「外して失う表示ユニットスコア ÷ 空く Pt」が小さいものを外して空ける（空けられなければ候補にしない。**同じ比なら空く Pt が少ないマスから** — 外しても損のないマス（メンバーの赤など）はどれも比 0 で並び、決めないと中心寄りのマスを外して先まで丸ごと外れた。2026-10-10 ユーザー指摘「Pt 足りてるのに全部外すことない？」）。**資材は 余り + この編成に効かないマス（外して回せる — `recoverableMaterials`）の範囲**（ADR-016。`materialLimits`。所持リソースを考慮しない色は制限なし。余りは外して回すぶん負になる）。**候補は登録の頻度マスの部分集合か上位集合だけ**（同じ数なら登録のまま、増やす・減らすときも登録に足す・減らすだけ。3 マスとも +4% で違いは経路だけなので、同じ数で場所だけ替える推奨は意味がない — 2026-10-09 ユーザー指摘）。`liveFrequencyOptimizer.ts` の `enumerateFrequencyCandidates` / `buildFrequencyMembers` は画面からは使っていない。
- **目的関数と推薦ポリシーを混同しない**: ゲーム仕様の仮定（周期・確率の式）と「どの案を勧めるか」の方針（`FREQUENCY_RECOMMEND_POLICY` の 0.1 ポイント以内で省素材を選ぶ等）は別の定数に分け、UI の脚注でも「ゲームの仕様ではなくこのツールの方針」と書く。主目的関数はユーザーに見せる 2 つ（期待値 / 理論最大）だけにし、カバレッジ・空白は tie-break にとどめる（ADR-007。画面の表示は 2026-10-10 に外した）。
- **青ボードの実効値は live 側も display 側もコネクト増幅込みにする**。`liveFrequencyOptimizer.ts` は `buildFrequencyMembers(..., connect)` → `enumerateFrequencyCandidates(currentNodeIds, factors)` → `blueBoardEffects(unlocked, factors)` で、現在の状態と全候補に同じ倍率表（`src/data/connect.ts` の `connectFactorsOf(...).blue`）を当てる。範囲・倍率の計算を `live*.ts` 側へ再実装しない。候補の畳み込みは効果の値で決まるので、増幅で値が割れると同じマス数の候補が分かれることがある。
- **探索の候補はボードの連結性から作る**: 「マスを開ける」選択肢は `[0, 4, 8, 12]%` を仮定せず、`blueBoard.ts` の `unlockNode` で現在の解放マスから到達できる状態を列挙する。**列挙は「現在値から増やす方向」だけにしない** — 発動頻度マスは 3 つとも葉なので、いま ON のマスをそのマスだけ外す候補（`removedNodeIds`）も含めて ON / OFF の全組合せを比べる。頻度マス以外の解放済みマスは固定し、コスト（`additionalNodeCount`）は新しく開けるマスだけ数える（外すと素材は返ってくるので、この値はこれから払う素材の上限）。現在の状態そのもの（追加 0・外す 0）は必ず候補に含める。
- **評価区間のような外から決まる値をゲーム仕様の定数にしない**: 曲を指定すれば曲長、指定がなければデータ由来の中央値（`medianSongDurationSeconds`）+ UI で変更可能にする。表示スコアボーナスの T = 200 秒は実機 20 ケースの当てはめで決めた**そのモデル専用**の値で、ライブ側へ流用しない。
- **候補を減らすしぼりこみは持たない**: 「衣装スキル発動に限る / パッシブ全員発動に限る」は UI ごと撤去し、`requireCostumeSkill` / `requireAllPassives` も消した（ユーザー指示「内部的にはそれらを考慮せず全探索する」）。**復活させない** — プールが小さいと条件 1 つで 0 件になった。発動しているかどうかは結果側で見せる（`breakdown.costumeSkillActive`）。
- **表示ユニットスコアの順位とライブ側の順位を同じものとして扱わない**。表示ユニットスコアに曲の長さは入らない（`docs/human/game-spec.md`）のに対しライブ側は曲長・ノーツで決まるので、順位が一致する理由がない。「ユニットスコア最大の編成を選ぶ → その編成で発動頻度を最適化する」はライブ期待値の最大にならない（所持 34 枚・リーダー固定の 248,946 編成を代理指標で総当たりすると、ユニットスコア 1 位はライブ 23 位で、頻度を最適化し直しても 573,670 対 582,882 で負ける）。同じ編成の中でも、表示側は青の発動頻度を `W_blue` 経由でしか見ないので頻度マスの最適解が live 側と割れる。**表示側の指標でライブの意思決定をせず、ライブ側の指標で表示値を説明しない。** 代理指標そのものが未検証であることは `pending.md` 9。
- モデルの信頼度の区分（確定 / 強い推定 / 仮説）と実機とのずれの書き方は `game-facts.md` に従う。仮説の式は差し替え地点として関数に切り出す。
- **素値合計が同値のメンバーの選び方は「最良」を採る暫定方針**（2026-09-30 ユーザー指示。実機の規則は未確認 — `pending.md` 16）。総合力のパッシブは効果ごとに加算量の大きい方（`power.ts` `passiveParamBonus`。並びに依らない）、表示スコアボーナスのスコアサポートは同値メンバーの並べ替えを試して最良（`tieOrder.ts` の `bestTieOrder`。`optimize.ts` と `exactSearch.ts` の正確評価で共有し、結果の `members` はその並びで返す）。**編成順に依る選び方を評価器へ戻さない** — 同じ 5 人が並べる順で違う値になり、固定ありの探索とおまかせの探索で食い違う。上限値（shortlist）は並びに依らない形なので上限のまま。
- **探索はコネクトのオプションを持たず、登録している（ボードで置いた）コネクトで常に計算する**（2026-10-02 ユーザー指示）。`runOptimize` の `connectPlacements` がそのまま探索・表示に効き、育成の前提に関わらない。「コネクトを外した探索は探索のあとに最適な配置を選び直す」近似は撤去済み — 復活させない。
- **ホロメンボードの最適化は、固定した編成の表示ユニットスコアを、ホロメンごとのボードPt の予算内で最大にする別の計算**（`boardOptimize.ts` の `optimizeBoards` + `boardPlan.ts` の `planBoards` + `optimizeWorker.ts`。出所・前提は ADR-012、資材の共有制約は ADR-013）。評価はコネクトの最適化と同じ `createTeamScorer` の経路（画面の値と一致 — `boardOptimize.test.ts`）で、ライブスコアの式は目的にしない。**どの結果も守る制約**: キューブ・コアキューブは色ごとのアカウント共有の有限資材（マス別の消費量は外部 master 由来の `src/data/boardMaterials.ts`。「リソース」の登録値は余りなので、再配分できる総量 = 変える可能性のあるホロメンのいまのボードへ投入済みの資材 + 余り + 変えないホロメンのこの編成に効かないマス（`recoverableMaterials`。赤はリーダー以外・青はメンバー以外の全部、黄は指定した曲の楽曲スコアボーナスに入らないマス、報酬のマス。効くマスや配置のあるコネクトへの途中のマスは外せないので端から数える。緑の全員・パラメータ・所属のマスは静的には入れず、取り崩し `release` が動的に扱う — ADR-016 / 019 / 026）。未登録の項目は制限なし、0 は余りが 0 個。候補はホロメンのボードPt と共有の資材の**両方**に収まるときだけ採用し、資材に上限のある色では Pt・cube・core の非劣な経路すべてを評価する — `BoardGraph.planUnlockRoutes`。推奨を反映するとき余りのリソースも新しい盤面に合わせて置き換える — `BoardPlanResult.remainingAfter`。手動のボード操作は資材で制限しない）/ ランク登録済みのホロメンは 通常マスのPt + 解放した非中心コネクトのPt ≤ 累積ボードPt（未登録は制限なし）/ 解放済みのセルはすべて中心から解放済みのセルだけで届く / **コネクトの配置は変えず、配置のある非中心コネクトは必ず解放済み**（1 Pt
