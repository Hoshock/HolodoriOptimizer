# 計算エンジンの構造（2026-09-09 ユーザー指示由来）

- **レイヤーを混ぜない**: 総合力（`power.ts`）/ ゲーム内表示のスコアボーナスとユニットスコア（`displayScore.ts`）/ 順位づけに後から掛かる倍率（`optimize.ts` の `ScoreModifierBreakdown` — 黄の楽曲スコアボーナスとイベント）/ ライブ中のアクティブスキルの発動タイミング（`liveSkillTimeline.ts` + `liveFrequencyOptimizer.ts`。発動頻度マスの投資判断用。ADR-007）/ 実ライブスコアそのもの（**未実装**。譜面・コンボ・SP の発動位置を含む将来の別エンジン）は別モデルとして型・関数・定数を分ける（ADR-004 / ADR-005 / ADR-006）。表示モデル専用の推定値（`ACTIVE_PROBABILITY`）を「将来共有するかもしれない」共通の置き場に出さない — 同じ値になる保証がない。
- **使われなくなった近似モデルは残さず削除する**: `legacy` 名で隔離するのではなく消し、必要になったフェーズでゼロから作り直す（旧 `live.ts` の曲長按分モデルは順位づけ・UI とも未使用だったため 2026-09-09 に削除 — 検証されていない近似を「エンジン」の名前で残さない）。削除の前に `rg` で参照（UI・Worker・テスト）を確認し、報告に file / symbol / 理由を書く。
- **名前は実体に合わせる**: 意味がずれた型・関数・定数を放置しない（順位づけの値は実ライブの期待スコアではないので `expectedScore` → `adjustedUnitScore`、`liveFactorOf` → `scoreModifierFactor`、`OptimizeRequest.live` → `songBonus` に改名 — 2026-09-09）。
- **丸め・整数化の規則もレイヤーごとに分ける**: スコアボーナス欄はサーバーが返す permil 整数に合わせて 0.1% 単位の切り上げ（`toScoreBonusPermil`。実機 20 ケースのアクティブ欄が四捨五入 15/20 → 切り上げ 20/20 で一致）、総合力・ユニットスコア・パラメータは各々の確定した丸め（パラメータごとの切り上げ / 最後の ceil）。片方の規則を他方へ流用しない。浮動小数のずり上がりを防ぐ epsilon は許容するが、実機値へ寄せる補正は入れない（2026-09-09）。
- **依頼の解決と探索は 1 本にする**: カード ID・マス ID から「開花・ボードを解決して `optimize` を呼ぶ」までは `src/engine/request.ts` の `runOptimize` だけが持ち、Web Worker（`worker.ts`）はメッセージの受け渡しに専念する。6 枠すべて決まっている編成（お気に入りユニットの再評価）は組合せが 1 通りなので、同じ関数を UI スレッドから同期で呼ぶ（2026-09-09）。
- **近似を入れるなら厳密な比較経路も持つ**: 探索を近似（上限値での shortlist）にしたら、小規模で真の上位と突き合わせられる厳密探索（`exactSearch.ts`）と比較テストを同時に維持する（ADR-005）。未確定の単調性に依存する枝刈りは使わない（`.claude/rules/game-facts.md`）。
- **ライブ最適化（`live*.ts`）は表示モデルへ依存しない**: `liveSkillTimeline.ts` / `liveFrequencyOptimizer.ts` から `displayScore.ts` を import しない（基礎発動確率も `LIVE_ACTIVE_PROBABILITY` として独自に持つ — 値が同じでも評価式が違う）。発動率の反映は表示側が加算・ライブ側が乗算で、**意図的に別式**なので片方に合わせて統一しない（ADR-007）。時刻は実数の秒で扱い、1 秒刻みの離散化や整数秒への丸めを推測で入れない。
- **目的関数と推薦ポリシーを混同しない**: ゲーム仕様の仮定（周期・確率の式）と「どの案を勧めるか」の方針（`FREQUENCY_RECOMMEND_POLICY` の 0.1 ポイント以内で省素材を選ぶ等）は別の定数に分け、UI の脚注でも「ゲームの仕様ではなくこのツールの方針」と書く。主目的関数はユーザーに見せる 2 つ（期待値 / 理論最大）だけにし、カバレッジ・空白は補助指標として tie-break と表示にとどめる — スコア UP の大きさを見ない指標を主目的関数にしない（ADR-007）。
- **探索の候補はボードの連結性から作る**: 発動頻度のような「マスを開ける」選択肢は `[0, 4, 8, 12]%` を仮定せず、`src/data/blueBoard.ts` の `unlockNode` で現在の解放マスから到達できる状態を列挙する（経路上の発動率マスも一緒に開くので、追加解放数と発動率が候補ごとに変わる）。**列挙は「現在値から増やす方向」だけにしない** — 発動頻度マスは 3 つとも枝の端（葉）なので、いま ON のマスをそのマスだけ外す候補（`removedNodeIds`）も含めて ON / OFF の全組合せを比べる（現在 12% でも 0 / 4 / 8% を探索する。2026-09-10 修正）。頻度マス以外の解放済みマスは固定し、コスト（`additionalNodeCount`）は新しく開けるマスだけ数えて「外せば素材が戻る」とは扱わない。現在の状態そのもの（追加 0・外す 0）は必ず候補に含める。
- **評価区間のような外から決まる値をゲーム仕様の定数にしない**: 曲を指定すれば曲長、指定がなければデータ由来の中央値（`medianSongDurationSeconds`）+ UI で変更可能にする。180 / 200 秒のような値を「ゲームの仕様」としてハードコードしない（表示スコアボーナスの T = 200 秒は実機 20 ケースの当てはめで決めた**そのモデル専用**の値で、ライブ側へ流用しない）。
- モデルの信頼度の区分（確定 / 強い推定 / 仮説）と実機とのずれの書き方は `.claude/rules/game-facts.md` に従う。仮説の式は差し替え地点として関数に切り出す。
