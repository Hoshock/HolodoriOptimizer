# 計算エンジンの構造（2026-09-09 ユーザー指示由来）

- **レイヤーを混ぜない**: 総合力（`power.ts`）/ ゲーム内表示のスコアボーナスとユニットスコア（`displayScore.ts`）/ 順位づけに後から掛かる倍率（`optimize.ts` の `ScoreModifierBreakdown` — 黄の楽曲スコアボーナスとイベント）/ 実ライブ中のスコア（**未実装**。将来別エンジン）は別モデルとして型・関数・定数を分ける（ADR-004 / ADR-005 / ADR-006）。表示モデル専用の推定値（`ACTIVE_PROBABILITY`）を「将来共有するかもしれない」共通の置き場に出さない — 同じ値になる保証がない。
- **使われなくなった近似モデルは残さず削除する**: `legacy` 名で隔離するのではなく消し、必要になったフェーズでゼロから作り直す（旧 `live.ts` の曲長按分モデルは順位づけ・UI とも未使用だったため 2026-09-09 に削除 — 検証されていない近似を「エンジン」の名前で残さない）。削除の前に `rg` で参照（UI・Worker・テスト）を確認し、報告に file / symbol / 理由を書く。
- **名前は実体に合わせる**: 意味がずれた型・関数・定数を放置しない（順位づけの値は実ライブの期待スコアではないので `expectedScore` → `adjustedUnitScore`、`liveFactorOf` → `scoreModifierFactor`、`OptimizeRequest.live` → `songBonus` に改名 — 2026-09-09）。
- **丸め・整数化の規則もレイヤーごとに分ける**: スコアボーナス欄はサーバーが返す permil 整数に合わせて 0.1% 単位の切り上げ（`toScoreBonusPermil`。実機 20 ケースのアクティブ欄が四捨五入 15/20 → 切り上げ 20/20 で一致）、総合力・ユニットスコア・パラメータは各々の確定した丸め（パラメータごとの切り上げ / 最後の ceil）。片方の規則を他方へ流用しない。浮動小数のずり上がりを防ぐ epsilon は許容するが、実機値へ寄せる補正は入れない（2026-09-09）。
- **依頼の解決と探索は 1 本にする**: カード ID・マス ID から「開花・ボードを解決して `optimize` を呼ぶ」までは `src/engine/request.ts` の `runOptimize` だけが持ち、Web Worker（`worker.ts`）はメッセージの受け渡しに専念する。6 枠すべて決まっている編成（お気に入りユニットの再評価）は組合せが 1 通りなので、同じ関数を UI スレッドから同期で呼ぶ（2026-09-09）。
- **近似を入れるなら厳密な比較経路も持つ**: 探索を近似（上限値での shortlist）にしたら、小規模で真の上位と突き合わせられる厳密探索（`exactSearch.ts`）と比較テストを同時に維持する（ADR-005）。未確定の単調性に依存する枝刈りは使わない（`.claude/rules/game-facts.md`）。
- モデルの信頼度の区分（確定 / 強い推定 / 仮説）と実機とのずれの書き方は `.claude/rules/game-facts.md` に従う。仮説の式は差し替え地点として関数に切り出す。
