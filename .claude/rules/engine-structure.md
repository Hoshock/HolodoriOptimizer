# 計算エンジンの構造（2026-09-09 ユーザー指示由来）

- **レイヤーを混ぜない**: 総合力（`power.ts`）/ ゲーム内表示のスコアボーナスとユニットスコア（`displayScore.ts`）/ 順位づけに後から掛かる倍率（`optimize.ts` の `ScoreModifierBreakdown` — イベントスコアボーナスだけ。**ロジックはあるがアプリからは未接続**で、`runOptimize` が渡さないので画面の値には掛からない — `pending.md` 8。黄の楽曲スコアボーナスは 2026-09-11 の実機確定でスコアボーナスのボード欄に入る側になり、`displayScore.ts` の `songBoardRaw` が持つ。後掛けしない）/ ライブ中のアクティブスキルの発動タイミング（`liveSkillTimeline.ts` + `liveFrequencyOptimizer.ts`。発動頻度マスの投資判断用。ADR-007）/ 実ライブスコアそのもの（**未実装**。譜面・コンボ・SP の発動位置を含む将来の別エンジン）は別モデルとして型・関数・定数を分ける（ADR-004 / ADR-005 / ADR-006）。表示モデル専用の推定値（`ACTIVE_PROBABILITY`）を「将来共有するかもしれない」共通の置き場に出さない — 同じ値になる保証がない。
- **使われなくなった近似モデルは残さず削除する**: `legacy` 名で隔離するのではなく消し、必要になったフェーズでゼロから作り直す（旧 `live.ts` の曲長按分モデルは順位づけ・UI とも未使用だったため 2026-09-09 に削除 — 検証されていない近似を「エンジン」の名前で残さない）。削除の前に `rg` で参照（UI・Worker・テスト）を確認し、報告に file / symbol / 理由を書く。
- **名前は実体に合わせる**: 意味がずれた型・関数・定数を放置しない（順位づけの値は実ライブの期待スコアではないので `expectedScore` → `adjustedUnitScore`、`liveFactorOf` → `scoreModifierFactor`、`OptimizeRequest.live` → `songBonus` に改名 — 2026-09-09）。
- **丸め・整数化の規則もレイヤーごとに分ける**: スコアボーナス欄はサーバーが返す permil 整数に合わせて 0.1% 単位の切り上げ（`toScoreBonusPermil`。実機 20 ケースのアクティブ欄が四捨五入 15/20 → 切り上げ 20/20 で一致）、総合力・ユニットスコア・パラメータは各々の確定した丸め（パラメータごとの切り上げ / 最後の ceil）。片方の規則を他方へ流用しない。浮動小数のずり上がりを防ぐ epsilon は許容するが、実機値へ寄せる補正は入れない（2026-09-09）。
- **派生する欄の値は、表示済みの丸め値ではなく表示に丸める前の raw 中間値から計算し、最後に 1 回だけ量子化する**（2026-09-11 ユーザー指示「必ず可能な限り既存の表示前 raw 値を使って計算すること」）。黄ボードの増分 黄 × (100 + アクティブ + パッシブ + SP) を表示済みの 77.0 / 2.3 / 46.0 から求めると 9.86% で丸め境界が合わず、`finishDisplay` の raw から求めて `songBoardRaw` → 量子化の順にすると実機 8 点がそろった。UI へ出す値を再利用して次の計算に入れない。
- **依頼の解決と探索は 1 本にする**: カード ID・マス ID から「開花・ボードを解決して `optimize` を呼ぶ」までは `src/engine/request.ts` の `runOptimize` だけが持ち、Web Worker（`worker.ts`）はメッセージの受け渡しに専念する。6 枠すべて決まっている編成（お気に入りユニットの再評価）は組合せが 1 通りなので、同じ関数を UI スレッドから同期で呼ぶ（2026-09-09）。
- **近似を入れるなら厳密な比較経路も持つ**: 探索を近似（上限値での shortlist）にしたら、小規模で真の上位と突き合わせられる厳密探索（`exactSearch.ts`）と比較テストを同時に維持する（ADR-005）。未確定の単調性に依存する枝刈りは使わない（`.claude/rules/game-facts.md`）。**shortlist の上限値は「同時候補の正規化 `max(1, Σp)` を入れた値」にする** — 正規化を無視した線形和は青ボードを開けたアカウントで 1.3 倍近く緩み、おまかせ探索が固定メンバーの探索より低い結果を返した（2026-09-30。ADR-005）。上限を変えたら、`shortlistSize` を絞った `optimizeShortlist.test.ts` で実データの厳密探索と突き合わせる。
- **ライブ最適化（`live*.ts`）は表示モデルへ依存しない**: `liveSkillTimeline.ts` / `liveFrequencyOptimizer.ts` から `displayScore.ts` を import しない（基礎発動確率も `LIVE_ACTIVE_PROBABILITY` として独自に持つ — 値が同じでも評価式が違う）。発動率の反映は 2026-09-13 に表示側も乗算型になり式の形はそろったが、**関数も定数も共有しない** — 評価対象が別（実ライブの発動 vs 表示欄の評価器）で、片方の反証・訂正でもう片方を自動的に動かさないため（ADR-007）。時刻は実数の秒で扱い、1 秒刻みの離散化や整数秒への丸めを推測で入れない。
- **発動頻度マスの目的関数は 3 つあり、モデルは混ぜない**: ライブ側の 2 つ（期待値 / 理論最大 — `liveFrequencyOptimizer.ts`）と、表示ユニットスコアを最大にする 1 つ。2026-10-08 から 3 つとも最適化の**頻度の段**（`frequencyStage.ts`。ADR-015）が持ち、候補（メンバーごとの頻度マスの部分集合と、その盤面）を作るのはこの段で、評価は各モデルが自分の式で行う — `live*.ts` は今までどおり `displayScore.ts` を import しない（表示ユニットスコアの評価は `teamEvaluator` を使う `frequencyStage.ts` 側に閉じ込める）。旧 `frequencyUnitScore.ts`（青だけを差し替える全探索）は、Pt を空けるために他の色も変わる候補を評価できないので廃止した。**推奨のユニットスコアは頻度マス込みの値を出す**（2026-09-30 の「値を画面に出さない」は 2026-10-08 に置き換えた — 最終的な値を見たいというユーザー指示。`W_blue` を通る近似であることは脚注に書く）。**頻度を固定した探索（`fixFrequencies`）は候補を絞るので `FrequencyPlan.choice` の添字が変わる** — 案を引くのは絞ったあとのメンバー（`frequencyStage.ts` は候補の同一性で元の添字へ戻す）。**候補を「発動率 % / 発動頻度 % が同じだから」と畳まない** — 青ボードには P/T/S のマスが並んでいて（`src/data/blueBoard.ts`）、どの頻度マスへ行くかで経路上に拾うパラメータが変わるので、同じ +4% でも総合力とユニットスコアは違う（2026-09-16 ユーザー指摘で修正）。畳んでよいのは**解放マスの集合が同じ候補だけ**。ライブ側は P/T/S を見ないのでこの問題がなく、モデルごとに畳み方が違うことも「混ぜない」理由になる。なお頻度の段の経路は、前の段の盤面から追加のボードPt が最小のもの（`BoardGraph.planUnlock`。コネクトの明示解放を含む）だけで、**遠回りして P/T/S を多く拾う開け方は探索していない** — UI の脚注にもそう書く。**ホロメンランクの Pt は超えない**: 足りない候補は経路を必須にしたまま、そのホロメンの 4 色のマスから「外して失う表示ユニットスコア ÷ 空く Pt」が小さいものを外して空ける（空けられなければ候補にしない）。**資材は不足してよい**（余りは負になる）。`liveFrequencyOptimizer.ts` の `enumerateFrequencyCandidates` / `buildFrequencyMembers`（コネクトを通れる通路として扱う旧来の列挙）は画面からは使っていない。
- **目的関数と推薦ポリシーを混同しない**: ゲーム仕様の仮定（周期・確率の式）と「どの案を勧めるか」の方針（`FREQUENCY_RECOMMEND_POLICY` の 0.1 ポイント以内で省素材を選ぶ等）は別の定数に分け、UI の脚注でも「ゲームの仕様ではなくこのツールの方針」と書く。主目的関数はユーザーに見せる 2 つ（期待値 / 理論最大）だけにし、カバレッジ・空白は補助指標として tie-break と表示にとどめる — スコア UP の大きさを見ない指標を主目的関数にしない（ADR-007）。
- **青ボードの実効値は live 側も display 側もコネクト増幅込みにする**（2026-09-14 に統一）。`liveFrequencyOptimizer.ts` は `buildFrequencyMembers(..., connect)` → `enumerateFrequencyCandidates(currentNodeIds, factors)` → `blueBoardEffects(unlocked, factors)` で、**現在の状態と全候補に同じ倍率表**を当てる。倍率表は `src/data/connect.ts` の `connectFactorsOf(...).blue` から作り、範囲・倍率の計算を `live*.ts` 側へ再実装しない。ADR-007 のモジュール分離（`live*.ts` から `displayScore.ts` を import しない・定数を共有しない）は崩さない。それまでは倍率なしで呼んでいて、この画面だけ表記値のままだった（発動率マスがコネクトの範囲に入るホロメンで実効値と期待値が低く出ていた — `liveFrequencyOptimizer.test.ts`「コネクト増幅」）。**候補の畳み込みは効果の値で決まる**ので、増幅で値が割れると同じマス数の候補が分かれることがある（列挙・経路・追加解放数の扱いは変えていない）。
- **探索の候補はボードの連結性から作る**: 発動頻度のような「マスを開ける」選択肢は `[0, 4, 8, 12]%` を仮定せず、`src/data/blueBoard.ts` の `unlockNode` で現在の解放マスから到達できる状態を列挙する（経路上の発動率マスも一緒に開くので、追加解放数と発動率が候補ごとに変わる）。**列挙は「現在値から増やす方向」だけにしない** — 発動頻度マスは 3 つとも枝の端（葉）なので、いま ON のマスをそのマスだけ外す候補（`removedNodeIds`）も含めて ON / OFF の全組合せを比べる（現在 12% でも 0 / 4 / 8% を探索する。2026-09-10 修正）。頻度マス以外の解放済みマスは固定し、コスト（`additionalNodeCount`）は新しく開けるマスだけ数える（外すと素材は実際に返ってくる — 2026-09-16 ユーザー報告。返還を引き算せず追加ぶんだけを数えるので、この値はこれから払う素材の上限になる）。現在の状態そのもの（追加 0・外す 0）は必ず候補に含める。
- **ホロメンボードの最適化は、固定した編成の表示ユニットスコアを、ホロメンごとのボードPt の予算内で最大にする別の計算**（2026-10-04 ユーザー指示。`boardOptimize.ts` の `optimizeBoards` + `boardPlan.ts` の `planBoards` + `optimizeWorker.ts`。出所・前提は ADR-012、資材の共有制約は ADR-013）。評価はコネクトの最適化と同じ `teamEvaluator` の経路（画面の値と一致 — `boardOptimize.test.ts`）で、ライブスコアの式は目的にしない。**どの結果も守る制約**: **キューブ・コアキューブは色ごとのアカウント共有の有限資材**（2026-10-07 ユーザー指示。マス別の消費量は外部 master 由来の `src/data/boardMaterials.ts`。**「リソース」の登録値は余り**なので、再配分できる総量 = 変えてよいホロメンのいまのボードへ投入済みの資材 + 余り。`scope = unit` ではユニット外のホロメンの使用分を回収しない。未登録の項目は制限なし、0 は余りが 0 個。候補はホロメンのボードPt と共有の資材の**両方**に収まるときだけ採用し、資材に上限のある色では Pt 最小の経路だけでなく Pt・cube・core の非劣な経路すべてを評価する — `BoardGraph.planUnlockRoutes`。推奨を反映するとき余りのリソースも新しい盤面に合わせて置き換える — `BoardPlanResult.remainingAfter`。**手動のボード操作は資材で制限しない**）/ ランク登録済みのホロメンは 通常マスのPt + 解放した非中心コネクトのPt ≤ 累積ボードPt（未登録は制限なし）/ 解放済みのセルはすべて中心から解放済みのセルだけで届く（コネクトの先ならコネクトも解放済み）/ **コネクトの配置は変えず、配置のある非中心コネクトは必ず解放済み**（1 Pt を予算に含み、ランクが低くて足りないホロメンは変更せず `infeasible` に載せる）。選び方は近似（**ターゲットのマスに必要な未解放の経路一式を 1 つの解放プランとして**追加Pt と増分で評価する遅延評価の貪欲法。出発点は「必須だけ」と「登録している状態（整合しているホロメンのみ）」、順は増分 ÷ Pt と増分の 2 通り（資材に上限があるときは増分 ÷ 資源の消費の割合も）で最良を選び、同点は登録に近いほう。土台（頻度マスを外した登録）を下回るときは土台を返し、効かず選ばれなかった登録済みのマスは予算が許す限り戻す）。最大を保証しない。**青の発動頻度マス（B-013 / B-020 / B-031）はすべて OFF にして最適化する**（2026-10-07 ユーザー指示。ADR-014）: 頻度の配分はそのあとの頻度の段の担当（ADR-015）。頻度マスは枝の端（葉）なので、外しても他のマスは孤立しない。変えてよいホロメンは**登録の頻度マスを外した状態**（`withoutFrequencyNodes`）から出発し、頻度マスはターゲットにも経路にもしない。**「現在」のスコアも頻度マスを外した状態の値**で、評価器（`planBoards`）は変えないホロメンの頻度マスも外して評価する。登録していた頻度マスの資材・Pt `src/data/boardState.ts`。**発動頻度の最適化（`liveFrequencyOptimizer.ts`）は青のコネクトを解放済みとして扱う**（別の責務）。**コネクトの最適化は解放済みのコネクトマス（と中心）にだけ置く**（`assignConnects` の `unlockedConnects`）。**ボードとコネクトは 1 `pending.md` 8）。各段は土台を下回らない（ボードは土台のまま返す・コネクトは厳密に上がる変更だけ）。段の間でボードは最適化後の盤面とその**余りのリソース**（`remainingAfter`）を、コネクトは最適化後の配置を次の段の出発点にする。コネクトの範囲は常にユニットのみ（`scope` コネクトのあとの盤面から頻度マスを選び、経路が盤面で一意に決まるので**反映もする**。「現在」は、頻度を選んだときは登録そのまま（頻度マス込み）、選ばないときは頻度マスを外した登録の値。
- **評価区間のような外から決まる値をゲーム仕様の定数にしない**: 曲を指定すれば曲長、指定がなければデータ由来の中央値（`medianSongDurationSeconds`）+ UI で変更可能にする。180 / 200 秒のような値を「ゲームの仕様」としてハードコードしない（表示スコアボーナスの T = 200 秒は実機 20 ケースの当てはめで決めた**そのモデル専用**の値で、ライブ側へ流用しない）。
- **候補を減らすしぼりこみは持たない**: 「衣装スキル発動に限る / パッシブ全員発動に限る」は 2026-09-16 に UI ごと撤去し、`optimize.ts` / `exactSearch.ts` の `requireCostumeSkill` / `requireAllPassives` も消した（ユーザー指示「内部的にはそれらを考慮せず全探索する」）。**復活させない** — プールが小さいとメンバー 5 枠の組合せが 1 通りしかなく、条件 1 つで 0 件になっていた（2026-09-14: 所持カード 5 枚であいうえお順の上位 — アーニャ / アイラニ / IRyS / 赤井はあと / アキ — を登録すると、アーニャのパッシブ「holoro が2人以上で」が満たせず 0 件）。発動しているかどうかは候補から外さずに結果側で見せる（`breakdown.costumeSkillActive`）。
- **表示ユニットスコアの順位とライブ側の順位を同じものとして扱わない**（2026-09-16）。表示ユニットスコアに曲の長さは入らない（実機確認済み — `docs/human/game-spec.md`）のに対しライブ側は曲長・ノーツで決まるので、順位が一致する理由がない。**「ユニットスコア最大の編成を選ぶ → その編成で発動頻度を最適化する」はライブ期待値の最大にならない**: 所持 34 枚・リーダー固定の 248,946 編成を代理指標 `総合力 × (1 + 期待スコア UP の時間平均 / 100)` で総当たりすると、ユニットスコア 1 位はライブ 23 位（頻度を最適化し直しても 573,670 対 582,882 で負ける）。同じ編成の中でも、表示側は青の発動頻度を `W_blue` 経由でしか見ないので頻度マスの最適解が live 側と割れる（表示側の最大は全開ではなく、live 側の理論値最大とは逆向きに動く）。**表示側の指標でライブの意思決定をせず、ライブ側の指標で表示値を説明しない。** 代理指標そのものが未検証であることは `docs/ai/tmp/pending.md` の実ライブスコアエンジンの項に置く。
- モデルの信頼度の区分（確定 / 強い推定 / 仮説）と実機とのずれの書き方は `.claude/rules/game-facts.md` に従う。仮説の式は差し替え地点として関数に切り出す。
- **素値合計が同値のメンバーの選び方は「最良」を採る暫定方針**（2026-09-30 ユーザー指示。実機の規則は未確認 — `pending.md` 16）。総合力のパッシブは効果ごとに加算量の大きい方（`power.ts` `passiveParamBonus`。並びに依らない）、表示スコアボーナスのスコアサポートは同値メンバーの並べ替えを試して最良（`tieOrder.ts` の `bestTieOrder`。`optimize.ts` と `exactSearch.ts` の正確評価で共有し、結果の `members` はその並びで返す）。**編成順に依る選び方を評価器へ戻さない** — 同じ 5 人が並べる順で違う値になり、固定ありの探索とおまかせの探索で食い違う。上限値（shortlist）は並びに依らない形（スコアサポートの倍率は最大側）なので上限のまま。
- **探索はコネクトのオプションを持たず、登録している（ボードで置いた）コネクトで常に計算する**（2026-10-02 ユーザー指示。同日に入れた「コネクトを外した探索は探索のあとに最適な配置を選び直す」近似は撤去した — 復活させない）。`runOptimize` の `connectPlacements` がそのまま探索・表示に効き、ボード状況を考慮するかどうか・全カードかどうかに関わらない。
- **コネクトの最適化は、所持のコネクトの範囲で、いま置いている配置から良くなる変更だけを重ねる別の計算**（2026-10-02 ユーザー指示。`connectOptimize.ts` の `assignConnects` + `connectPlan.ts` の `planConnects`。いまは最適化の中のコネクトの段 — `planBoardConnect`）。**所持（形 × ％ × 枚数。`connectInventory.ts`）の範囲**で、その編成 1 つのユニットスコアが**厳密に上がる**変更だけを確定する（**変更量を最小にする**方針。置いても置かなくても同じ場所は現状維持なので、出発点が現在の配置であれば返す配置のスコアは現在以上）。**空から置き直さない** — 空から貪欲に置くと、所持にない形を置いている場所や効果が 0 の場所が「なし」へ落ち、変更が膨らむ。変えてよい範囲は `scope`: `unit`（リーダーとメンバーのホロメンだけ。ユニットが必要で枚数が足りないときだけ、**外して失うスコアが最小の場所**（同じならユニット外を先に）から回す）/ `all`（全ホロメン）。評価は 6 枠固定の依頼と同じ経路（`request.ts` の `teamEvaluator` が `optimize` に編成の 6 枚だけを渡す。カード全部を解決し直さない）にして、画面の値と「同じ配置を登録して出した値」が一致するようにする（`connectOptimize.test.ts`）。選び方は**遅延評価の貪欲法**（変更先ごとに 1 枚置いたときの増分を測り、大きい順に取り出して置く直前に測り直す）で、**近似であることを脚注に書く**。効かない候補は試さない（解放済みのマスに掛からない・スコアに効かないマス・効かない色 — 青はメンバーのホロメン、赤はリーダー、黄は曲あり）。**現在の配置が所持に収まっていること**は呼び出し側（OptimizerPanel の `placementShortage`）が先に確かめ、収まっていなければ最適化せずエラーを出す。基準は**登録している状態**。**目的は表示ユニットスコアだけ**で、ライブの理論値を最大にする置き方とは一致するとは限らない（`connect-effect.md`「コネクトの最適化の性質」）。近似の精度は `pending.md` 18。
