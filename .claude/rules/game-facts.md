# ゲーム仕様の確定は実機確認だけ（2026-09-07 ユーザー指示）

- ゲームの仕様（ボードのマス配置・接続線・マスと効果の対応・値、スキルの実文言）は**ユーザーの実機確認だけを確定**とする。公開の攻略情報・他ツールの解釈・解析由来のデータは参考程度（仮説と確認箇所の絞り込み）にだけ使い、必ず実機で確認する。確認前の内容をリポジトリに「確定」として書かず、未確認の項目は「未確認」と明記する。仮説メモはリポジトリの外に置く（解析由来の情報を出典にしないので ADR-002 とは矛盾しない — 緑ボードの引き継ぎで確認）。例外は**実機画面では原理的に確認できない項目**（発動確率の実数値・サーバー応答の構造など）で、これは 【外部情報】 と明示し「確定」と書かない形でだけ記録してよい（2026-09-09 ユーザー指示。数値データ・識別子・ファイル名などダンプ由来の成果物そのものは持ち込まない — ADR-002）。**効果の種別と値**が外部情報で分かることと、**その値をゲームの計算式がどう換算するか**は必ず分けて書く（例: 青ボードのマスが「発動確率 UP」「クールタイム短縮」であることは分かっても、編成画面のスコアボーナス欄の算出方法は未解明）。
- 位置・効果・接続線は**別々に**検証する。青では他の解釈をそのまま写した位置と効果の対応が一部違い、近いマス同士を繋いだ推測の接続線も実機と食い違った（2026-09-06）。緑では逆に、図から「線がない」と読んだ 6 組が実機では繋がっていた（2026-09-07）— 図の省略と実機の欠線を区別できないので、線の有無も聞く。
- 訂正は指摘された範囲だけを直し、指摘されていない箇所を「ついでに」入れ替えない。青の「上下が逆」（2026-09-06）の訂正時に上・下の 5 マス塊の左右も一緒に入れ替え、2026-09-08 に「上と下のブランチの左右が逆になってる」と再訂正された。訂正で複数の向きを変えるなら「左右も入れ替えたか」を確認項目に入れて聞く。
- 実機確認の依頼は、開く画面・見る（タップする）場所・答えてほしい形（番号つきの図と「番号 → 文言」の表）まで具体的に書く。「各マスの文言を中心から辿った順に」「所属向けマスの個数・位置・値を 3 名で」のような項目名だけの依頼は「何を確認したいのかがよくわかってない」となった（2026-09-07）。仮説があるなら仮説を表で見せて「合っているか、違うところだけ」と聞くのが最も速かった。
- 楽曲の区分（ソロ = ホロメン 1 人 / ユニット = 複数人 / 全体 = hololive IDOL PROJECT）と、所属名で書けない曲の歌唱者はユーザー確認の事実（2026-09-08）。`src/data/songSingers.ts` が `artists` から導き、曲別の歌唱者は `SONG_SINGER_OVERRIDES` に持つ。推測で埋めない。
- 確定した構成の正典は parameter-calculation スキルの `references/<color>-board.md`（配置図・座標と効果・接続線・大マス・全取得合計・実機確認のログ）。実装（`src/data/*Board.ts`）はそれを写し、テストで座標・接続・合計を固定する。割合はゲーム内どおり小数第 1 位まで（+4.0%）で書く（2026-09-08）。大きいボード（赤 63 マス）は実機確認も 1 エリアずつ（位置 → 大マス → 線 → 効果の順）で、図のコネクトは 1 つだけ描く（C を 2 段に描いて「上の C は上エリアの 1 つ目」と訂正された — 2026-09-08）。確認中の段階でも確認できた分は正典に「確認中」「未確認」を明記して書いてよい。
- イベント（開催期間・獲得ボーナスの対象カードとホロメン・倍率・課題曲とスコアボーナスの対象カード・開花ボーナス表）はユーザー確認の事実（2026-09-08）。`src/data/events.json` に既存の ID で持ち（名前から解決し、ID を発明しない）、新イベントはデータ 1 件の追加で対応する。獲得ボーナスの「メンバー」はカード単位・「ホロメン」は人物単位で別々に加算、スコアボーナスは対象カードが何枚でも +10% 上限。リーダー枠は判定に入らない（2026-09-08 確認）。イベント用スコアの式の位置は未確認（pending 11）。
- 総合力（ユニット編成画面）の構造はユーザー実機の内訳（2026-09-08、2 ケース + 青ボード変更 2 例）で確定した事実: 6 項目の加算・素値基準・切り上げ・「◯◯2人の」は素値合計の上位 count 人（2026-09-12 に「対象パラメータ上位」と「編成順の先頭」を実機で否定）・強化ボーナスはメモリー抜き（parameter-calculation スキル「総合力の構造」、`src/engine/power.ts`）。表示のユニットスコア = ceil(総合力 × (1 + スコアボーナス/100) × 2.03734) は実機 20 ケースで全一致（確定）。スコアボーナス 4 項目の内部式（`src/engine/displayScore.ts`）は「確定 / 強い推定 / 仮説」の 3 段階で信頼度を分けてファイル冒頭・テスト・pending 12 に書き、仮説の式は差し替えやすいように関数へ切り出しておく（`blueActivationProbability` / `blueActivationInterval` / `attributeDisplaySupport`） — アクティブ欄（5 人共通の 200 秒タイムライン、確率 55/46/37）と SP 欄は強い推定、青ボードとパッシブのスコアサポートは仮説。実機の表示は 4 欄だが、サーバー応答は 5 カテゴリ（アクティブ / リーダー（衣装）/ パッシブ / スキルツリー / スペシャル）の独立値だという【外部情報】があるので、タイムラインの差分でボード欄・パッシブ欄へ配賦する現在の実装を「ゲーム内部の式」と書かない（2026-09-09。ADR-006 の Update）。
- ホロメンボード効果の実機比較実験は、`src/data/boardGraph.ts` の連結性で**到達可能なマスの集合**だけを扱う（2026-09-09）。ボードは初期地点からつながっているマスしか解放・解除できないので、青の発動率 UP・発動頻度 UP・パラメータのマスを**独立変数のように任意に変えられると仮定しない**（「発動率だけ 33% → 15% にして」のような実現できない実機確認を依頼しない）。複数のマスが同時に変わった実測を「発動率だけの実験」等と表現せず、外したマスと総合力の変化まで記録する（status.md の「9.13〜9.17 で実際に外したマス」）。同じ理由で、探索の枝刈りに「頻度が高いほど必ず強い」「発動率は同じ比率で効く」のような未確定の単調性を使わない — 上界は数学的に真値以上と保証できるものだけ使う（実機で頻度の非単調性が確認済み。ADR-005）。
- **ゴールデンの実機観測列は変更しない**。モデル列だけを再実行の結果で更新し、実機へ手で寄せない（2026-09-09、3 回同じ指示）。誤差の上限（regression の閾値）は締める方向に更新し、緩めるのは**入力の実機値が訂正されたとき**だけ — そのときは「モデルを通すために緩めたのではない」と理由をテストのコメントに書く。
- ホロメンボードの発動率 UP・発動頻度 UP は**コネクトマスの増幅を含む実効値**（カード画面の表示値）で記録する。値の訂正が来たら、**その観測がいつの状態のものか**を必ず確認する — 現在値と観測時点の値が違うことがあり、観測時点が不明なものは現在値へ差し替えず「保留」と書いて分ける（2026-09-09: フブキ 33 → 39・ぺこら 24 → 30・みこ 37 → 36 は訂正、ころね 33.6 と 9.16 / 9.17 の 15 / 6 は保留）。
- 実機再現のモデルは、実機値に合わせるための場当たりの定数・補正・ケース別の当てはめをハードコードしない。ゴールデンケース（実機値とモデル値を並記して固定）に一致しない項目は無理に合わせず「どの計算段階から何点ずれるか」をテストとドキュメントに明記し、報告は 実装した式 / 実測で確定した部分 / 仮説のままの部分 / ケース別の実機・モデル・誤差の表 の形にする（1 回目の引き継ぎ「段階と点数を報告」と 2 回目「expected / actual / error を Markdown で」— 2026-09-08、同種 2 回）。未確定でも仮定を明示すれば数字を出してよい（「多少ズレてもいいから仮定で実装して」— 同日。出さないより、試算と明記して出す方がよい）が、実機値に合わせるために仮定を後から個別にいじらない。
- **1 つの編成の観測にしか合わせていない定数を「実機確定」と書かない**（2026-09-11、赤スコアサポートの 0.88）。同じ 5 人で X だけを変えた点がそろっても、それは「その編成での実機再現則」にとどめ、編成を変えた 2 点目が出るまで一般式として確定にしない。編成依存を示す観測が出たら、別の定数（0.85 など）に置き換えるのではなく、編成から計算できる構造（候補秒率など、既存のタイムラインから導ける量）に置き換える。アカウントの構造化データから再計算した**現在の**実効値は同日の観測にだけ使い、観測時点の状態が確認できない過去のゴールデンへ流用しない（historical snapshot と current snapshot を混同しない）。
- **1 つの実機確定を、別の効果や別の未確定項目まで「解決済み」に広げない**（2026-09-11 ユーザー指示「黄の今回の実測からこれらまで『解決済み』にしない」）。黄の楽曲スコアボーナスがボード欄に入ると確定しても、イベントスコアボーナスの適用位置・ボード欄 / パッシブ欄の算出式・青の発動率 / 頻度の換算・赤の一般式・実ライブスコア・SP の発動タイムラインは未確定のまま書く。解けたのは何か（黄なら「適用位置と増分の形」）を明記し、同じ画面の隣の項目にまで確定を波及させない。
- **`cards.json` の値は検索結果の近傍スニペットだけでカードを同定せず、必ずカード ID と object の境界を確認する**（2026-09-12）。赤スコアサポートの 3 編成目の解析で、隣接する object のアクティブの周期 / 効果時間（水着フワワの直前にある `takane-lui-02` の 28/9 など）を対象カードへ誤対応し、基準候補秒 140/200 → 7.0 で「候補秒率換算を反証した」と読みかけた（正しくは 174/200 → 8.7 で実機 +8.7 と一致）。テストのフィクスチャは手打ちの周期 / 効果時間ではなく**実カード ID + `cardAtBloom`** から取る（`displayScore.test.ts` の `member()`）。実機の通常のアクティブ欄（77.0 / 78.9 / 77.9）がモデルと一致することを、赤の結果とは独立した入力の検証として使う。
