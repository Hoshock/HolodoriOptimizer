# Journal

ユーザーの訂正と、作業中に自分で見つけた再発しうる落とし穴を記録する。あとの棚卸しで規則にまとめられるよう、具体的なまま残す。

記録先は1か所で、そのリポジトリの CLAUDE.md の「ドキュメントの分担」表が「ユーザーの訂正・作業中に見つけた落とし穴」の行で指すファイル。表がなければ `docs/ai/tmp/journal.md`。ファイルがなければ作る。訂正を受けたターン、または落とし穴に気づいたターンのうちに書く。コンパクションをまたぐと、具体的な言い回しや手順が要約で失われ、あとから規則にできなくなるため。

ここから CLAUDE.md やスキルへ直接書き込まない。1回の訂正をその場でルールにすると、場当たりの追記が積もってルール同士が食い違う。

## auto memory との関係

そのリポジトリに関わる訂正と落とし穴の正典は journal.md で、auto memory ではない。auto memory はリポジトリをまたぐ挙動やユーザー自身の特性のためのものだが、リポジトリに関わる内容が書かれることもある。その場合も journal.md に書くことをやめない。auto memory 側の重複は棚卸し(`distill`)が journal.md と同じように扱い、移したあと消す。

## 分類

| 分類       | 判定                                                                                              | 扱い                                                                                               |
| :--------- | :------------------------------------------------------------------------------------------------ | :------------------------------------------------------------------------------------------------- |
| その場限り | 事実の修正や、その場の文脈に合わせた調整で、好みが読み取れない。1回のやり直しで解消した失敗もここ | 反映するだけで記録しない                                                                           |
| 事例       | 好みや再発しうる落とし穴は読み取れるが、根拠がその1回しかない                                     | 具体的なまま記録する: 日付・対象・何がどう変わったか・ユーザーの言い回しか再現手順・読み取れる好み |
| 規則       | ユーザーが一般化を明言した(「今後は…」「他も…」)、または同じ種類の2回目                           | 規則の文として記録し、まとめた事例は消す                                                           |

その場限りにも規則にも当たらないものは、事例として記録する。規則は少ないほど効く。

## 規則にする前の確認

次の3つをすべて満たすときだけ、規則として記録する。満たさないものは事例のまま残す。

- 訂正なら、別の文書でユーザーが次に何を直すかを予測できる。落とし穴なら、別のセッションで同じ手順を踏めば再現する
- ユーザーがすでに承認した文書に当てはめても、直す箇所が出ない。出るなら一般化しすぎている
- 固有名詞を消しても意味が通る

## journal.md の構成

`## 規則` と `## 事例` の2つの節に分ける。
