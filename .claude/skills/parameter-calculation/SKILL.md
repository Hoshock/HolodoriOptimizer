# Parameter-Calculation

ゲームの公式な計算式は公開されていないので、このツールの値は実機の表示を観測して組み立てたモデルによる。このスキルは、観測とカードデータをどこまで事実として扱ってよいか(証拠の扱い)と、いま分かっているゲーム仕様の要点を定める。証拠の状態ラベルの定義は `docs/ai/evidence-policy.md`、カード DB の出所は `docs/ai/card-data-provenance.md`、表示ユニットスコアの式と棄却した仮説は `docs/ai/display-score.md` が正典で、カードの値を使う前に前の 2 つを読む。

## 証拠の扱い

- 権威の順は「実機表示 > 公式・公開構造情報 > 外部解析 > 仮説」。ただし人が実機から転記した値にも誤りは起こりうるので、単発の報告 `reported`・再確認 `rechecked`・算術の一致 `cross-checked` を区別する。算術の一致は入力条件の再確認の代わりにならない。転記・再構成・推定も区別する。
- Golden の実測値をモデルに合わせて変えない。入力条件が怪しい観測は消さずに「要再確認」へ下げる。直してよいのはユーザーが誤記を明示したときだけで、理由を履歴に残す。
- 式から逆算した値を実測欄へ入れない。テストの期待値は実機の値だけで固定し、推定値・流用値から出した数字をテストへ書かない。
- ケース別の magic constant を入れない。仮説に反例が出たら、例外を継ぎ足す前に棄却を検討する。1 つの確定から、隣の未確定の項目まで確定に広げない。
- 同時に複数の要因(カード・Lv・開花・タイプ・スキル)が変わった比較を、単独差分(「○○だけを OFF にした実験」)と呼ばない。
- 観測時点のアカウント状態を、いまの値で上書きしたり、過去の観測へ流用したりしない。
- 実装の近似とゲーム内部の式を分け、反証された実装は「既知の近似」と明記する。コードのコメントやテストに古い仮説が残っていても、docs/ai/ の正典に反する説明をゲーム事実として再利用しない。反証を見つけたら、正典 → 再現資料(`docs/ai/repro/`)→ コメント → テストの順にそろえる。
- モデルの信頼度は「確定 / 強い推定 / 仮説」で書き分ける。

## カードデータ

- `src/data/cards.json` は取り込み元のレコードで、ランタイムの正典は `src/data/index.ts` の `cards` / `cardById`。`cards.json` の検索断片や隣のオブジェクトだけでカードを帰属しない。カードの仕様を述べる前、因果の説明に使う前に、card ID・holomen ID・役割(リーダー / メンバー)・開花段階・provenance を確かめる。
- リーダーの衣装スキルとメンバーのパッシブを取り違えない。
- 実機での訂正は `src/data/cardCorrections.ts` に明示し、テストで固定する。
- `bloomVariants.raw` を無条件に「ゲーム内原文」と呼ばない。`src/data/bloomEvidence.ts` で確かめる。
- スキル文言は「確認済 / 未確認」の 2 状態で管理する。記録のない開花段階は「未確認」と表示し、計算には最も近い凸の内容をそのまま使う(`unknown`)。流用した値はゲーム事実ではない。`cardAtBloom()` の値を実測と呼ばず、出所が要るときは `cardAtBloomWithProvenance()` を使う。

## 逆解析の実験

- 位置・効果・接続線は別々に検証する。条件にするのは、到達可能なボード解放集合だけ。
- 解放済みのマスは外して振り直せ、外すと素材は全部返ってくる(正典は `docs/ai/game-spec.md`「ホロメンボード」)。振り直しの前後を同じ観測系列として扱わない。探索のコストを「新しく開けるマス」だけで数えるのは、これから払う素材の上限になるため(`engine-structure`)。
- 青 / 赤 / 黄 / 緑の実効値を解析 fixture へ手入力するときは、マスの表記値ではなくコネクトの増幅込みの値を入れる。増幅は production の `connectFactorMapOf` → 各色の `*BoardEffects` に、アカウントスナップショットの保存値(解放マス + コネクトの配置)を通して確かめる。コネクトの図形はホロメンの左右型で反転せず、物理座標の絶対方向(ADR-008。青が右のホロメンでも「左へ 3」は左へ 3)。例: 発動率をマスの表記値 6% で入れると解析を誤る(正しくは 1500‰ の増幅込みで 15%)。

## 横断事実

正典は `docs/ai/display-score.md` と `docs/ai/game-spec.md`。ここは計算と逆解析で毎回効く要点だけで、式の導出や候補の比較はしない。

- リーダー 1 + メンバー 5 は別枠。リーダーカードから試算に入るのは「衣装スキル」と「そのホロメンの赤ボード」の 2 つだけで、リーダーカードの P/T/S・開花段階・パッシブ・アクティブ・SP はどこにも入らない(総合力はメンバー 5 人ぶんの加算で、衣装スキルの条件判定もメンバー 5 人だけを数える — `isConditionMet`)。衣装スキルの内容は開花段階で変わらないので、リーダーの開花段階は値を 1 pt も動かさない。赤はリーダーにしたホロメンのボードがメンバー 5 人へ効き、歌唱者条件などの発動判定もそのホロメン(カードではない)の状態で決まる。UI でリーダーに開花の値を見せるときは最大(5凸)で出す。
- Active は 200 秒の共通タイムラインのモデルが既存の Golden に高い精度で一致する。曲の長さは表示ユニットスコアに入らない(曲で変わるのは黄の楽曲スコアボーナス・赤の歌唱者条件・イベントの 3 つだけ)。曲長を使ってよいのはライブ側の試算だけ。
- 青ボードの反映は、発動率が乗算型 `min(1, p0 × (1 + r/100))`、発動頻度が `周期 ÷ (1 + f/100)`。頻度側の非単調な実機系列(4.6 → 4.7 → 4.4 → 5.0)は、同時候補の正規化 `max(1, Σp)` と projective 配分を合わせると、自由係数なしで再現できる。
- 黄 10% の直接対照は、`Y × (100 + Costume + Active + Passive + Special)` のボード増分を支持する。
- SP 欄は `表示アクティブ欄 × Σ_i (効果時間_i/120) × (支援_i/100) × (1 + 発動率 UP_i/200)` の 0.1% 切り上げ(確定。カードデータに記録のある実機 23 編成で誤差 0)。SP スキルごとの独立な加法項で、発動率 UP はタイムラインを動かさず、自分の支援項を定数倍するだけ。条件は SP ごとに評価し、基準は raw ではなく表示のアクティブ欄。旧「効果時間 / 100 × タイムライン再評価の差分」型は棄却済み。
- 赤スコアサポートの旧候補秒率式は、一般式としては棄却済み。
- スコアサポート(赤・リーダー衣装)の表示合計への総増分は `支援/100 × E_blue(乗算)` が強い推定。リーダー衣装・赤・パッシブの支援は加算で合成する(乗算ではない)。パッシブのスコアサポートは静的で、供給側の発動確率で割り引かない(gated 型は棄却)。
- 青がなければ、リーダー支援の増分はパッシブ支援の有無によらず全量が衣装欄に入る。カテゴリ再配賦の起点は青。
- 表示 5 欄のうち衣装 / ボード / パッシブは、「source ごとの増分の和 `T`」を「source ごとの raw weight `W`」で按分する(`(C,B,P) = T × W/ΣW`)。衣装欄はアクティブ欄との差 `ceil(A + C) − ceil(A)` で量子化される(確定。いまの独立切り上げは棄却済みだが、production はまだ独立切り上げのまま)。`W_C` はリーダーのスコアサポート % に比例する。残る不定性はメンバーごとの `w_i` だけ(`display-score.md`「量子化」、`pending.md` 4)。逆解析での注意:
  - 表示の 0.1 刻みから raw へ戻すときは量子化規則の仮定が入るので、切り上げと四捨五入を分けて評価する。
  - `A` の量子化ぶれ(1 quantum = 要求区間の幅と同じ桁)を入れずに区間を出さない。
  - `W` は定数倍しても同じ表示になる。raw の `W` をデッキ間で比べる議論は gauge を固定した比較で、構造的な棄却には gauge に依らない比(`B/C`・`P/C`・同じ編成での複数状態の一定性)を使う。
- `W_blue`(青ボードの配分の重み)は、青を実効スコアサポート % に直す形 `(青の実効支援%/100) × H_C` がいまの最有力で、確定ではない(実装は `displayScore.ts` の `blueSupportPercentOf`。式・候補の比較・棄却した族は `display-score.md`「`W_blue` の決定式」が正典で、ここで導き直さない)。効くのは 2 点: 青の % は直接効き、青の窓・青の確率は入らない / メンバーの重みは青の状態に依らないが、所有者には依る。棄却済みの族(編成全体の評価値どうしの差の型、member-local 型、2 つの分母をそろえる形)を作り直さない。残る未解決は `pending.md` 3。

## カード詳細 P/T/S

- 反映する: カード本体の Lv / 開花、青・緑、所属向けパラメータ、コネクトで増幅した青・緑。
- 反映しない: 赤、メモリーのユニットパラメータ、メンバー強化、編成条件の衣装 / パッシブ、Active / SP のスコア効果。

## 開花

確認済みの ★5 の強化段階:

| 段階 | 主な強化     |
| :--- | :----------- |
| 1凸  | Active       |
| 2凸  | 全パラ +10%  |
| 3凸  | SP           |
| 4凸  | Passive      |
| 5凸  | Connect 関連 |

トップレベルのカード値は、最大開花の側の取り込みレコード。途中の段階は `cardAtBloomWithProvenance()` で出所つきで引く。

- `observed-variant`: 実機の variant
- `reconstructed-observation`: 数値は実機由来だが、raw の文は再構成
- `extracted-master-variant`: 抽出マスター(外部解析)由来。実機の目視ではない
- `derived-from-max-confirmed-ratio`: 2凸 +10% からの逆算
- `unknown`: その段階の記録がない。文言は「未確認」で、計算には最も近い凸の内容を流用する(仮定の倍率で推定はしない)

推定値を確定値として引用しない。

## ボードの役割

- 赤: リーダー用。メンバー 5 人への P/T/S・スコアサポートなど
- 青: メンバー本人の P/T/S・Active の発動率 / 頻度
- 黄: 曲・ホロワーク
- 緑: アカウント全体の P/T/S・所属効果

ボードの状態はホロメン単位。

## 総合力

```txt
totalPower = memberParameters
           + costumeSkill
           + holomenBoard
           + passiveSkill
           + memory
           + enhancement
```

各項目は素値を基準に独立に計算する。count 人が対象の確認済みの効果は、対象候補の素値 P+T+S の上位を選ぶ。メンバー強化はメモリーを基準に含めない。赤の P/T/S はボードの項に入る。丸めには ±1〜2 の未解明が残る。

表示ユニットスコアの入口だけは次の式で、表示カテゴリの内部は `docs/ai/display-score.md`、実ライブは ADR-006。

```txt
ceil(totalPower × (1 + scoreBonus / 100) × 2.03734)
```
