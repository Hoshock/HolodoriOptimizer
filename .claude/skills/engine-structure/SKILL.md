# Engine-Structure

計算エンジンは、ゲーム内表示の値(総合力・表示ユニットスコア)を再現するモデルと、そのモデルの上で編成・ボード・コネクト・発動頻度を選ぶ探索と最適化からなる。このスキルは、モデルを混ぜないための境界と、探索・最適化が結果を変えずに守る約束を定める。ゲーム仕様そのもの、証拠の扱い、モデルの信頼度(確定 / 強い推定 / 仮説)の書き方は `parameter-calculation` にある。

## レイヤーを混ぜない

- 次の 5 つは別のモデルとして、型・関数・定数を分ける(ADR-004 / 005 / 006)。片方の訂正がもう片方へ黙って波及しないようにするため。
  - 総合力(`power.ts`)
  - ゲーム内表示のスコアボーナスとユニットスコア(`displayScore.ts`)
  - 順位づけに後から掛かる倍率(`optimize.ts` の `ScoreModifierBreakdown`)。中身はイベントスコアボーナスだけで、ロジックはあるがアプリからは未接続(`docs/ai/tmp/pending.md` 10)。黄の楽曲スコアボーナスはボード欄に入る側で `songBoardRaw` が持ち、後掛けしない
  - ライブ中のアクティブスキルの発動タイミング(`liveSkillTimeline.ts` + `liveFrequencyOptimizer.ts`。ADR-007)
  - 実ライブスコアそのもの(未実装。将来の別エンジン)
- 表示モデル専用の推定値(`ACTIVE_PROBABILITY`)を、将来共有するかもしれないからと共通の置き場に出さない。同じ値になる保証がない。
- ライブ最適化(`live*.ts`)は表示モデルに依存しない。`displayScore.ts` を import せず、基礎発動確率も `LIVE_ACTIVE_PROBABILITY` として別に持つ。値が同じでも評価対象(実ライブの発動と表示欄の評価器)が別で、片方の反証・訂正でもう片方を自動的に動かさないため(ADR-007)。時刻は実数の秒で扱い、1 秒刻みの離散化や整数秒への丸めを推測で入れない。
- 表示ユニットスコアの順位とライブ側の順位を同じものとして扱わない。表示ユニットスコアに曲の長さは入らない(`docs/ai/game-spec.md`)が、ライブ側は曲長・ノーツで決まる。ユニットスコア最大の編成で発動頻度を最適化しても、ライブ期待値の最大にはならない(所持 34 枚・リーダー固定の 248,946 編成を代理指標で総当たりすると、ユニットスコア 1 位はライブ 23 位で、頻度を最適化し直しても 573,670 対 582,882 で負ける)。同じ編成の中でも、表示側は青の発動頻度を `W_blue` 経由でしか見ないので、頻度マスの最適解が割れる。表示側の指標でライブの意思決定をせず、ライブ側の指標で表示値を説明しない。代理指標そのものが未検証であることは `pending.md` 9。
- 評価区間のような外から決まる値をゲーム仕様の定数にしない。曲を指定すれば曲長、指定がなければデータ由来の中央値(`medianSongDurationSeconds`)を使い、UI で変えられるようにする。表示スコアボーナスの T = 200 秒は実機 20 ケースの当てはめで決めた表示モデル専用の値で、ライブ側へ流用しない。
- 名前は実体に合わせ、意味がずれた型・関数・定数を放置しない。順位づけの値は実ライブの期待スコアではないので `adjustedUnitScore` / `scoreModifierFactor` / `songBonus` と呼ぶ。

## 丸めと量子化

- 丸め・整数化の規則もレイヤーごとに分け、片方の規則を他方へ流用しない。スコアボーナス欄は 0.1% 単位の切り上げ(`toScoreBonusPermil`。実機 20 ケースで四捨五入は 15/20、切り上げは 20/20)。総合力・ユニットスコア・パラメータは、それぞれの確定した丸めに従う。浮動小数のずり上がりを防ぐ epsilon は許容するが、実機値へ寄せる補正は入れない。
- 派生する欄の値は、表示済みの丸め値ではなく raw の中間値から計算し、最後に 1 回だけ量子化する。UI へ出す値を次の計算に入れない。表示済みの値から求めると丸めの境界が合わない(黄ボードの増分は、`finishDisplay` の raw から `songBoardRaw` → 量子化の順にして実機 8 点がそろった)。

## 近似の扱い

- 使われなくなった近似モデルは残さず削除する。`legacy` 名で隔離せず消し、必要になったらゼロから作り直す。検証されていない近似がエンジンの名前で残ると、正しいものとして再利用される。削除の前に `rg` で参照(UI・Worker・テスト)を確かめ、報告に file / symbol / 理由を書く。
- 近似を入れるなら、厳密な比較経路も持つ(ADR-005。詳細は [references/search.md](./references/search.md))。未確定の単調性に依存する枝刈りは使わない。仮説の式は差し替えられるよう関数に切り出す。
- 速くするための変更では、近似や評価の順番を変えない。それで推奨が変わったら不具合として扱う(ADR-018)。
- 撤去した次の 2 つは復活させない。
  - 候補を減らすしぼりこみ(「衣装スキル発動に限る / パッシブ全員発動に限る」と `requireCostumeSkill` / `requireAllPassives`)。プールが小さいと条件 1 つで 0 件になった。発動しているかどうかは結果の側で見せる(`breakdown.costumeSkillActive`)。
  - 探索のコネクトのオプション。探索は登録している(ボードで置いた)コネクトで常に計算し、`runOptimize` の `connectPlacements` がそのまま探索・表示に効く。育成の前提にも関わらない。「コネクトを外して探索し、あとで最適な配置を選び直す」近似も撤去した。
- 素値合計が同じメンバーの選び方は「最良」を採る(暫定。実機の規則は未確認 — `pending.md` 16)。総合力のパッシブは効果ごとに加算量の大きいほう(`power.ts` の `passiveParamBonus`。並びに依らない)。表示スコアボーナスのスコアサポートは、同値メンバーの並べ替えを試して最良を採る(`tieOrder.ts` の `bestTieOrder`。`optimize.ts` と `exactSearch.ts` の正確評価で共有し、結果の `members` はその並びで返す)。編成順に依る選び方を評価器へ戻さない。同じ 5 人が並べる順で違う値になり、固定ありの探索とおまかせの探索で食い違うため。上限値(shortlist)は並びに依らない形なので、上限のままでよい。
