# Claude-Md-Convention

CLAUDE.md は、セッション開始時に毎回全文が読み込まれる。そのセッションの作業に関係がなくても 1 行ごとにコストがかかるので、リポジトリを読めば分かることは書かず、読んでも分からない事実だけを最小限の索引として書く。日本語で書き、コード識別子・パス・コマンド・規約名は原文のまま。

## 判定の基準

どの行についても、書くときと、その後に編集するたびに問う。**この行を消したら、Claude は間違えるか。** 間違えないなら消す。この基準から次のことが言える。

- どの作業にも当てはまるものだけを書く。一部の作業でしか使わない行は、ほかのすべての作業で無駄なコストになる。
- 説明し直さず、場所を示す。別の場所に書いてあることは、パス・スキル名・リンクで指す。
- ルールの行は、記録された訂正を昇格させて増やす。候補の大半は別の場所に置くべきものなので、まず次の節の表に当てはめる。

## CLAUDE.md 以外に置くもの

指示を置ける場所は CLAUDE.md のほかにもある。合わない場所に置くと、無視されるか、ファイルが長くなる。書こうとしている行が次の表のどれかに当たるなら、CLAUDE.md には書かず、置くべき場所をユーザーに伝える。表は CLAUDE.md に入れないものを見分けるためのもので、表の置き場に書く作業までは指示していない。スキルや hook は自分の判断で作らない。本人の知らないところで仕組みが増えると、どこに何があるかを誰も把握できなくなるため。

| 内容                                                           | 置き場                                                                                                                                                                                 |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 複数ステップのワークフローや、ときどきしか使わないドメイン知識 | スキル。毎回のセッションではなく、必要なときだけ読み込まれる                                                                                                                           |
| 1 つのディレクトリやファイル種別でだけ要るルール               | そのファイルを扱う作業のスキル。`.claude/rules/` の `paths:` は使わない。Claude がファイルを読んだときに読み込まれる仕組みで、Bash や sed で読み書きする場面では読み込まれる保証がない |
| 毎回、機械的に起きなければならないこと                         | hook または CI チェック。文章で書いても依頼にとどまる                                                                                                                                  |
| 作業中に見つけた落とし穴、ユーザーの訂正                       | journal.md に記録する。CLAUDE.md へ直接追記せず、棚卸しで「作業ルール」などへ昇格する                                                                                                  |

## スケルトン

リポジトリに当てはまらない節は省く。どの節にも合わない内容は、新しい見出しを立てずに、上の表に当てはめる。見出しが増えるほど、同じことを別々の節に書いて矛盾させやすくなる。

````markdown
# <プロジェクト名>

<1〜3 文: このリポジトリが何か、触る前に知っておくべき 1 点。宣伝は書かない>

## ディレクトリ構成

```txt
.
├── <dir>/    # <開く理由>
└── <file>    # <取り上げる理由>
```

<ディレクトリを先、ファイルを後にし、それぞれアルファベット順に並べる。載せるのは、`#` で説明を付ける価値があるものか、作業で触るものだけ。ツリー全体は書かない>

## 技術スタック

| 領域   | 技術   | 備考                                                   |
| ------ | ------ | ------------------------------------------------------ |
| <領域> | <技術> | <自明でない制約: バージョン固定、非推奨、進行中の移行> |

## コードスタイル

<linter / formatter が強制せず、既定と異なる規約だけ。formatter が担うものは書かない>

## テスト

<テストの実行方法、ランナー、推奨する粒度(全体より単体など)、自明でない準備>

## コマンド

```bash
<正確なコマンド>    # <何をするか>
```

## ドキュメントの分担

<内容の種類ごとの置き場の表と、どの種類のコード変更でどのドキュメントを同じコミットで直すか。ドキュメントの種類ごとに担当するスキルがあれば名前を書く。docs/ の配置規約を使っているなら、その共通の行を表に入れる>

## 作業ルール

<どの作業にも当てはまり、リポジトリを読んでも分からないルールを、1 項目ずつ理由を添えて書く。作業の途中で追記せず、記録された訂正から昇格させる>
````
