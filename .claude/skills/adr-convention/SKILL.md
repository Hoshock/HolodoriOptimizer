# Adr-Convention

ADR には、意思決定の理由のうち、将来コードを読むエンジニアが自力では復元できない部分を記録する。ADR を書くかどうかを決めるときも、節を 1 つ残すかどうかを決めるときも、基準は同じで、「コードを読めば分かる内容か」を問う。分かるなら削る。

## 書くべきとき

覆すのが難しい（または覆すコストが高い）決定、モジュールやチームの境界をまたぐ決定、コードを見ただけでは分からない形で今後の作業を制約する決定について書く。具体的には次のとおり。

- 有力な案が複数あるなかから 1 つを選び、他の案を外した理由が結果のコードからは読み取れない。
- スキーマや API の形、採用した依存関係、データ形式、セキュリティ／コンプライアンス上のトレードオフを固定した。
- コードでは表現できない制約を記録する。ステークホルダーの要件、「バグに見えるが意図的に変えずにいる」挙動、設計を方向づけた期限やリソースの制約などである。

次の場合は書かない。

- 検討に値する代替案がない。妥当な選択肢が 1 つしかない場合、日常的なバグ修正、依存関係の更新、議論になるトレードオフのないリファクタリングなどである。
- 局所的で元に戻すコストも低く、レビュアーが差分とテストだけで理由を完全に読み取れる。この場合はコードコメントで足りる。

変更が 1 つの関数に収まっていても、それだけで ADR が不要とは言えない。影響範囲の大小にかかわらず、上の基準で判断する。

## 粒度

1 つの ADR には 1 つの決定を、おおよそ 1 ページで書く。1 ページを超えるときは、複数の決定をまとめて書いているか、設計ドキュメントに書くべき実装の詳細まで書いていることが多い。

2 つの決定を 1 つの ADR にまとめてよいのは、両者が必ず一緒に Superseded になる場合に限る。つまり、トレードオフも根本原因も同じで、片方だけステータスが変わることがあり得ない場合である。（「注文サービスに PostgreSQL を使う」は 1 つの ADR に収まる。「全サービスのデータベース戦略」は ADR ではなく設計ドキュメントに書く。）決定が短期・中期・長期のようにフェーズに分かれて進む場合は、フェーズごとに ADR を分ける。フェーズごとに Accepted / Superseded になる時期が違うからである。

迷ったら分割する。短い ADR を書く手間は小さいが、まとめて書いた ADR を後から分けるのは手間がかかる。

## 命名

- パターンは `NNN-short-kebab-case-title.md`（3 桁のゼロ埋め）とし、既存の最大番号の次の番号を振る（最初は `001`）。`index.md` はこのパターンの対象外とする。
- ADR ディレクトリは glob `docs/**/adr/*.md` で探す。存在しない場合は既定の `docs/adr/` を作成する。

## ステータスと編集

| 遷移元   | 遷移先                         | 条件                             |
| -------- | ------------------------------ | -------------------------------- |
| Proposed | Accepted                       | チームが合意した                 |
| Accepted | `Superseded by [ADR-NNN](NNN-…)` | 新しい決定がこの決定を置き換える |
| Accepted | Deprecated                     | 決定が当てはまらなくなった       |

Accepted になった後は、Decision / Context / Consequences の本文を書き換えない。本文がこのスキルの規約に合わなくなっても、そのままにする。ADR の価値は当時の判断を正確に残すことにあり、最後に編集した人の見解で上書きすると失われるからである。例外は 3 つある。1 つは誤字・リンク切れ・書式の修正。1 つは、決定の中身を変えない翻訳（言語の規約を変えたときの既存 ADR の翻訳など）。もう 1 つは、決定を変えない新しい情報を、日付付きの補足（`**Update (YYYY-MM-DD):** ...`）として節に追記すること。補足は追記だけにして、元の本文は置き換えない。

決定が変わる場合は新しい ADR を書き、古い ADR のステータスを Superseded にする。Superseded / Deprecated の ADR を `docs/adr/` から削除したり編集したりしてはならない。決定の記録はずっと残すものなので、古い ADR は間引かない。探しやすさは `index.md` で保つ。

## インデックス

ADR と同じディレクトリに `docs/adr/index.md` を置き、重要な ADR だけを選んで表にする。

- 今後の作業で参照が必要な ADR や、うっかり破られそうな ADR を載せる。軽微なものや、経緯を残すためだけのものは載せない（全件はディレクトリの一覧で分かる）。
- インデックスに載せるべき ADR を変更するときは、同じコミットでインデックスも更新する。

## 言語

ADR の内容は日本語で書く。ADR を読み書きするのは日本語を使うチームで、英語にすると読み手の負担が増えるわりに得るものがないからである。節見出し（Status / Decision / Context / Consequences / Pros / Cons）とコード・識別子・パスは原語のまま残す。

## スケルトン

ADR:

```markdown
# ADR-NNN: <タイトル>

Date: YYYY-MM-DD

## Status

[Proposed | Accepted | Deprecated | Superseded by [ADR-NNN](NNN-filename.md)]

## Decision

<決定を結論として、何をなぜ選んだかを 1〜2 文で書く。経緯の物語にしない。>

## Context

<なぜ必要だったか: 制約、トレードオフ、真剣に検討して外した案とその理由(話に出ただけの案は省く)、選択を方向づけた自明でない背景(ステークホルダーの要望、障害、期限、プラットフォームの制限)。>

## Consequences

### Pros

- <何が楽になったか、何が可能になったか>

### Cons

- <何が難しくなったか、承知のうえで受け入れたリスク。どの決定にも実際のコストがある>
```

インデックス（`docs/adr/index.md`）:

```markdown
| ADR                        | 概要                 |
| -------------------------- | -------------------- |
| [ADR-NNN](NNN-filename.md) | <何についての決定か> |
```
