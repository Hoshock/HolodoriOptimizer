# 所持メンバー（kind: "owned-members"）

ツールの「持っているカードのみからさがす」で使う登録内容を作る。封筒（`format` / `version` / `kind`）と守ることは [SKILL.md](../SKILL.md)（raw: `https://raw.githubusercontent.com/Hoshock/HolodoriOptimizer/main/.claude/skills/structure-import/SKILL.md`）にある — このファイルだけを読んでいるなら、下の「例」がそのまま完成形の全体である。保存されるのは**どの★5 カードを持っているか**と**その開花段階（凸数）**の 2 つだけで、レベル・P/T/S・スキルはカードデータ側にあるので出力しない（`.claude/rules/storage-compat.md`）。

## 対象

- **★5 のカードだけ**を出す（レア度はタイルの星の数で見分ける）。最適化の対象は★5 のみで、★3・★4 は出さない（カード名・種類数が未確認でもある — `docs/human/game-spec.md`）。
- 1 枚のカードにつき 1 行。ゲーム内で重複入手したぶんは開花段階に反映されるので、行を増やさない。
- **`cards` の並びは画面に写っている順**（1 行 6 枚なので、左上から右へ 6 枚読んだら次の行の左端へ。スクショは渡された順）。名前順・レア度順に並べ替えない — 画面と JSON を上から見比べて検算できるようにするため（2026-09-10 ユーザー指示）。
- ホロメンボード・メモリー・強化ボーナスはこの種別に含めない（別の `kind` として後から追加する）。

## 入力のスクショ（メンバー一覧のカード画面）

ユーザーが撮るのは**ゲームのメンバー一覧（カードが並ぶ画面）**で、1 行あたり 6 枚のタイルが並ぶ。タイル 1 枚から読めるのは次のとおりで、**ホロメン名・カード名は書かれていない**（2026-09-10 ユーザー確認）。

| タイルの場所 | 何が出ているか                                   | この作業での使い方                                                        |
| :----------- | :----------------------------------------------- | :------------------------------------------------------------------------ |
| 中央         | カードのイラスト                                 | **これが本体**。ここからホロメンと衣装を見分け、名前は web 検索で特定する |
| 星の並び     | レア度                                           | **★5 だけを対象にする**（星 5 つ以外は飛ばす）                            |
| 左上         | タイプのアイコン（キュート / ハッピー / ピュア） | 検索でカードを絞る手がかり。出力には入れない                              |
| 右上         | ユニット名                                       | 同じく手がかり。出力には入れない                                          |
| イラスト上   | 開花状況                                         | `bloom`（0〜5）として読む                                                 |
| イラスト上   | レベル                                           | **使わない**（ツールはカードデータ側の値を使う）                          |

- 1 画面に収まらないので**スクロールして複数枚**。重なりがあってよく、重なりは最後に 1 件へまとめる。**途中まででも、写っている範囲で作る** — 足りないぶんはユーザーが追加のスクショを送れるし、取り込みは既存の登録を減らさない。
- ★5 で絞り込める画面なら絞ってから撮ってもらうと選別が楽になる。
- 開花状況が判断できないタイルは `bloom` を `null` にする（推測しない）。

## 読み取りの手順（タイル 1 枚ごと）

1. **星の数を見る。★5 でなければ飛ばす。**
2. イラスト・左上のタイプ・右上のユニット名を手がかりに、**web 検索でホロメン名とカード名を特定する**（ホロドリの★5 カード一覧が載っている攻略サイトなど）。イラストからホロメンを見分けたうえで、そのホロメンの★5 カードを検索で照らし合わせる。
3. **カード名まで確定できたら `card` に入れる。ホロメンまでしか確定できなければ `card` を省略する**（そのホロメンの★5 が 1 枚なら、取り込み側が確認の質問つきで引き受ける）。ホロメンも分からなければ `cards` に入れず `unreadable` へ回す。
4. 開花状況から `bloom` を読む。
5. 検索できない環境なら、**推測で名前を作らない** — 分かるところだけ出し、残りは `unreadable` に理由を書く。

**web 検索の結果とスクショが食い違ったらスクショを優先**（タイプ・星・ユニット名・開花はスクショが実機の事実）。ゲームクライアントの解析・データダンプ由来の一覧は使わない（ADR-002）。

## スキーマ

`cards` は封筒（[SKILL.md](../SKILL.md)）の直下に置く配列。

| フィールド | 必須 | 型                   | 意味                                                                                                                                                                  |
| :--------- | :--- | :------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `card`     | —    | string               | カード名（サブタイトル）。★5 のカード名は全 73 枚で重複しないので、読めれば実質の照合キー。**読めないときは省略する**（★5 が 1 枚のホロメンなら取り込み側が特定する） |
| 並び       | ○    | —                    | 配列の順序そのものが情報: 画面の左上から右下（複数枚は渡された順）。並べ替えない                                                                                      |
| `holomen`  | ○    | string               | ホロメン名。**これだけは必須**。`card` と食い違う行は取り込まず「取り込みエラー」に数えられる                                                                         |
| `bloom`    | ○    | integer 0〜5 \| null | 開花段階（凸数）。0 = 未開花、5 = 最大。読み取れないときは `null`（取り込み側は 0凸 として登録し件数を報告）                                                          |
| `cardId`   | —    | string               | `src/data/cards.json` の `id`（例 `azki-01`）。分かる場合のみ。あれば名前より優先して照合する                                                                         |
| `note`     | —    | string               | 判断に迷った点・読み取りの根拠。人間の確認用で、取り込みでは無視される                                                                                                |

- レベル・パラメータ・スキル文言・所属・タイプは**入れない**（カードデータ側にあり、入れると二重管理になる）。
- 開花段階と「開花Pt の残数」「カードのレベル」を混同しないこと。0〜5 を外れた値は丸めずに取り込まず「要確認」に出る。

## 例

```json
{
  "format": "holodori-optimizer/import",
  "version": 1,
  "kind": "owned-members",
  "capturedAt": "2026-09-10",
  "cards": [
    {
      "card": "咲き誇る一途な花",
      "holomen": "AZKi",
      "bloom": 3
    },
    {
      "card": "サクラBloom",
      "holomen": "さくらみこ",
      "bloom": 0
    },
    {
      "card": "叡智を灯し、アートに導く",
      "holomen": "儒烏風亭らでん",
      "bloom": null,
      "note": "開花アイコンが指で隠れている"
    }
  ],
  "unreadable": [{ "reason": "カード名が途中で切れている", "hint": "4 枚目の右下、白上フブキの★5" }]
}
```

## 照合の指針

- **カード名を第一のキーにする。** ホロメン名だけでは特定できない（19 名は★5 が 2 枚あるので、そのホロメンはカード名がないと取り込めない）。
- 名前は検索で得た**正式表記をそのまま**入れる（「サクラBloom」を「サクラブルーム」にしない）。表記ゆれ（全角と半角、英字の大小、中黒や空白の有無）と 1〜2 文字の違い（漢字の異体・脱字）は取り込み側が吸収するので、整え直すより見つけた表記のまま出す。
- 検索で確定できなければ `card` を省略し、それでも分からなければ `unreadable` へ回す。**推測した名前を入れない**（取り込み側では捏造を見分けられない）。
- 同じカードが複数のスクショに写っていて開花段階の読みが違うときは、**いちばん鮮明な 1 枚**の値を採り、`note` にどちらを採ったか書く。

## 取り込み側（サイト）の扱い

入口はサイドメニュー一番上の「データの取り込み」。実装は `src/storage/import.ts`（解釈とプランの純関数）と `src/components/ImportSheet.vue`（貼る → 差分の確認 → 取り込む の 2 段。取り込むと閉じる）。取り込み画面には**このスキーマを自己完結させたコピー用プロンプト**（`src/ui/importPrompt.ts`。末尾にこのスキルの URL を入れて、読める AI は詳しい仕様まで辿れるようにしている）が載っている — 手元の AI がリポジトリを読めるとは限らないので、**スキーマを変えたらそのプロンプトも直す**。

- 保存先は `holodori-optimizer:owned-card-ids`（v2 の封筒 `{version, cards: [{id, bloom}]}` — `src/storage/owned.ts`）。JSON の名前から `id` への解決はサイト側が `src/data/cards.json` を使って行い（全角半角・大小・空白・中黒の違いは吸収する）、`cardId` があればそれを優先する。
- **カード名がない行**（`card` を省略した行）は、そのホロメンの★5 が 1 枚なら「◯◯ の★5 は「△△」の 1 枚です。これとして取り込みますか？」の質問にして取り込む。2 枚以上あるホロメンは特定できないので取り込まない（件数だけ「取り込みエラー」に出る）。
- **読み取りの少しのブレは吸収する**（2026-09-10 ユーザー判断「少しのブレを許そう」）: 完全一致しないときは、そのホロメンのカードのうちカード名が近いもの（正規化後の編集距離 2 以内、または一方が他方を含む）が**1 つに絞れるときだけ**読み替える。候補が複数なら取り込まない。カード名が一致していればホロメン名の 1 文字違いも許す。読み替えた行は確認画面に「『<データの名前>』として取り込みます」と必ず出す。実例: 探究心 → 探**求**心（漢字 1 文字違い）、愛嬌たっぷり**ビット**フィールド → **ラビット**フィールド（脱字）。
- 取り込まない行（見つからないカード名・`holomen` の食い違い・同じカードの重複・範囲外の開花段階）は、黙って捨てず理由つきで確認画面の先頭に出る。`unreadable` もそこに並ぶ。
- **マージの方針**: JSON にある行は登録し、開花段階は JSON の値で上書きする。**JSON に無いカードの既存の登録は消さない** — スクショが全件そろっている保証がないので、取り込みで登録が減るのは危ない。全消しは明示的な別操作にする（未実装）。
- `bloom: null`（未読取）は、新規なら 0凸で登録し、登録済みなら現在の段階を保つ（推測で上書きしない）。どちらも確認画面に理由が出る。
