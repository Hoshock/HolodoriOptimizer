# 表示ユニットスコアの逆解析

ユニット編成画面に表示される「スコアボーナス」と「ユニットスコア」の現在の知識をまとめる。実測値そのものは [repro/](./repro/)（`display-score-*` の観測資料と `*-account-snapshot` — 読み方は [repro/README.md](./repro/README.md)）、証拠の扱いは [evidence-policy.md](./evidence-policy.md) を正典とする。

`src/engine/displayScore.ts` は現在の試算実装であり、反証済みの近似が残る。コードが存在することをゲーム仕様の証拠にしない。

## 確定・強く支持されること

### ユニットスコアの外側

```txt
unitScore = ceil(totalPower × (1 + scoreBonus / 100) × 2.03734)
```

多数の実機報告で1点単位まで一致する。新しい観測もこの式で cross-check する。ただし式が一致しても、編成・Lv・カードの読み違いまでは検出できない。

### 5カテゴリ

現在の実機では次の5カテゴリを観測できる。

1. 衣装（Costume / Leader）
2. アクティブ（Active）
3. ホロメンボード（Board / SkillTree）
4. パッシブ（Passive）
5. SP（Special）

0のカテゴリは表示上省略されることがある。【外部情報】サーバー応答にも Active / Leader / Passive / SkillTree / Special の独立カテゴリがあるとされる。現在実装の projective 配分（総量 `T` を raw weight `W` で按分）をゲーム内部式とみなさない。

### 黄ボード

同一編成・同一赤状態の「曲なし Y=0」と「Gamers Y=10%」の直接比較では、Boardだけが `40.7 → 64.8`（+24.1）となった。他4カテゴリは `Costume 14.1 / Active 77.7 / Passive 1.9 / SP 47.0` で同じ。

表示値でも、

```txt
0.1 × (100 + 14.1 + 77.7 + 1.9 + 47.0) = 24.07
```

となる。したがって現在の最も強いモデルは、量子化前rawを用いる

```txt
YellowBoardIncrement
= Y × (100 + Costume + Active + Passive + Special)
```

である。Costumeを除く旧4カテゴリ式はこの直接対照に合わない。

実装（`songBoardRaw`）は2026-09-12にこの5カテゴリ式へ更新した。`DisplayScoreBreakdown` も `costume` を含む5カテゴリで、合計は5欄の表示値の和。Costume欄は2026-09-13に「衣装スコアサポートを静的に (1 + X/100) 倍した増分」（実機より3〜17pt大きい既知の近似だった）から下の projective 配分へ置き換えた。

### 表示 5 欄の生成は「総量」と「配分」の 2 レイヤー（2026-09-13 に production へ実装）

`src/engine/displayScore.ts` の `attributeDisplaySupport`。アクティブ欄と SP 欄は独立で、残り 3 欄（衣装 / ボード / パッシブ）を次の 2 段で作る。

**1. 総量 `T`（pre-yellow の 3 欄合計）は source ごとの増分の和。**

```txt
T = Σ_i (衣装支援_i/100) × E_blue の取り分_i    リーダー衣装のスコアサポート
  + (X/100) × E_blue                             赤「全員のスコアサポート効果」
  + (E_blue − アクティブ欄)                      青ボードの純増分
  + (パッシブ込み − E_blue)                      パッシブのスコアサポート（静的）
```

`E_blue` は青の発動頻度で短縮した周期の窓 × 乗算型の発動確率で評価したアクティブ期待値。支援 3 種は加算合成（K6 が乗算を棄却）。

**2. 配分は projective。** 3 欄は source ごとの raw weight `W` に比例する。

```txt
W_C = Σ_i (衣装支援_i/100) × H_C の取り分_i    W_B = W_blue + (X/100) × E_blue    W_P = H_P
(衣装, ボード, パッシブ) = T × (W_C, W_B, W_P) / (W_C + W_B + W_P)
```

`H_C` は **p0Only kernel**（青の窓で、対象自身は基準確率 `p0`、同時候補の競合の分母だけ青の乗算型）、`H_P` はそこへ静的にパッシブ支援を掛けた増分、`W_blue` は**青ボードを実効スコアサポート % に直して `W_C` と同じ形にしたもの**（`(青の実効支援%/100) × H_C`。下の「`W_blue` の決定式」）。`W` は全体を定数倍しても同じ表示になる（gauge 自由）。

3 欄の raw が負になる編成（F2 の支援なし側）は実機も 0 表示なので 0 で切る。

**この式に替えた効果**（旧「タイムライン差分を全部ボード欄へ入れる」近似との比較）:

| 材料                                   | 旧 ボード / パッシブ の最大誤差 |            新 ボード / パッシブ の最大誤差 |
| :------------------------------------- | ------------------------------: | -----------------------------------------: |
| 2026-09-08 の Golden 20 ケース         |                       2.7 / 1.8 |                                  0.5 / 0.2 |
| 青の発動頻度系列 4 点（フブキ水着）    |                       2.1 / 0.1 |                    **0.1 / 0（完全一致）** |
| 赤 +10 の単独差分 3 編成               |                       0.4 / 0.5 | **0.1 / 0.1**（1 編成は 3 欄とも完全一致） |
| 発動頻度 ownership 系列 8 点（F0〜F3） |                               — |                                  0.8 / 0.1 |

衣装欄は旧実装が実機より最大 16.9 pt 大きかった（RMSE 6.6）のに対し、新式は同じ 42 行で RMSE 0.28 / 最大 0.8。

**`W_blue` は 2026-09-13 に「青を実効スコアサポート % に直す」形へ替えた**（下の「`W_blue` の決定式」。**確定ではなく現時点の最有力**）。同じ 51 行 × 3 欄 = 153 列のコーパスで、旧 member-local 型（`H_C` のメンバー取り分に % を掛ける）と比べると

| パッシブ RMSE / 最大 |         0.09 / 0.2 |                0.09 / 0.2 |

### 赤のパラメータ効果と赤スコアサポートは分ける

赤の P/T/S 固定値・割合を変えて総合力が変化しても、スコアカテゴリが変わらなかった対照がある。赤のパラメータ計算を、赤「全員のスコアサポート効果」の表示換算へ混ぜない。

### SP

**確定（2026-09-13）。**

```
SP 欄 = ceil_0.1%( 表示アクティブ欄 × Σ_i (効果時間_i / 120) × (支援_i / 100) × (1 + 発動率 UP_i / 200) )
```

- **SP スキルごとに独立な加法項**。編成の SP 集合を足し合わせた形になる。
- **発動率 UP はアクティブのタイムラインを動かさない。** 同じ SP のスコアサポート項を `1 + X/200` 倍するだけで、**係数はデッキ非依存**。
- **発動率 UP の条件は SP ごとに評価する**（不成立なら倍率 1）。白銀ノエル 0凸 の「3期生が 2 人以上で 40%」は、3期生 1 人の編成では効かない。
- **基準はアクティブ欄の raw ではなく表示値**（0.1% 単位に切り上げた値）。raw を基準にすると 23 編成中 8 編成で 0.1 低くなる。
- 最終の整数化は 5 欄共通の 0.1% 単位の切り上げ（下の「量子化」）。

**確定なのは「アクティブ欄との関係」。** 検証は実機のアクティブ欄を入力にしていて、そこは 23 編成とも実機と一致している。ただし production が SP へ渡すアクティブ欄は下の「Active」モデル（強い推定）が作る値なので、**未検証の編成でアクティブ欄がずれれば SP もそのぶんずれる**。

カードデータに記録のある実機 **23 編成すべてで誤差 0**（B / 9.7〜9.17 / 2026-09-12 の対照 16 行 / K1〜K4 / F0〜F3 / 2026-09-13 の 40% 観測 / K5・K6・K7）。分母の同定:

- `200` は 20〜800 の総当たりで唯一解。連続値でも許容区間は `199.53〜200.16`（幅 0.3%）しかなく、その中の丸い値は 200 だけ。発動率 UP の値が `35 / 40 / 50 / 55%` の 4 通りあり、同じ 1 つの分母を指している — 「一番よく合う値を探した自由係数」ではない。
- `120` も連続値で `119.98〜120.01` しか通らない。
- 発動率 UP をスコアサポート % に**掛けない**加法型 `+ (効果時間/120) × (X/D)` は、どの `D` でも 23 編成を通らない。

**棄却したもの**

- `効果時間 / 100 × 発動確率を +X した基準タイムラインの再評価差分`（2026-09-13 まで production が使っていた形）。同じ発動率 UP 50% でもデッキによって差分が 1.2 倍変わり、実機が要求する「1 スキルあたりの寄与がデッキ非依存」を満たさない。F0〜F3 では実機 42.8 に対して 41.2 と全 8 点で −1.6 の共通残差が出ていた。
- 一時的に置いていた fit 係数 `β35 ≈ 0.0907 / β50 ≈ 0.1387`（`(効果時間/120) × (1 + 支援/100) × β` 型）。6 編成の区間は満たすが、23 編成へ広げるとどの `β` でも通らない。

**K5 / K6 / K7 は 2026-09-15 に corpus へ入った。** それまでは SP のスコアサポート % が実機未確認で、SP 欄だけ 3.8〜4.2 高く出ていた（アクティブ欄は一致していたので、ずれているのは式ではなく入力だと分かっていた）。**同日に恒常 0凸 の全区間を実機で確認したところ、3 編成とも誤差 0 になった** — 「必要な係数は試算値の 0.89〜0.92 倍」という当時の逆算は、流用値に依存した見かけの数字で、式には何も足りていなかった。

残る exploratory 行（恒常みこ 0凸、Lv 約 20）だけは**アクティブ欄そのものが実機と合わない**ので corpus に入れない。こちらも実機値で 3.5 → 0.5 まで縮んだが、Lv・スキル Lv の再読までは fit に入れない。

観測: [repro/display-score-20260908-11.md](./repro/display-score-20260908-11.md)、[repro/display-score-20260912.md](./repro/display-score-20260912.md)、[repro/display-score-20260913-frequency.md](./repro/display-score-20260913-frequency.md)、[repro/display-score-20260913-sp.md](./repro/display-score-20260913-sp.md)。

## 強い推定

### Active

200秒の共通仮想タイムラインを使う現在モデルが既存Goldenに非常によく一致する。

- 発動候補: `k × interval <= s < k × interval + duration`、`k >= 1`
- 基礎発動確率: 高55% / 中46% / 低37%【外部情報を含む】
- 同時候補時は確率和で正規化する現在モデル
- Activeの0.1%単位化は切り上げで既存観測と一致

発動確率の実数値自体はゲーム内表示から直接確認できない。

**青ボードの反映は 発動率 = 乗算型 / 発動頻度 = 周期の短縮**（2026-09-13 に production も乗算型へ変更）。

- 発動率: `p = min(1, p0 × (1 + r/100))`。支援の総増分 `支援/100 × E_blue` が 13 対照 + Leader-only matched pair 7 組 + F0〜F3 で量子化の範囲に収まる。加算型 `min(1, p0 + r/100)` は同じ材料で 2〜4 pt 外れる。
- 発動頻度: `interval ÷ (1 + f/100)`。**以前「実機のボード欄 4.6 → 4.7 → 4.4 → 5.0 が単調でないので再現できない」と書いたのは誤りで、撤回する。** 差分配賦をやめて projective 配分にすると同じ式が 4.5 → 4.6 → 4.3 → 4.9 を返し、4 点とも表示 0.1 以内・パッシブ欄は完全一致する。非単調性は同時候補の正規化 `max(1, Σp)` から出る（周期が短くなると低スコアのメンバーが候補に増えて平均が下がる秒がある）。2026-09-13 の発動頻度 ownership 系列（[repro/display-score-20260913-frequency.md](./repro/display-score-20260913-frequency.md)）では、この効果で支援なし側の raw が負になり実機の 0 / 0 表示と一致する。

**K5 / K6 の不一致は入力誤りだった（2026-09-13）**: 恒常そら / アキ / スバル / フレア / ぼたん 0凸を含む K5 / K6 で評価器が 67.9 → 59.6（K6 71.4）と実機 63.3 / 73.7 を外していたのは、0凸アクティブの入力（仮定倍率、次いで抽出マスターの level 1 を 0凸に当てたもの）が誤っていたため。カード詳細画面で再確認した実機値（そら 100、ぼたん 60→125。[card-data-provenance.md](./card-data-provenance.md)）に直すと、式を変えずに raw 63.24 / 73.69 → 表示 63.3 / 73.7 で一致する（`displayScore.test.ts`「K5 / K6 のアクティブ欄」）。**そら / ぼたん の 0凸 Active はその後 2026-09-15 に「未確認」へ取り下げたが、取り下げ前の値は最大側レコードと同値だったので入力も一致も変わらない。**ライフ・コンボ・タイプ人数の条件つきアクティブを production どおり扱って一致したので、K5 / K6 を根拠にした「条件つきアクティブの表示評価方式が未解明」という主張は撤回する。

### パッシブのスコアサポートは静的

対象メンバーに常に `S_ji` を掛ける（供給側 `j` の発動確率で割り引かない）。**供給側の確率で重みづけする gated 型は棄却した**: 青なし・パッシブ支援ありの negative control K6（恒常マリン 1凸「3期生が2人以上で3期生2人のスコアサポート効果 9%」が フレア との 2 人で成立）で gated 型は 1.0 を返し、実機 2.9 に 1.9 足りない。静的型は 2.85 を返す。Golden 9.8〜9.11 のパッシブ欄も 1.7〜2.1（不足 0.7〜1.8）から 2.6〜3.5（誤差 0.2 以内）になった。

総合力側のパッシブ（`power.ts` の `passiveParamBonus`）とは別のレイヤーなので、片方の規則を他方へ流用しない。

## 赤「全員のスコアサポート効果」

### 観測から安全に言えること

- 表示への効きは編成依存。赤+24の報告差は現在 `+16.4〜+20.9pt` まで広がっている。
- 赤+24の曲比較ではActive / SPが変わらず、Boardを中心にCostume / Passiveも動く例がある。
- R-061（+3）だけを開いた対照ではPower不変、Bonus `178.7 → 181.4`（+2.7）。
- 同じ白上フブキのホロメンボード状態でも、水着フブキ0凸と恒常フブキ1凸で赤+24の差が異なる報告がある。これは「青ボード量だけ」では説明できないが、カード変更に伴いActive / Passive等も同時に変わるため原因は特定できない。
- 水着ミオ + 恒常マリンでは、青補正なし候補秒149/200に対して赤+24の実測差が+20.9で、旧候補秒率式の17.88を大きく外す。

### 棄却済み

一般式として使わない。

- `固定係数 × X`（0.88、0.85等）
- `X × 基準候補秒 / 200`
- `X × 表示Active / 90`
- Costume表示値だけで決める単純倍率
- 青込み候補秒・発動確率込み占有率だけで決める単純式

`X × 基準候補秒 / 200` は2026-09-11〜12にproductionが採用していた式（`redScoreSupportDisplayGain`）だが、追加実測で一般式として反証され、**2026-09-13に実装ごと削除した**。現在のproductionは総量 `(X/100) × E_blue` + projective 配分（上の「表示 5 欄の生成」）。実装を根拠にGoldenや正典を書き換えない。

### 現在最有力の一般則候補（強い推定。確定ではない）

```txt
ΔRed(X) = X / 100 × E_blue
```

`E_blue` は production のアクティブ欄と同じ評価器（200秒の共通仮想タイムライン、条件解決済みスコアUP、同時候補は確率和 `Σ up × p / max(1, Σ p)` で正規化）に、青ボードを次のように入れたアクティブ期待値。

- 発動確率: `p_i = min(1, p0_i × (1 + 発動率UP_i / 100))`（**乗算型**）
- 発動周期: `interval_i / (1 + 発動頻度UP_i / 100)`
- 候補窓: `k × interval_i' <= s < k × interval_i' + duration_i`（`k >= 1`、200秒）

実機13対照（[repro](./repro/display-score-20260912.md) の赤+24 × 9、R-061 +3、旧R-002 +10 × 3）に対する raw 予測は RMSE ≈ 0.09 pt、最大絶対誤差 ≈ 0.13 pt（2026-09-12、各対照はその観測時点の青実効値を使用）。旧候補秒率式は同じ13対照で RMSE ≈ 1.0 pt（+24の9件だけなら ≈ 1.2 pt、水着ミオ+恒常マリンで 3 pt 外す）で、大幅に改善する。発動率UPを加算型 `p0 + r` にすると RMSE ≈ 0.85 pt になり、乗算型が明確に良い。

解析コードは `src/engine/displayScoreExperimental.ts`、回帰評価は `displayScoreExperimental.test.ts`（仕様のGoldenではなく仮説の回帰ガード: RMSE < 0.15 / 最大 0.25）。

**この節を書いた2026-09-12時点では production に採用しなかった**（総増分は説明できても、増分が Costume / Board / Passive へ分かれる配賦式が未解明だったため）。2026-09-13 に配賦のほうが projective 構造として決まったので、総量 `(X/100) × E_blue` も乗算型の青も production へ入っている（上の「表示 5 欄の生成」）。ただし青の一般仕様として `p0 × (1 + r)` が確定したわけではなく、raw の server permil も未取得。

### 逐次 marginal 型の配賦は全順序で反証（2026-09-12。projective 配分に置き換わった経緯）

総増分 `X/100 × E_blue` を、production と同じ評価器 F の上で「スキルツリー赤（S）・リーダー衣装（L）・パッシブ支援（P）」の 3 供給源を順に足したときの限界寄与として配賦する仮説を、2026-09-12 に 6 順序 × 供給側確率 2 種（`p0` / 青乗算型）× 量子化 2 種（round / ceil）の 24 組で評価した（`src/engine/displayScoreAttributionExperimental.ts` / `.test.ts`、production 未採用）。コーパスは赤だけを変えた直接比較 15 行（水着フワワリーダー +24 × 9、R-061 +3、衣装なし R-002 +10 × 3、水着ミオリーダー +24 の黄 0 / 10%）で、各行に赤変更前後の 5 欄の絶対値を持つ。黄の交差項は raw 5 欄 → `songBoardRaw` → 量子化の順で分離し、量子化は全ケース同一とした。

**結果: どの組も 衣装 ΔC ≤ 0.25 / パッシブ ΔP ≤ 0.25 / ボード ΔB ≤ 0.5 pt を同時に満たさない。**

| 順序（先 → 後）                 | ΔC RMSE / 最大   | ΔP RMSE / 最大   | ΔB RMSE / 最大   | 主な破綻                                                                                           |
| :------------------------------ | :--------------- | :--------------- | :--------------- | :------------------------------------------------------------------------------------------------- |
| S → P → L, S → L → P            | 3.65〜3.70 / 5.3 | 0.19〜0.31 / 0.5 | 0.73〜0.75 / 1.2 | 衣装欄が赤で ×(1+X/100) され、+24 で ΔC ≈ +5.2（実機 −0.1〜+0.5）                                  |

**衣装欄は一様倍率ではない（構造的な下限による棄却）。** 衣装スキル「ピュア 2 人以上で全員のスコアサポート 25%」を、どの配賦法であれ全員のスコアに掛かる一様な ×1.25 として表すなら、衣装欄の値はどの順序でも `0.25 × E_base`（青・赤なしのアクティブ期待値。L を先頭に取った限界寄与がちょうどこの値）以上になる。水着フワワリーダー 9 編成でこの下限は 17.7〜19.9 pt だが、実機の衣装欄は 13.4〜17.4 pt で全編成が下限を下回る（比 0.72〜0.97）。したがって衣装欄の算出は「一様倍率 × 何らかの配賦」の形ではなく、配賦順序を変えても救えない。また衣装欄は同じ X でもメンバーで大きく変わり（水着ミオ1 + 水着ころね2 で 14.1、水着ミオ1 + 恒常マリン1 で 17.4）、X 26 → 50 で −0.1 になった編成もある。22 個の衣装欄観測に対する単一特徴量の探索では、どの候補も編成間の差を 22% 以内に収められなかった。

### 現在は原因仮説を固定しない

以前は「水着フブキ0凸を含むケースだけ低い」ことから、水着フブキのパッシブ・スコアサポートとの相互作用を本命仮説としていた。しかしカード仕様の参照ミスが発生し、さらに水着みこ→恒常みこへ変更した新観測では、同時にActive / Passive / SP / Costume成立など複数条件が変化して赤+24差が+16.4まで下がった。

このため、**水着フブキのパッシブを原因とする仮説は正典から撤回する**。数値相関は観測として残すが、対照実験が成立するまで特定カード・特定スキルを原因扱いしない。

次の実験は、カードID・開花・Lv・リーダー/メンバー役割・衣装条件・各スキルprovenanceを事前に監査し、変更要因を1つに近づけられるものだけ採用する。

2026-09-13 の K7 は、この撤回を独立に裏づけた。水着フブキ 0凸 の Active / Passive / 青がすべて実機で確定した編成でも配賦モデルの残差は消えないので、**「水着フブキ 0凸 の入力・スキルが原因」という筋は使えない**（下の「source 分離型の projective weight」）。

### 支援 3 種の合成と総量（2026-09-13、K6 と赤 / 衣装コーパス 11 行）

`src/engine/displayScoreSourceAttributionExperimental.ts` / `.test.ts`（production 未採用）で、秒 × 発動候補単位に source（青の頻度 Q / 発動率 R / パッシブ支援 P / リーダー衣装 L / 赤 X）を持たせて総量と配賦を調べた。

- **支援は加算合成（強い推定）。** 候補 i の値を `up_i × p_i × (1 + L + X + P_i) / max(1, Σp)` とすると、K6 の総増分 44.3 は 0.6 × 73.7 = 44.2、K1〜K4 は既存どおり `S × E_blue(乗算)`（RMSE 0.11）。乗算合成 `(1 + L)(1 + X)(1 + P_i)` は K6 で +1.7、水着フワワリーダー 10 行（支援 48〜75%）で +5〜+13 過大で棄却。

### 共通 normalization（機構の候補。ゲーム仕様とは断定しない）

非 native 2 欄の比が保存されるのは、カテゴリごとの独立な raw weight `W` と 3 欄に共通の normalization `λ` があって

```txt
C = λ W_C   B = λ W_B   P = λ W_P
```

と書ける場合と整合する。1 つの source が自分の `W` だけを変えるなら残り 2 欄の比はそのままで、両方が `λ' / λ` 倍になる（`commonNormalization` で 3 通りの native とも代数的に確認済み）。`λ` は「3 欄の合計 = 総量」から決まるので自由係数ではない。アクティブ欄・SP 欄はこの normalization の対象に入れない（どの matched pair でも動かない）。黄の楽曲スコアボーナスは既知の後段のボード加算なので混ぜない。

**この構造は 1 組の matched pair からは共通 scale と同値**で、それ以上の検証には `W` の式が要る。以下は未解決。

**衣装候補族を「最終的な衣装欄」ではなく raw weight `W_C` として入れ直す（oracle-baseline stage）。** 支援なし側の表示値をそのまま raw weight にする（`W_C = 0` / `W_B` = 実測ボード / `W_P` = 実測パッシブ。このとき baseline の λ は 1）。target は baseline 合計 + 確定扱いの総増分 `S/100 × E_blue(乗算)`。**baseline を実測で与えているので完全予測ではない。**

oracle が要求する `ΔW_C` は K1 18.10 / K2 32.73 / K3 18.56 / K4 18.75、青のない K6 は 44.30（= 総増分そのもの）。青があると総増分の 0.35〜0.63 倍に縮む。既存の衣装候補族 436 個（`ups × タイムライン × 確率 × 効き方 × 正規化 × 候補人数` の格子 + C\* / p0Only / S×E_base / S×E_blue）を入れ直しても、最良は `unconditional | 青の窓 | p0 | multiplier | 候補人数で割る` の **3 欄 RMSE 2.42 / 最大 3.96** で、成功条件の 0.2 に届く候補は 1 つもない。「最終的な衣装欄」として最良だった C\*（6.20）/ p0Only（6.11）は raw weight に読み替えても改善しない。

したがって **projective な不変量（非 native 2 欄の比の保存）は支持されるが、raw weight の式は未解明**。これが次の課題。

**パッシブ欄の分割との接続。** 支援なし側で「青の純増分」と「静的パッシブ」を raw weight 候補に取ると、和は λ = 1 と整合する（`(B0 + P0) / (青の純増分 + 静的パッシブ)` = K1 1.012 / K2 1.001 / K3 1.028 / K4 1.004 / K6 1.017）。しかし欄ごとの λ は一致しない（ボード由来 1.17 / 1.00 / 1.08 / 1.23、パッシブ由来 0.40 / 0.61 / 0.46、K6 1.02）。同じ組で 1.8〜2.9 倍ずれるので、**この 2 つは `W_B` / `W_P` としては棄却**され、和だけが合う。青のない K6 だけ両方 1 に寄る。非 native 共通 scale の規則は支援なし側の表示値を gauge にするだけで `W` の中身を仮定しないので、ここに矛盾はない。

**赤側の raw weight（参考）。** native = ボード なので `ΔW_B` を足して同じ λ で normalize する形になる。oracle が要求する `ΔW_B` は、λ を 0.1 刻みの衣装欄から逆算するため区間でしか決まらない（例: R-061 は 1.60〜3.00）。最も近い単一候補 `ΔX/100 × E_base` は 10 行中 7 行で区間の中だが 3 行で外れるので式ではない。黄ありの行は後段のボード加算を含むため、黄なしの R-061（曲なし）を別に見ている。リーダー側で `W` の式が決まっていないので、ここは本命ではない。

### source 分離型の projective weight（2026-09-13。**構造は実質確定**。未知数は `W_blue` だけ）

`src/engine/displayScoreProjectiveWeightExperimental.ts` / `.test.ts`（production 未採用）。上の共通 normalization を、source ごとに分離した重みとして具体化する。

```txt
(C, B, P) = T × (W_C, W_B, W_P) / (W_C + W_B + W_P)
W_C = (L/100) × H_C      リーダー衣装のスコアサポート L%
W_B = W_blue + (X/100) × H_B   青ボード由来 + 赤スコアサポート X%
W_P = H_P                パッシブのスコアサポート
```

`T` は pre-yellow の 3 欄合計（既存の「青は乗算型・パッシブは静的・支援は加算合成」）。黄の楽曲スコアボーナスは既知の後段のボード加算なので normalization に混ぜず、pre-yellow を出したあとで戻す。

### 9. `W_blue` の決定式（2026-09-13。**現時点の最有力 production model。確定ではない**）

材料は [repro/display-score-20260913-blue-weight.md](./repro/display-score-20260913-blue-weight.md) の 9 状態。F0〜F3 と**同じ 5 人・同じリーダー（典獄クロニー 60%）・曲なし・赤 0・黄 0** のまま、青のマスを 1 つずつだけ開閉した系列で、**発動率だけを 3pt 動かす組 3 つ・発動頻度だけを 4pt 動かす組 2 つ・ΣR も ΣF も変えずに所有者だけを移す組 2 つ**が同時に取れる。F0〜F3 と合わせて**同一編成 13 状態**、K1〜K7 を足して **20 状態**で評価する。

```txt
W_blue = (青の実効スコアサポート% / 100) × H_C

青の実効支援% = Σ_i 単独寄与_i × 発動率 UP_i / Σ_i 単独寄与_i
              + Σ_i 単独寄与_i × 発動頻度 UP_i / アクティブ欄 raw
単独寄与_i     = スコア UP_i × p0_i × 発動候補秒_i / T   （同時候補の正規化を入れない、メンバー単独の基準寄与）
```

実装は `displayScore.ts` の `blueSupportPercentOf`。**リーダー衣装の `W_C = (L/100) × H_C` と同じ形**で、青は「メンバーの発動率 / 発動頻度 % を、そのメンバーの単独寄与で重みづけした加重平均」というスコアサポート % として配分に効く、という読み方。

#### 要求区間の作り方（量子化規則を未確定のまま扱う）

実測が要求するのは `W_blue / H_C = (L/100) × ボード欄 / 衣装欄` だが、**表示 0.1 刻みから raw へ戻すときに量子化規則の仮定が入る**。3 欄の規則は未確定（下の「量子化」）なので、**切り上げと四捨五入を分けて評価する**。

| 仮定     | 表示 `d` の raw      | 例: 衣装 34.8 / ボード 16.1（S1）の要求区間 |
| :------- | :------------------- | :------------------------------------------ |
| 切り上げ | `(d − 0.1, d]`       | 0.2759〜0.2784                              |
| 四捨五入 | `[d − 0.05, d+0.05)` | 0.2763〜0.2788                              |

**対称な `± 0.05` は四捨五入を仮定したもの**で、production が採っている切り上げとは別物。2026-09-13 の最初の評価は対称区間だけで行っていた（`displayScoreBlueWeight.test.ts` で両方を持つように直した）。

#### 候補の比較（20 状態。inside = 区間に入った数 / 最大逸脱 = 外れたぶんの最大）

| 候補                                                     | 切り上げ inside / 逸脱 | 四捨五入 inside / 逸脱 |
| :------------------------------------------------------- | ---------------------: | ---------------------: |
| **採用（上の式）**                                       |   **12 / 20 · 0.0026** |   **10 / 20 · 0.0029** |
| 分母をそろえる（両方 `Σ 単独寄与`）                      |         3 / 20 · 0.011 |         2 / 20 · 0.011 |
| 分母をそろえる（両方 アクティブ欄 raw）                  |         2 / 20 · 0.072 |         2 / 20 · 0.072 |
| 条件つきスコア UP を解決しない（基準値で重みを作る）     |         2 / 20 · 0.022 |         2 / 20 · 0.022 |

**どちらの量子化仮定でも順位は変わらず、採用式が inside で 4 倍・最大逸脱で 4 倍以上良い。** ただし**採用式でも 20 状態中 8 状態は切り上げ区間の外**（S1 / S2 / S3 / S3' / F16 / RmF / K1 / K4。うち 6 つは今回の 9 状態）で、逸脱はほとんどが 0.0001〜0.0006、最大は K1 の 0.0026。青なしの K5 / K6 は `W_blue = 0` の negative control として厳密に通る。

#### この系列が支持すること

1. **青の % が直接効き、タイムライン経由ではない。** 発動頻度 +4% はこの編成では発動候補秒を 1 秒も増やさない（周期 27 秒 → 25.96 秒でも 200 秒に入る窓は 7 個のまま）のに、実機の配分は 4% のマス 1 つで一定量だけ動く。青の窓・青の確率から作った量（`E_blue − E_base` 型、候補秒の増加率型）はこの一定量を作れない。
2. **メンバーの重みは青の状態に依存しない。** 単独寄与は基準タイムラインだけで決まるので、同じ 5 人なら 13 状態で完全に同じ値になる。旧 member-local 型が使っていた `H_C` のメンバー取り分は青で動くので、ここが違う。
3. **ただし所有者には依存する。** `単独寄与_A ≠ 単独寄与_B` なら同じ % を A から B へ移すと値は変わる（F0 → F3 でモデルは 0.2200 → 0.2219）。**F0〜F3 で実測の要求区間がほぼ重なるのは「所有者に依存しない」ことの証拠ではなく、この編成ではメンバー間の重みの差が量子化の区間幅（約 0.002）より小さいという観測**。2026-09-13 に「所有者に依存しない」と書いたのは実装と矛盾する表現で、撤回する。

#### 分母は「自然量の中では明確に優位」だが一意ではない

自由係数なしで作れる正規化量 7 つ（`Σ 単独寄与` / `Σ 単独寄与(青の窓)` / アクティブ欄 raw / 表示アクティブ欄 / `H_C` / `E_blue(乗算)` / `E_blue(加算)`）で総当たりした結果（切り上げ仮定）:

| 側                                             | 最良                            | 次点                                             |
| :--------------------------------------------- | :------------------------------ | :----------------------------------------------- |
| 発動率側（発動頻度側は アクティブ欄 raw 固定） | `Σ 単独寄与` 12/20 · 0.0026     | `E_blue(加算)` 2/20 · 0.057（**20 倍以上悪い**） |
| 発動頻度側（発動率側は `Σ 単独寄与` 固定）     | アクティブ欄 raw 12/20 · 0.0026 | `H_C` 3/20 · 0.0064（**2.5 倍悪い**）            |

- **発動率側の `Σ 単独寄与` は決定的**（次点と 20 倍以上の差）。これで割ると「% の加重平均」になるので意味も通る。
- **発動頻度側の アクティブ欄 raw は「明確に優位」止まり。** `表示アクティブ欄`（0.1% 切り上げ）とは逸脱が 0.0001 も違わず**分離できない**。`H_C` も 2.5 倍悪いだけで、桁違いに棄却されているわけではない。
- **なぜ発動頻度側だけ「競合込みの合計」で割るのかは導けていない。** 2 つの分母の比はこの編成で `89.12 / 70.78 = 1.259` で、発動頻度 1pt が発動率 1pt の約 1.26 倍効くことになる。**経験的な同定**として扱う。

#### 分母の総当たり（49 組）と盤面再構成への頑健性

上の片側固定（発動率側を測るとき発動頻度側を固定、逆も同じ）だけだと、`D_R` と `D_F` の間の誤差補償を見逃す。自然量 7 種を **発動率分母 × 発動頻度分母 の 49 組**で総当たりした結果（20 状態）:

| 順位 | 発動率分母   | 発動頻度分母     | 切り上げ inside / 逸脱 |
| ---: | :----------- | :--------------- | ---------------------: |
|    1 | `Σ 単独寄与` | アクティブ欄 raw |   **12 / 20 · 0.0026** |
|    2 | `Σ 単独寄与` | 表示アクティブ欄 |       12 / 20 · 0.0026 |
|    3 | `Σ 単独寄与` | `H_C`            |        3 / 20 · 0.0064 |

## 量子化（0.1% 単位）

サーバー応答はカテゴリごとに permil の整数を返す【外部情報】。**アクティブ欄と SP 欄は 0.1% 単位の切り上げで確定**（実機 20 ケースで四捨五入 15/20 に対し切り上げ 20/20）。

**衣装欄は「アクティブ欄との差」として量子化される** — `ceil_0.1(A + C) − ceil_0.1(A)`。欄ごとに独立に丸める現行 production の規則は棄却済み。ボード欄とパッシブ欄の位相は分かれていない（下の 2026-09-15）。

### 欄ごとに独立に丸める形が落ちる理由（モデル非依存。2026-09-15）

K5 / K6 はどちらも 青 0・赤 0・黄 0・パッシブ以外の source なしで、production の `attributeDisplaySupport` は **衣装欄 raw = 0.60 × アクティブ欄 raw** をそのまま返す（K6 はパッシブ支援があるが `W_P = ΔP` で projective 配分が約分される）。この形が正しいなら**実機のアクティブ欄の表示値だけから衣装欄の表示値が決まる** — モデルの raw は要らない。

| 材料                        | K5                            | K6                                      |
| :-------------------------- | :---------------------------- | :-------------------------------------- |
| 実機 アクティブ欄           | 63.3                          | 73.7                                    |
| 切り上げ前提の raw 区間 `A` | `(63.2, 63.3]`                | `(73.6, 73.7]`                          |
| `0.60 × A`                  | `(37.92, 37.98]`              | `(44.16, 44.22]`                        |
| 実機 衣装欄                 | **37.9**（切り上げなら 38.0） | **44.3**（四捨五入・切り捨てなら 44.2） |

**アクティブ欄 3 通り × 衣装欄 3 通りの 9 通りすべてで K5 と K6 は両立しない**（`displayScoreQuantization.test.ts`「{K5, K6} が落とす仮説(モデル非依存)」）。切り上げを仮定すると K5 は `衣装/アクティブ < 0.59968` を、K6 は `> 0.59973` を要求する。したがって「raw の残差が 0.1% を切れば量子化規則が決まる」という 2026-09-13 の見立ては誤りで、取り下げた。落ちているのは丸めの選び方ではなく、**欄ごとに独立に丸めるという位相そのもの**。

対して `ceil(A + C) − ceil(A)` は自由係数なしで K5 と K6 を同時に満たし、現在のモデルの raw（63.235 / 73.693）は両方の要求区間に入る。2026-09-15 の 16 編成でも、残る位相はすべてこの差分型（下）。

**コーパス 153 列は位相の判別に使えない。** 切り上げ 59 列 / 四捨五入 57 列 / 切り捨て 49 列で、衣装欄はどの位相でも最良 27/51 にしかならない（`displayScoreQuantization.test.ts`）。この 51 行は青・赤入りで **raw 自体がまだ合っていない**ので、差がつくのは位相ではなく raw の残差のほう。青 0・赤 0 の 16 編成のほうが強い。

### 2026-09-15: 位相・総量・`W_C` が決まり、残りは配分の重み 1 箇所

青 0・赤 0・黄 0・曲なしで 16 編成（リーダー 典獄クロニー 60%）、うち 3 編成は 恒常ぺこら（25%）でも、
6 編成は 恒常みこ 0凸（支援 0）でも読んだ（[repro/display-score-20260915-costume.md](./repro/display-score-20260915-costume.md)）。

**確定（`A` の量子化ぶれを許しても残る）**:

- アクティブ欄 16/16、みこ側のパッシブ欄 6/6、SP 欄・合計・ユニットスコアが一致。
  したがって**総量 `T = 0.60 × A + ΔP` と対象選抜は正しい**。
- **衣装欄はアクティブ欄との差として量子化される**（`ceil(A + C) − ceil(A)`）。
  欄ごとの規則と累積順序を総当たりして残るのは差分型だけで、**現行の「独立に切り上げ」は棄却**。
  パッシブ欄が 独立-切り上げ か 差分か は分かれない。
- **`W_C` はリーダーのスコアサポート % に比例する**。メンバーを動かさず 60% → 25% にしたとき、
  60% で測った重みの割合 `f` がそのまま通る（予測を先に出しての out-of-sample 一致。3/3）。

したがって表示の重みは `W = Σ (支援% / 100) × w_i` で、**残る不定性はメンバーごとの `w_i` の形だけ**。

**`w_i` は production の「競合で正規化した取り分」ではない** — 12 編成中 9 で外れる。一様でもない。
自由係数なしの候補の一致数は 取り分 3 / 発動確率 4 / 一様 4 / スコアUP% 3 / `up × p0` 2。

6 枚プール（ロボ子 / ポルカ / リス / 奏 / スバル / アーニャ から 5 人を選ぶ 6 編成）に限れば、
カードごとに固定の重みが**過剰決定で成立**する。そこで効くのが **リス と スバル**（どちらも周期 34 秒）で、
取り分は 0.87 / 0.84 と平均を大きく下回るのに、実機は ≥ 1.02 / ≥ 0.98 を要求する。
**表示の重みはタイムライン上の寄与よりずっと平ら。**

> **訂正（2026-09-15）**: 「位相は 1 通りに決まる」「S2 → S3 で実機とモデルの向きが逆」と書いたのは、
> モデルの `A` を厳密とみなした計算だった。`A` は表示値を 16/16 で再現するが、表示が 0.1% 切り上げなので
> `A` 自体に 1 quantum のぶれが残り、それは `f` の区間幅と同じ桁。ぶれを入れると位相は 6 通りに増え

## 実験・実装時のルール

- Golden観測値をモデルに合わせない。
- 実機報告は最優先だが、単発報告を無誤謬と扱わない。`reported / rechecked / cross-checked` を分ける。
- 1ケースだけに合う定数を一般化しない。
- 同時に複数要因が変わった比較から単独因果を主張しない。
- カード事実はID・開花・role・provenanceを確認してから使う。
- モデル変更前に既存コーパスで反証を探す。
- 実ライブのスコア式と表示ユニットスコアを混同しない。
