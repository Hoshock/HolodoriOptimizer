# カードデータの provenance

カード値を使う前に [evidence-policy.md](./evidence-policy.md) と併せて読む。

## どのファイルが何か

- `src/data/cards.json`: 取り込み元のカードレコード。トップレベルの `stats` / 4スキルは最大開花側として扱う。初期の多くは公開データ転記で、全件実機確認ではない。
- `src/data/cardCorrections.ts`: 後日、実機で誤りが確認されたレコードへ適用する補正。`src/data/index.ts` がexportする `cards` / `cardById` がランタイム正典。
- `src/data/bloomEvidence.ts`: `bloomVariants` の値・文言が何由来かを分類する。
- `cardAtBloomWithProvenance()`: 指定開花へ解決したカードと、各フィールドの出所を同時に返す。

## provenance の読み方

| source                             | 意味                                                                                                                                                                            |
| :--------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `max-record`                       | 最大開花側として扱う取り込みレコード。実機確認済みとは限らない                                                                                                                  |
| `observed-variant`                 | そのvariantのゲーム内文言を実機情報として記録                                                                                                                                   |
| `reconstructed-observation`        | 数値・効果は実機確認したが、raw文は最大側文言を基に再構成                                                                                                                       |
| `extracted-master-variant`         | 外部で抽出されたマスターデータ由来のvariant。実機目視ではない（権威順位は「外部解析」）。出所は `bloomEvidence.ts` の `master`（repo / commit / ファイル / マスター側カードID） |
| `recorded-variant-unclassified`    | variantはあるが出典分類が未棚卸し。通常はテストで禁止                                                                                                                           |
| `derived-from-max-confirmed-ratio` | 2凸+10%という確認済み規則から最大値を逆算。ただし整数丸め不確実性あり                                                                                                           |
| `unknown`                          | その段階の記録がない。文言は「未確認」と表示し、計算には最近傍の凸（強化後の最大側レコード）の内容をそのまま流用する                                                            |

## 棚卸し状態

- 既存の `bloomVariants` は全件 `bloomEvidence.ts` で分類済み。`recorded-variant-unclassified` が1件でも実データに残れば `bloomEvidence.test.ts` が失敗する。
- 0凸variantを1凸Active、3凸SP、4凸Passiveの強化境界後まで誤って持ち越す旧 `variantAt()` 挙動は修正済み。強化境界のテストを追加した。
- `cardAtBloomWithProvenance()` は、最大レコードそのもの・確認済みvariant・再構成観測・抽出マスターvariant・未確認を区別して返す。
- 抽出マスターのスキル level 番号と画面の凸段階の対応はカード共通ではない（下の「低開花値の確定」）。実機 variant を最優先し、level 番号だけから未観測の凸値を確定扱いしない。
- 一方、トップレベル `cards.json` 各レコードが歴史的に「初期公開データ転記 / 実機入力 / 後日訂正」のどれに由来したかは、古い元資料が残っていないものもある。根拠を追えないものを推測で `observed` に昇格しない。ここだけは継続棚卸し対象。

## 2026-09-15 「未確認 / 確認済」の2状態へ（推定の廃止）

ユーザー方針: **スキルの文言は「確認済」と「未確認」だけで管理する。実機で確認が取れていない段階は、推定値を入れずに「未確認」と書く。**

- 記録（`bloomVariants`）のない強化前の段階は `unknown` になり、カード詳細では**文言を「未確認」と表示**する。
- **スコアの計算では最近傍の凸（= 強化後の最大側レコード）の内容をそのまま流用する。** 旧実装の「最大値 ÷1.1」の推定（`ASSUMED_SKILL_UPGRADE_RATIO`）は廃止した。パラメータの 2凸+10% は実測で確認済みの規則なので逆算を続ける（`derived-from-max-confirmed-ratio`）。
- **記録のある variant は「未確認」にしない** — 実機観測・実機再構成に加えて抽出マスター（外部解析）由来もそのまま使う。外すと実機 SP 欄の閉じた形（誤差 0）が崩れて実機と矛盾する（`src/engine/displayScoreSpecialColumn.test.ts`）。
- **テストは実機の値だけで固定する**（ユーザー方針「テストするときには必ず実機の値を使う。推定値でテストはしない」）。流用値から出した係数を数値で固定していた SP の「未確認を含む編成」のテストは、実機どうしで言えること（アクティブ欄は一致するのに SP 欄は一致しない）だけに絞った。

**区切りは読点だけ**（2026-09-15 に全 73 枚を監査）。括弧・改行・タブ・中黒・スラッシュ・句点はどこにもなく、唯一の半角空白は「AREA15 2人の」（空白がないと「AREA152人」で数字が続いて読めない。ほかの英字所属はすべて空白なし）。**raw の区切りと `structured` はずれてはいけない** — スコアの計算は `structured` を見るので、ずれると画面の文言と計算が食い違う。SP / アクティブの追加条件は raw 末尾に読点でつながり、衣装 / パッシブの読点の数は効果の数 − 1 であることを `src/data/cardText.test.ts` で固定した（現データは全件一致）。

## 実機で入れ直すときの入口（開発用の「開花文言」）

`unknown` のまま残っている段階を実機で埋めるための入力フォームを、サイドメニューの折り畳み「開発用」に置いている（`src/components/BloomTextSheet.vue`。2026-09-15 追加）。カードを選ぶと、スキル 4 種の欄が**いまのカードデータから出る文言**（`cardAtBloomWithProvenance` の raw）で埋まり、区間ごとに出所の印が付く（「未確認」と書かれている区間が、実機を見て埋めてほしいところ）。欄は開花段階ごとではなく**文言が変わらない区間ごと**に 1 つで、区切りは `BLOOM_UPGRADE_STAGE`（衣装 = 変わらない / アクティブ = 1凸 / SP = 3凸 / パッシブ = 4凸）。この区切り自体が実機確認済みの前提なので、**区間の途中で文言が変わる実機観測が出たらこのフォームの前提から直す**（`src/ui/bloomText.ts` の `bloomTextRangesOf`）。

このフォームは**カードデータを書き換えない**。入れた内容はそのブラウザの localStorage に残り、末尾の共有用データ（`kind: "holodori-optimizer/bloom-text"`）としてコピーできるだけで、`src/data/cards.json` と `src/data/bloomEvidence.ts` への反映は、上の provenance の規約どおり根拠を確かめてからコミットで行う。共有用データは上書きした段階に `edited` といまの文言（`current`）を付けるので、**どこが実機由来でどこが据え置きか**が受け取り側で分かる。直していないカードも「この内容で合っている」の記録として入る。

## 事故防止

カード仕様を回答・実験設計へ使うときは、最低でも `cardId / holomenId / role / bloom / provenance` を並べて確認する。検索結果に隣接して表示された別カードのスキルを帰属しない。
