# 表示ユニットスコアの逆解析

ユニット編成画面に表示される「スコアボーナス」と「ユニットスコア」について、いま分かっていることをまとめる。実測値は [repro/](./repro/)（`display-score-*` の観測資料と `*-account-snapshot`。読み方は [repro/README.md](./repro/README.md)）、証拠の扱いは [evidence-policy.md](./evidence-policy.md) が正典。棄却した仮説は末尾の「棄却済み」に、根拠のテスト・観測つきで置く。導出の経緯は Git 履歴にある。

`src/engine/displayScore.ts` は現在の試算実装で、反証済みの近似が残っている。コードがあることをゲーム仕様の証拠にしない。

## 確定・強く支持されること

### ユニットスコアの外側

```txt
unitScore = ceil(totalPower × (1 + scoreBonus / 100) × 2.03734)
```

多数の実機報告で1点単位まで一致する。新しい観測もこの式で cross-check する。ただし式が一致しても、編成・Lv・カードの読み違いまでは検出できない。

### 5カテゴリ

現在の実機では次の5カテゴリを観測できる。

1. 衣装（Costume / Leader）
2. アクティブ（Active）
3. ホロメンボード（Board / SkillTree）
4. パッシブ（Passive）
5. SP（Special）

0のカテゴリは表示上省略されることがある。

【外部情報】サーバー応答にも Active / Leader / Passive / SkillTree / Special の独立カテゴリがあり、カテゴリごとに permil の整数を返すとされる。公開 proto（`HolodoriDB/holodori-app-protos` commit `8465f36b`）には `LiveDeckInGameEffect.LiveActiveSkillLevel { live_active_skill_id, level }` があり、サーバー応答に解決済みの level が観測できる可能性がある（応答そのものは取得していない。公開情報に `LiveDeckEvaluation` 系のキーの算出コードや式は見つかっていない）。現在実装の projective 配分（総量 `T` を raw weight `W` で按分）をゲーム内部式とみなさない。

### 黄ボード

同一編成・同一赤状態の「曲なし Y=0」と「Gamers Y=10%」の直接比較では、Boardだけが `40.7 → 64.8`（+24.1）となった。他4カテゴリは `Costume 14.1 / Active 77.7 / Passive 1.9 / SP 47.0` で同じ。表示値でも `0.1 × (100 + 14.1 + 77.7 + 1.9 + 47.0) = 24.07`。したがって、量子化前 raw を用いる

```txt
YellowBoardIncrement = Y × (100 + Costume + Active + Passive + Special)
```

が現在の最も強いモデル（実装は `songBoardRaw`。Costume を除く旧 4 カテゴリ式はこの直接対照に合わない）。黄は後段のボード加算なので、3 欄の配分には混ぜず pre-yellow を出したあとで戻す。

### 表示 5 欄の生成は「総量」と「配分」の 2 レイヤー

production の実装は `src/engine/displayScore.ts` の `attributeDisplaySupport`。アクティブ欄と SP 欄は独立で、残り 3 欄（衣装 / ボード / パッシブ）を次の 2 段で作る。

**1. 総量 `T`（pre-yellow の 3 欄合計）は source ごとの増分の和。**

```txt
T = Σ_i (衣装支援_i/100) × E_blue の取り分_i    リーダー衣装のスコアサポート
  + (X/100) × E_blue                             赤「全員のスコアサポート効果」
  + (E_blue − アクティブ欄)                      青ボードの純増分
  + (パッシブ込み − E_blue)                      パッシブのスコアサポート（静的）
```

`E_blue` は青の発動頻度で短縮した周期の窓 × 乗算型の発動確率で評価したアクティブ期待値。支援 3 種は加算合成。

**2. 配分は projective。** 3 欄は source ごとの raw weight `W` に比例する。

```txt
W_C = Σ_i (衣装支援_i/100) × H_C の取り分_i    W_B = W_blue + (X/100) × E_blue    W_P = H_P
(衣装, ボード, パッシブ) = T × (W_C, W_B, W_P) / (W_C + W_B + W_P)
```

`H_C` は **p0Only kernel**（青の窓で、対象自身は基準確率 `p0`、同時候補の競合の分母だけ青の乗算型）、`H_P` はそこへ静的にパッシブ支援を掛けた増分、`W_blue` は青ボードを実効スコアサポート % に直して `W_C` と同じ形にしたもの（下の「`W_blue` の決定式」）。`W` は全体を定数倍しても同じ表示になる（gauge 自由）。3 欄の raw が負になる編成（F2 の支援なし側）は実機も 0 表示なので 0 で切る。

この構造を支える観測:

- **非 native の 2 欄が共通倍率で scale する**（現コーパスでは確定扱い）: 1 つの source だけを変えた matched pair では、その source が直接乗る欄（リーダー衣装 → 衣装、赤 → ボード）以外の 2 欄の比が保存される。2 欄とも情報を持つ matched pair は リーダー 4 組（K1 / K3 / K4 / K7）+ 赤 8 行 = 12 件で、量子化込みで意味のある反例は 1 件もない（`displayScoreCategoryRedistributionExperimental.test.ts`。赤 8 行の oracle は RMSE 0.043 / 最大 0.059。ただし赤の行はパッシブ側の拘束が弱く、比例配分を 0.01 の精度で決めているわけではない）。
- **gauge 非依存の比が候補を決める**（`displayScoreProjectiveWeightExperimental.test.ts`）: `H_B / H_C` は K1〜K4 で E_blue(乗算) / p0Only kernel が RMSE 0.031（次点 0.054）/ `C / (L × P)` は赤が違っても一定で `W_C ∝ L` / `B / C` は赤 `X` に対して affine（K1 の X = 23 / 26 / 50 で傾き 0.054〜0.056 一定）/ `H_P / H_C` は K7 の実測区間 0.0313〜0.0330 に `p0Only × 静的` の 0.0328 が入る。
- **青がなければリーダー支援の増分は全量衣装欄**（K5 / K6: 衣装 37.9 = 0.60 × 63.3、44.3 = 0.60 × 73.7。パッシブ支援があってもボード・パッシブ欄は動かない）。カテゴリ再配賦の起点は青。

旧近似（タイムライン差分を全部ボード欄へ入れる）との誤差の比較:

| 材料                                   | 旧 ボード / パッシブ の最大誤差 |            新 ボード / パッシブ の最大誤差 |
| :------------------------------------- | ------------------------------: | -----------------------------------------: |
| 2026-09-08 の Golden 20 ケース         |                       2.7 / 1.8 |                                  0.5 / 0.2 |
| 青の発動頻度系列 4 点（フブキ水着）    |                       2.1 / 0.1 |                    **0.1 / 0（完全一致）** |

衣装欄は旧実装（衣装スコアサポートを静的に (1 + X/100) 倍した増分）が実機より最大 16.9 pt 大きかった（RMSE 6.6）のに対し、新式は同じ 42 行で RMSE 0.28 / 最大 0.8。

### 赤のパラメータ効果と赤スコアサポートは分ける

赤の P/T/S 固定値・割合を変えて総合力が変化しても、スコアカテゴリが変わらなかった対照がある。赤のパラメータ計算を、赤「全員のスコアサポート効果」の表示換算へ混ぜない。

### SP

**確定。**

```
SP 欄 = ceil_0.1%( 表示アクティブ欄 × Σ_i (効果時間_i / 120) × (支援_i / 100) × (1 + 発動率 UP_i / 200) )
```

- **SP スキルごとに独立な加法項**。編成の SP 集合を足し合わせた形になる。
- **発動率 UP はアクティブのタイムラインを動かさない。** 同じ SP のスコアサポート項を `1 + X/200` 倍するだけで、係数はデッキ非依存。
- **発動率 UP の条件は SP ごとに評価する**（不成立なら倍率 1）。
- **基準はアクティブ欄の raw ではなく表示値**（0.1% 単位に切り上げた値）。raw を基準にすると 23 編成中 8 編成で 0.1 低くなる。
- 最終の整数化は 5 欄共通の 0.1% 単位の切り上げ。

カードデータに記録のある実機 **23 編成すべてで誤差 0**（B / 9.7〜9.17 / 2026-09-12 の対照 16 行 / K1〜K4 / F0〜F3 / 2026-09-13 の 40% 観測 / K5・K6・K7）。`200` は 20〜800 の総当たりで唯一解で、連続値でも許容区間は `199.53〜200.16` しかなく、発動率 UP の値が 35 / 40 / 50 / 55% の 4 通りで同じ 1 つの分母を指す。`120` も `119.98〜120.01` しか通らない。発動率 UP をスコアサポートに掛けない加法型はどの分母でも通らない。固定は `displayScoreSpecialColumn.test.ts`。

**確定なのは「アクティブ欄との関係」。** production が SP へ渡すアクティブ欄は下の「Active」モデル（強い推定）が作る値なので、未検証の編成でアクティブ欄がずれれば SP もそのぶんずれる。入力に流用値（未確認の段階）が入っても SP 欄はずれる — K5 / K6 / K7 は未確認の 0凸 SP を流用していたあいだ SP 欄だけ 3.8〜4.2 高く出て、実機値を入れると誤差 0 になった（式の問題ではない）。exploratory 行（恒常みこ 0凸、Lv 約 20）はアクティブ欄そのものが実機と 0.5 合わないので corpus に入れない。

観測: [repro/display-score-20260908-11.md](./repro/display-score-20260908-11.md)、[repro/display-score-20260912.md](./repro/display-score-20260912.md)、[repro/display-score-20260913-frequency.md](./repro/display-score-20260913-frequency.md)、[repro/display-score-20260913-sp.md](./repro/display-score-20260913-sp.md)。

## 強い推定

### Active

200秒の共通仮想タイムラインを使う現在モデルが既存Goldenに非常によく一致する。**評価区間が曲に依存しないことは実機で確認済み**（曲の長さは表示ユニットスコアに入らない — [game-spec.md](./game-spec.md)「楽曲・イベント」）。200秒という値自体が実機の内部値である証拠ではない。

- 発動候補: `k × interval <= s < k × interval + duration`、`k >= 1`
- 基礎発動確率: 高55% / 中46% / 低37%【外部情報を含む】。実数値自体はゲーム内表示から直接確認できない
- 同時候補時は確率和で正規化する（`Σ up × p / max(1, Σ p)`）
- Activeの0.1%単位化は切り上げで既存観測と一致（20 ケースで四捨五入 15/20 に対し切り上げ 20/20）
- ライフ・コンボ・タイプ人数の条件つきアクティブは production どおり扱って K5 / K6 が一致する

**青ボードの反映は 発動率 = 乗算型 `p = min(1, p0 × (1 + r/100))` / 発動頻度 = 周期の短縮 `interval ÷ (1 + f/100)`**（production も乗算型）。支援の総増分 `支援/100 × E_blue` が 13 対照 + Leader-only matched pair 7 組 + F0〜F3 で量子化の範囲に収まり、加算型は同じ材料で 2〜4 pt 外れる。頻度側の非単調な実機系列（ボード欄 4.6 → 4.7 → 4.4 → 5.0）は同時候補の正規化 `max(1, Σp)` と projective 配分で自由係数なしに再現できる（周期が短くなると低スコアのメンバーが候補に増えて平均が下がる秒がある）。

### パッシブのスコアサポートは静的

対象メンバーに常に `S_ji` を掛ける（供給側 `j` の発動確率で割り引かない）。青なし・パッシブ支援ありの negative control K6（恒常マリン 1凸「3期生が2人以上で3期生2人のスコアサポート効果 9%」）で静的型は 2.85（実機 2.9）、gated 型は 1.0。対象は production と同じ「count 人」限定で全員化はしていない。総合力側のパッシブ（`power.ts` の `passiveParamBonus`）とは別のレイヤーなので、片方の規則を他方へ流用しない。

### スコアサポート（赤・リーダー衣装）の総量は `支援/100 × E_blue(乗算)`

`E_blue` は production のアクティブ欄と同じ評価器（200秒・条件解決済みスコアUP・同時候補の正規化）に乗算型の青を入れたアクティブ期待値。

- **赤 `X`**: 実機 13 対照（[repro/display-score-20260912.md](./repro/display-score-20260912.md) の赤+24 × 9、R-061 +3、R-002 +10 × 3）に対する raw 予測は RMSE ≈ 0.09 pt、最大 ≈ 0.13 pt（各対照はその観測時点の青実効値を使用。回帰ガードは `displayScoreExperimental.test.ts`）。
- **リーダー衣装 `S`**: 同じメンバー 5 人・赤 0・黄 0 でリーダーだけを 恒常みこ 0凸（支援 0）→ 典獄クロニー 0凸（60%）に替えた K1〜K7（[repro/display-score-20260912.md](./repro/display-score-20260912.md)「Leader-only matched pairs」）。

| :-------------------------------------------------- | :------------------------------- | -------: | --------------------------------: | ------------------: | ------------------: |
| K1 水着ミオ1 / 水着ころね2                          | 38.6 / 12.6 / 1.1                |     52.3 |                              46.6 |                54.9 |                52.3 |
| K2 水着ミオ1 / 恒常マリン1                          | 46.2 / 6.3 / 0                   |     52.5 |                              43.2 |                54.6 |                52.4 |

K1〜K4 で乗算型は RMSE 0.11 / 最大 0.18、加算型は RMSE 2.7（+2.1〜+3.1 過大）、`E_base` は RMSE 6.2。過去の同じ 5 人での 水着フワワ 25% + 赤 26% と クロニー 60% + 赤 0 の合計差も 4 組とも `(60 − 25 − 26)/100 × E_blue` に ±0.2 で一致する。K5 / K6 の 0凸アクティブは 2026-09-13 にカード詳細画面で再確認した実機値で、production の評価器は式の変更なしに raw 63.24 / 73.69 → 表示 63.3 / 73.7 を再現する。

- **支援 3 種は加算合成**: 候補 i の値を `up_i × p_i × (1 + L + X + P_i) / max(1, Σp)` とすると K6 の総増分 44.3 は 0.6 × 73.7 = 44.2、K1〜K4 は上のとおり。赤 / 衣装コーパス 11 行の 4 欄合計も赤の前後 22 点すべて −0.1〜−0.4（`displayScoreSourceAttributionExperimental.test.ts`）。
- **衣装欄の絶対値は一様倍率 `0.25 × E` ではない。** 水着フワワ 25% の 9 編成で衣装欄は 13.4〜17.4 と編成で大きく変わり（相手枠に強く依存。水着ミオ1 + 恒常マリン1 は候補窓が完全に重なる組が最大）、どの一様倍率の下限（`0.25 × E_base` = 17.7〜19.9）も全編成が下回る。衣装欄そのものの独立した一般式は要らない — 上の projective 配分で説明する。

### `W_blue` の決定式（**現時点の最有力 production model。確定ではない**）

材料は [repro/display-score-20260913-blue-weight.md](./repro/display-score-20260913-blue-weight.md) の 9 状態（F0〜F3 と同じ 5 人・同じリーダー 典獄クロニー 60%・曲なし・赤 0・黄 0 のまま、青のマスを 1 つずつだけ開閉した系列。発動率だけ 3pt 動かす組 3 つ・発動頻度だけ 4pt 動かす組 2 つ・ΣR も ΣF も変えずに所有者だけ移す組 2 つ）と、[repro/display-score-20260913-frequency.md](./repro/display-score-20260913-frequency.md) の F0〜F3（同じ 5 人・同じ ΣR 92.1・同じ ΣF 12% で発動頻度マスの所有者だけを移した 4 状態）。合わせて同一編成 13 状態、K1〜K7 を足して **20 状態**で評価する。

```txt
W_blue = (青の実効スコアサポート% / 100) × H_C

青の実効支援% = Σ_i 単独寄与_i × 発動率 UP_i / Σ_i 単独寄与_i
              + Σ_i 単独寄与_i × 発動頻度 UP_i / アクティブ欄 raw
単独寄与_i     = スコア UP_i × p0_i × 発動候補秒_i / T   （同時候補の正規化を入れない、メンバー単独の基準寄与）
```

実装は `displayScore.ts` の `blueSupportPercentOf`。**リーダー衣装の `W_C = (L/100) × H_C` と同じ形**で、青は「メンバーの発動率 / 発動頻度 % を、そのメンバーの単独寄与で重みづけした加重平均」というスコアサポート % として配分に効く、という読み方。固定は `displayScoreBlueWeight.test.ts`。

#### 要求区間の作り方（量子化規則を未確定のまま扱う）

実測が要求するのは `W_blue / H_C = (L/100) × ボード欄 / 衣装欄` だが、表示 0.1 刻みから raw へ戻すときに量子化規則の仮定が入る。3 欄の規則は未確定（下の「量子化」）なので、**切り上げ `(d − 0.1, d]` と四捨五入 `[d − 0.05, d + 0.05)` を分けて評価する**。対称な `± 0.05` は四捨五入を仮定したもので、production が採っている切り上げとは別物。

#### 候補の比較（20 状態。inside = 区間に入った数 / 最大逸脱 = 外れたぶんの最大）

| 候補                                                     | 切り上げ inside / 逸脱 | 四捨五入 inside / 逸脱 |
| :------------------------------------------------------- | ---------------------: | ---------------------: |
| **採用（上の式）**                                       |   **12 / 20 · 0.0026** |   **10 / 20 · 0.0029** |
| 分母をそろえる（両方 `Σ 単独寄与`）                      |         3 / 20 · 0.011 |         2 / 20 · 0.011 |
| 分母をそろえる（両方 アクティブ欄 raw）                  |         2 / 20 · 0.072 |         2 / 20 · 0.072 |
| 条件つきスコア UP を解決しない（基準値で重みを作る）     |         2 / 20 · 0.022 |         2 / 20 · 0.022 |
| 旧 production の member-local 型（`H_C` の取り分 × %）   |         2 / 20 · 0.021 |         2 / 20 · 0.022 |
| 「編成全体の評価値どうしの差」型（`E_blue(加算) − H_C`） |         3 / 20 · 0.064 |         3 / 20 · 0.064 |

どちらの量子化仮定でも順位は変わらず、採用式が inside で 4 倍・最大逸脱で 4 倍以上良い。ただし採用式でも 20 状態中 8 状態は切り上げ区間の外（S1 / S2 / S3 / S3' / F16 / RmF / K1 / K4。逸脱はほとんど 0.0001〜0.0006、最大は K1 の 0.0026）。青なしの K5 / K6 は `W_blue = 0` の negative control として厳密に通る。

#### この系列が支持すること

1. **青の % が直接効き、タイムライン経由ではない。** 発動頻度 +4% はこの編成では発動候補秒を 1 秒も増やさない（周期 27 → 25.96 秒でも 200 秒に入る窓は 7 個のまま）のに、実機の配分は 4% のマス 1 つで一定量だけ動く。青の窓・青の確率から作った量はこの一定量を作れない。
2. **メンバーの重みは青の状態に依存しない。** 単独寄与は基準タイムラインだけで決まるので、同じ 5 人なら 13 状態で同じ値になる（旧 member-local 型の `H_C` の取り分は青で動く）。
3. **ただし所有者には依存する。** `単独寄与_A ≠ 単独寄与_B` なら同じ % を A から B へ移すと値は変わる（F0 → F3 で 0.2200 → 0.2219）。F0〜F3 で実測の要求区間がほぼ重なるのは、この編成ではメンバー間の重みの差が量子化の区間幅（約 0.002）より小さいという観測で、「所有者に依存しない」証拠ではない。

#### 分母は「自然量の中では明確に優位」だが一意ではない

自由係数なしで作れる正規化量 7 つ（`Σ 単独寄与` / `Σ 単独寄与(青の窓)` / アクティブ欄 raw / 表示アクティブ欄 / `H_C` / `E_blue(乗算)` / `E_blue(加算)`）を 発動率分母 × 発動頻度分母 の 49 組で総当たりした（切り上げ仮定）:

## 量子化（0.1% 単位）

**アクティブ欄と SP 欄は 0.1% 単位の切り上げで確定**（実機 20 ケースで四捨五入 15/20 に対し切り上げ 20/20）。

**衣装欄は「アクティブ欄との差」として量子化される** — `ceil_0.1(A + C) − ceil_0.1(A)`（確定）。欄ごとに独立に丸める現行 production の規則は棄却済み。ボード欄とパッシブ欄の位相は分かれていない。

### 欄ごとに独立に丸める形が落ちる理由（モデル非依存）

K5 / K6 はどちらも 青 0・赤 0・黄 0 で、production は **衣装欄 raw = 0.60 × アクティブ欄 raw** をそのまま返す（K6 はパッシブ支援があるが projective 配分で約分される）。この形が正しいなら実機のアクティブ欄の表示値だけから衣装欄の表示値が決まる。

| 材料                        | K5                            | K6                                      |
| :-------------------------- | :---------------------------- | :-------------------------------------- |
| 実機 アクティブ欄           | 63.3                          | 73.7                                    |
| 切り上げ前提の raw 区間 `A` | `(63.2, 63.3]`                | `(73.6, 73.7]`                          |
| `0.60 × A`                  | `(37.92, 37.98]`              | `(44.16, 44.22]`                        |
| 実機 衣装欄                 | **37.9**（切り上げなら 38.0） | **44.3**（四捨五入・切り捨てなら 44.2） |

アクティブ欄 3 通り × 衣装欄 3 通りの 9 通りすべてで K5 と K6 は両立しない（`displayScoreQuantization.test.ts`「{K5, K6} が落とす仮説(モデル非依存)」）。落ちているのは丸めの選び方ではなく、欄ごとに独立に丸めるという位相そのもの。`ceil(A + C) − ceil(A)` は自由係数なしで K5 と K6 を同時に満たし、現在のモデルの raw（63.235 / 73.693）は両方の要求区間に入る。コーパス 153 列は位相の判別に使えない（青・赤入りで raw 自体がまだ合っていない）。

### 位相・総量・`W_C` は確定、残るのは配分の重み `w_i`

青 0・赤 0・黄 0・曲なしで 16 編成（リーダー 典獄クロニー 60%）、うち 3 編成は 恒常ぺこら（25%）でも、6 編成は 恒常みこ 0凸（支援 0）でも読んだ（[repro/display-score-20260915-costume.md](./repro/display-score-20260915-costume.md)。固定は `displayScoreCostumeQuantization.test.ts`）。

**確定（`A` の量子化ぶれを許しても残る）**:

- アクティブ欄 16/16、みこ側のパッシブ欄 6/6、SP 欄・合計・ユニットスコアが一致。したがって**総量 `T = 0.60 × A + ΔP` と対象選抜は正しい**。
- **衣装欄はアクティブ欄との差として量子化される。** 欄ごとの規則と累積順序を総当たりして残るのは差分型だけ。パッシブ欄が独立-切り上げか差分かは分かれない。
- **`W_C` はリーダーのスコアサポート % に比例する。** メンバーを動かさず 60% → 25% にしたとき、60% で測った重みの割合 `f` がそのまま通る（予測を先に出しての out-of-sample 一致。3/3）。

したがって表示の重みは `W = Σ (支援% / 100) × w_i` で、**残る不定性はメンバーごとの `w_i` の形だけ**。`w_i` は production の「競合で正規化した取り分」ではなく（12 編成中 9 で外れる）、一様でもない。自由係数なしの候補の一致数は 取り分 3 / 発動確率 4 / 一様 4 / スコアUP% 3 / `up × p0` 2。6 枚プール（ロボ子 / ポルカ / リス / 奏 / スバル / アーニャ）に限ればカードごとに固定の重みが過剰決定で成立し、周期 34 秒の リス / スバル の取り分 0.87 / 0.84 に対し実機は ≥ 1.02 / ≥ 0.98 を要求する — **表示の重みはタイムライン上の寄与よりずっと平ら。**

`f` を出すときは `A` の量子化ぶれを必ず入れる。モデルの `A` は表示値を 16/16 で再現するが 1 quantum のぶれが残り、それは `f` の区間幅と同じ桁。入れずに出すと区間が狭く出て、「位相は 1 通り」「S2 → S3 で向きが逆」のような誤った結論になる。

**production はまだ現行のまま**（位相だけ直すと配分が逆向きに崩れる。`finishDisplay` に既知の実装ギャップとして明記）。次の観測は `pending.md` 4。

## 実験・実装時のルール

Golden の扱い・状態ラベル・仮説を昇格する条件・カード事実の確認手順は [evidence-policy.md](./evidence-policy.md) が正典。表示スコアの解析では、加えて次を守る。

- モデル変更前に既存コーパスで反証を探す。
- 実ライブのスコア式と表示ユニットスコアを混同しない。
- 青 / 赤 / 黄 / 緑の実効値は、マスの表記値ではなくコネクト増幅込みの値を使う（例: K7 の 水着フブキ の発動率は表記値 6% ではなく 15%）。
- 表示 0.1 刻みから raw へ戻すときは量子化規則の仮定が入る。切り上げと四捨五入を分けて評価し、モデルの `A` の 1 quantum のぶれを入れてから区間を出す。
- `W` は定数倍しても同じ表示になる。raw `W` をデッキ間で比べる議論は gauge を固定した比較で、構造的棄却には gauge 非依存の比を使う。
