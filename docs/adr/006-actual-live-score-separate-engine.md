# ADR-006: 実ライブスコアは表示ユニットスコアと別エンジンにし、旧簡易期待値モデルを削除する

- Date: 2026-09-09
- Status: Accepted

## Decision

ツールの第一エンジンは**ユニット編成画面の表示ユニットスコア**（総合力 `src/engine/power.ts` + スコアボーナス `src/engine/displayScore.ts`）とし、探索の順位づけはこの値に曲・イベントで決まる倍率（score modifier: 黄ボードの楽曲スコアボーナス・イベントスコアボーナス）を掛けた値で行う。**実際に曲をプレイしたときのライブスコアは未解明・未実装**として扱い、将来まったく別のエンジンとして新規に設計する（譜面のノーツ列・メンバー順・SP の発動位置と順序・アクティブの重なり・スコアサポートの重なり・RNG の期待値）。

この決定に伴い、曲長で按分する旧簡易期待値モデル（`src/engine/live.ts` と `src/data/live.ts` の `SP_ACTIVATIONS_PER_SONG` / `SCORE_SUPPORT_WEIGHT`）を削除し、順位づけの型・関数名から「期待スコア」を外す（`LiveBreakdown` → `ScoreModifierBreakdown`、`expectedScore` → `adjustedUnitScore`、`liveFactorOf` → `scoreModifierFactor`、`OptimizeRequest.live` → `songBonus`）。表示スコアボーナス専用の推定値である発動確率 `ACTIVE_PROBABILITY`（高 55 / 中 46 / 低 37）は `displayScore.ts` に置き、実ライブのエンジンと共有しない（同じ値になる保証がない）。

## Context

2026-09-08 に結果の値と順位づけを表示ユニットスコアへ切り替えて以降、`live.ts` が返すアクティブ・SP の期待寄与は**順位づけにも UI 表示にも使われていない**（結果一覧と詳細に出るのは総合力・表示スコアボーナス 4 項目・ユニットスコアだけ）。内容も「floor(曲長 / 周期) × 発動率 × 効果時間 / 曲長」「SP は 1 曲 1 回」「スコアサポートをスコア UP と等価」という精度未検証の近似で、実機との突き合わせも行っていない。これを「実ライブスコアのエンジン」として残すと、実機で検証を進めている表示スコアボーナスのモデルと混ざり、どちらの数字が何を意味するのか読めなくなる。

却下した代替案: (1) `legacyLiveEstimate.ts` へ改名して隔離する — 使われないコードの維持と誤読のリスクだけが残る（検証済みの値がひとつもないので保存する価値がない）。(2) `live.ts` を改造して実ライブエンジンに育てる — 曲長で按分する構造は譜面ベースの計算と噛み合わず、書き直しになる。(3) 曲長ベースの期待値を順位づけに戻す — 実機の表示ユニットスコアと合わない値で並べることになる。

曲の演奏時間の中央値（旧 `DEFAULT_SONG_DURATION_SECONDS`）だけは UI の「指定なし」行の表示に使っているので、データ由来の値として `src/data/index.ts` の `MEDIAN_SONG_DURATION_SECONDS` に移した。

## Consequences

### Pros

- 「表示ユニットスコアの再現」という 1 つの目的にエンジンとテスト（ゴールデン 20 ケース）が集中し、信頼度（確定 / 強い推定 / 仮説）が型と関数の単位で言えるようになる。
- 順位づけの型名が実体（ユニットスコア × 倍率）と一致し、「期待スコア」という誤解を招く名前が消える。
- 実ライブエンジンを作るときに、旧モデルの仮定（1 曲 1 回の SP など）を引き継がずゼロから設計できる。

### Cons

- 曲を指定しても順位が変わるのは黄・イベントの倍率だけになり、「曲別最適化」の意味が実ライブエンジンができるまで薄い（曲ピッカーの「指定なし / 全曲の中央値」表示は曲長を試算に使う印象を与えるので、表示の見直しは未判断 — pending）。
- 実ライブスコアの実装は 0 から。削除したコードは git 履歴にのみ残る。
- 実ライブ側の発動確率が判明したとき、表示モデルの `ACTIVE_PROBABILITY` と二重管理になりうる（共有するかはそのとき判断する）。

**Update (2026-09-09):** Cons の「中央値表示の見直しは未判断」は解消した。曲ピッカーの「指定なし」行から演奏時間の中央値表示（`2:09` / 全曲の中央値）を削除し、行は「指定なし」だけにした（行の高さは充填時に合わせる）。試算に効かない値を実値として見せると「曲長で計算している」と読めるため。これに伴い `MEDIAN_SONG_DURATION_SECONDS` は参照がなくなったので `src/data/index.ts` から削除した（Decision 末尾の「UI 表示用に残した」はこの追記で置き換わる）。

**Update (2026-09-09、外部情報):** ユーザーから、ゲームのサーバー応答ではスコアボーナスが**カテゴリごとの独立した値（‰ の整数）**として返り、カテゴリが アクティブ / リーダー（衣装）/ パッシブ / スキルツリー（ホロメンボード）/ スペシャル の **5 つ**であるとの情報が共有された（実機画面では確認できない領域なので【外部情報】扱い。ADR-002 の方針どおり、この情報を出典とするデータやコードはリポジトリに入れない）。これにより、`displayScore.ts` の現在のボード欄・パッシブ欄の求め方（3 本のタイムラインの差分を配賦する `attributeDisplaySupport`）は**ゲーム内部の式の再現ではなく、各カテゴリの算出式が不明なあいだの近似的な帰属モデル**だと確定した。表示が 4 欄なのは実機 20 ケースで衣装（リーダー）由来が 0 だったためで、スコアボーナスの源が 4 種類しかないわけではない。同じ情報源では発動確率の 3 段階（低 37 / 中 46 / 高 55%）も同じ値で、`ACTIVE_PROBABILITY` の値は基礎発動率としては裏づけがある（ただしゲーム内に数値表示がないので「実機確定」にはしない。評価式がその値をどう扱うかは別問題）。この Update は Decision を変えない — 次の逆解析の対象が「スキルツリー（ホロメンボード）欄」と「パッシブ欄」の算出式である、と対象を明確にするための記録（pending 12）。
