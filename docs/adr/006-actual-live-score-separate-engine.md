# ADR-006: 実ライブスコアは表示ユニットスコアと別エンジンにし、旧簡易期待値モデルを削除する

Date: 2026-09-09

## Status

Accepted

## Decision

ツールの第一エンジンはユニット編成画面の表示ユニットスコア（総合力 `src/engine/power.ts` + スコアボーナス `src/engine/displayScore.ts`）とし、実際に曲をプレイしたときのライブスコアは未解明・未実装として、将来まったく別のエンジンとして新しく設計する。これに伴い、曲長で按分する旧簡易期待値モデル（`src/engine/live.ts` と `src/data/live.ts` の定数）を削除し、順位づけの型・関数名から「期待スコア」を外す。

## Context

2026-09-08 に結果の値と順位づけを表示ユニットスコアへ切り替えてから、`live.ts` が返すアクティブ・SP の期待寄与は、順位づけにも UI にも使われていなかった。中身も「floor(曲長 / 周期) × 発動率 × 効果時間 / 曲長」「SP は 1 曲 1 回」「スコアサポートはスコア UP と等価」という精度未検証の近似で、実機とも突き合わせていない。これを実ライブスコアのエンジンとして残すと、実機で検証を進めている表示スコアボーナスのモデルと混ざり、どの数字が何を意味するのか読めなくなる。

順位づけは、表示ユニットスコアに曲・イベントで決まる倍率（score modifier: 黄ボードの楽曲スコアボーナス・イベントスコアボーナス）を掛けた値で行い、名前を実体に合わせる（`adjustedUnitScore` / `scoreModifierFactor` / `songBonus` など）。実ライブのエンジンは、譜面のノーツ列・メンバー順・SP の発動位置と順序・アクティブの重なり・スコアサポートの重なり・RNG の期待値から組み立てる。表示スコアボーナス専用の推定値である発動確率 `ACTIVE_PROBABILITY` は `displayScore.ts` に置き、実ライブのエンジンとは共有しない（同じ値になる保証がない）。

外した案:

- `legacyLiveEstimate.ts` へ改名して隔離する — 使われないコードの維持と誤読のリスクだけが残る（検証済みの値が 1 つもなく、残す価値がない）。
- `live.ts` を改造して実ライブエンジンに育てる — 曲長で按分する構造は譜面ベースの計算と噛み合わず、結局書き直しになる。
- 曲長ベースの期待値を順位づけに戻す — 実機の表示ユニットスコアと合わない値で並べることになる。

## Consequences

### Pros

- 表示ユニットスコアの再現という 1 つの目的にエンジンとテスト（ゴールデン 20 ケース）が集中し、信頼度（確定 / 強い推定 / 仮説）を型・関数の単位で言えるようになる。
- 順位づけの型名が実体（ユニットスコア × 倍率）と一致し、誤解を招く「期待スコア」という名前が消える。
- 実ライブエンジンを、旧モデルの仮定（1 曲 1 回の SP など）を引き継がずにゼロから設計できる。

### Cons

- 曲を指定しても順位が変わるのは黄・イベントの倍率だけで、実ライブエンジンができるまで「曲別最適化」の意味は薄い。
- 実ライブスコアの実装は 0 から始まる。削除したコードは Git 履歴にだけ残る。
- 実ライブ側の発動確率が分かったとき、表示モデルの `ACTIVE_PROBABILITY` と二重管理になりうる（共有するかはそのとき決める）。

**Update (2026-09-09、外部情報):** ゲームのサーバー応答ではスコアボーナスがカテゴリごと（アクティブ / リーダー（衣装）/ パッシブ / スキルツリー（ホロメンボード）/ スペシャル）の独立した ‰ の整数で返る【外部情報。ADR-002 のとおり、これを出典とするデータやコードは入れない】ので、`displayScore.ts` の欄の求め方はゲーム内部の式の再現ではなく、各カテゴリの式が分からないあいだの帰属モデルである（`docs/ai/display-score.md`「5カテゴリ」）。発動確率の 3 段階も同じ値だったが、ゲーム内に数値の表示がないので実機確定にはしない。Decision は変えない。

**Update (2026-09-11):** この ADR の「黄ボードの楽曲スコアボーナスは倍率」は誤りで、黄は総合力を変えず、スコアボーナスのボード欄に入る（観測は `docs/ai/repro/display-score-20260908-11.md`、式は `docs/ai/display-score.md`「黄ボード」）。後掛けの倍率に残るのはイベントだけで、黄は候補ごとの値に比例するので曲を選ぶと順位が変わりうるが、第一エンジンを表示ユニットスコアにする Decision は変わらない。
