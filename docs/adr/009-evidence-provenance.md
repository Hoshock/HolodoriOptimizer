# ADR-009: 実測・転記・推定を provenance で分離する

Date: 2026-09-12

## Status

Accepted

## Decision

ゲームデータと逆解析では、実機観測・公開情報の転記・実測値から再構成した文・最大開花値からの推定を同じ「事実」として扱わず、開花の解決には provenance を返す API を用意し、実機による訂正は `cardCorrections.ts` に隔離する。

## Context

`cards.json` のトップレベルは最大開花側のレコードで、途中の開花段階は `bloomVariants` と仮定の倍率で補っていた。一部の variant は実機で数値を確かめていたが、`raw` は最大開花の文をもとに数値だけを差し替えた再構成文だった。また、検索スニペットに並ぶ隣のカードを取り違えて帰属させると、カード仕様・実験設計・正典まで連鎖して誤る危険がある。

さらに、従来の `variantAt()` は 0凸の variant を強化段階のあとにも当てうるので、1凸 Active・3凸 SP・4凸 Passive の境界を越えて古い値を引きずる可能性があった。

## Consequences

### Pros

- 後続のエージェントが「実測」と「最大値からの推定」を機械的に区別できる。
- 実機による訂正を元データの取り込み層と分けられ、訂正の理由を小さいファイルで監査できる。
- variant が開花の強化境界をまたがないことをテストで固定できる。
- 単発の観測を尊重しつつ、人間の読み違いを再確認できる形で扱える。

### Cons

- `cards.json` 単体はランタイムの最終的な正典ではなくなるので、直接 import を増やさない規律が要る。
- provenance API を通らない既存のコードでは、値の出所を表示できない。
- 既存の全カードを実機確認済みにできるわけではなく、`source-transcribed` / `estimated` は残る。

**Update (2026-09-15):** Cons の「`estimated` は残る」は [ADR-011](011-bloom-text-known-or-unknown.md) で置き換わった。記録のない開花段階は推定せず「未確認」(`unknown`)とし、計算には最も近い凸の内容を流用する。
