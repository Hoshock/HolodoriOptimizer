# ADR-009: 実測・転記・推定を provenance で分離する

- Date: 2026-09-12
- Status: Accepted

## Decision

ゲームデータと逆解析では、実機観測・公開情報の転記・実測値から再構成した文・最大開花値からの推定を同じ「事実」として扱わない。開花解決には provenance を返すAPIを用意し、実機訂正は `cardCorrections.ts` に隔離する。

## Context

`cards.json` のトップレベルは最大開花側のレコードで、途中開花は `bloomVariants` と仮定倍率で補っていた。一部 variant は実機で数値を確認したものの `raw` は最大開花文を基に数値だけ差し替えた再構成文だった。また、検索スニペットの隣接カードを誤って帰属すると、カード仕様・実験設計・正典まで連鎖して誤る危険がある。

さらに従来の `variantAt()` は0凸variantを強化段階後にも適用し得たため、1凸Active・3凸SP・4凸Passiveの境界を越えて古い値を引きずる可能性があった。

## Consequences

### Pros

- 後続エージェントが「実測」と「最大値からの推定」を機械的に区別できる。
- 実機訂正を元データ取り込み層と分離し、訂正理由を小さいファイルで監査できる。
- 開花強化境界をvariantが跨がないことをテストで固定できる。
- 単発観測を尊重しつつ、人間の読み違いを再確認可能な形で扱える。

### Cons

- `cards.json` 単体はランタイムの最終正典ではなくなるため、直接importを増やさない規律が必要。
- provenance APIを経由しない既存コードでは、値の出所を表示できない。
- 既存の全カードを実機確認済みにできるわけではなく、`source-transcribed` / `estimated` は残る。
