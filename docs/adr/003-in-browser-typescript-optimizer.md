# ADR-003: スコア計算・編成最適化はブラウザ内 TypeScript の全探索を基本とする

Date: 2026-08-31

## Status

Accepted

## Decision

ユニットスコアの計算と編成最適化はすべてブラウザ内の TypeScript で行い、リーダー固定時の残り 5 枠(一部メンバー固定時は残りの枠)を全探索して、上位 n 件を保持しながら TOP n 候補を返す。スコアモデルはコミュニティで検証されている解析モデルを採り、UI に「試算値であり実測と異なりうる」と明記する。

## Context

2026-08 時点の ★5 は約 70 枚で、リーダー固定の全探索は C(69,5) ≈ 1,124 万通り。1 組合せの評価は条件判定と加算・乗算だけなので、単一スレッドの TypeScript でも数秒で終わり、サーバも WASM も要らない。カードが 150 枚規模になると約 5.9 億通りで数十秒〜分かかるので、そのときに Web Worker での並列化か枝刈り(候補カードの絞り込み)を入れる。そのために計算コアは、どちらも後から足せる純粋関数として書く。

公式のスコア計算式は非公開なので、コミュニティのモデルに頼るしかない。採ったモデルでは、基礎値はメンバー 5 人のパラメータ合計だけで、リーダー自身のパラメータは加算せずパッシブも発動しない。リーダーは衣装スキルなどの乗算バフで寄与する。

外した案:

- サーバサイドで計算する — 静的サイトの方針に反する。
- 事前計算した結果を埋め込むだけにする — 「一部メンバー固定」のような対話的な条件変更に応えられない。
- ILP などの厳密最適化ライブラリ — スキル発動条件の非線形性に合わず、全探索で足りる規模でもある。

## Consequences

### Pros

- 静的サイトだけで完結し、オフラインでも動く。運用コストがかからない。
- 全探索なので、モデル上の厳密な最適解と TOP n を保証できる。
- 純粋関数の計算コアは `vp test` で単体テストしやすい。

### Cons

- スコアモデルが実測とずれる可能性があり、モデルの修正に追従する必要がある。
- カードが増えると、いずれ Web Worker か枝刈りの実装が必須になる。

**Update (2026-09-08):** スコアモデル(連鎖乗算・カード詳細値基準のコミュニティ解析モデル)は実機観測と合わず、[ADR-004](004-total-power-additive-model.md) の加算モデルに置き換えた。ブラウザ内 TypeScript・全探索・Web Worker の方針は変わらない。

**Update (2026-09-09):** 探索は上限値で候補を絞ってから正確に評価する近似になり、Pros の「厳密な最適解と TOP n を保証できる」は [ADR-005](005-display-unit-score-shortlist-search.md) で置き換わった(品質は小規模の厳密探索と突き合わせて検証する)。ブラウザ内 TypeScript・Web Worker・純粋関数の方針は続く。

**Update (2026-10-08):** Web Worker での分担は [ADR-018](018-faster-without-changing-results.md) で入れた(探索を組合せの 1 枚目で何本かに分け、結果は 1 本と同じ)。
