# ADR-003: スコア計算・編成最適化はブラウザ内 TypeScript の全探索を基本とする

- Date: 2026-08-31
- Status: Accepted

## Decision

ユニットスコアの計算と編成最適化は、すべてブラウザ内の TypeScript で実装する。リーダー固定時の残り 5 枠(および一部メンバー固定時の残り枠)は全探索を基本とし、TOP n 候補は探索中に上位 n 件を保持して返す。カード数の増加に備え、計算コアは Web Worker 化と枝刈り(候補カードの絞り込み)を後付けできる純粋関数として設計する。スコアモデルはコミュニティで検証されている解析モデル(基礎値はメンバー 5 人のパラメータ合計のみで、リーダー自身のパラメータは非加算・パッシブ非発動。リーダーは衣装スキル等の乗算バフで寄与)を採用し、UI に「試算値であり実測と異なりうる」旨を明記する。

## Context

2026-08 時点の★5 カードは約 70 枚で、リーダー固定の全探索は C(69,5) ≈ 1,124 万通り。1 組合せの評価は条件判定と加算・乗算のみの軽い演算のため、単一スレッドの TypeScript でも数秒以内に完了する規模であり、サーバや WASM は不要。カードが 150 枚規模になると約 5.9 億通りとなり全探索は数十秒〜分オーダーに達するため、その時点で Web Worker 並列化または枝刈りを導入する。公式のスコア計算式は非公開のため、コミュニティモデルへの依拠は避けられない(却下した代替案: サーバサイド計算は静的サイト方針に反し不採用。事前計算結果の埋め込みのみで済ます案は「一部メンバー固定」等の対話的な条件変更に対応できず不採用。ILP 等の厳密最適化ライブラリはスキル発動条件の非線形性に合わず、全探索で足りる規模のため不採用)。

## Consequences

### Pros

- 静的サイトのみで完結し、オフラインでも動作する。運用コストゼロ。
- 全探索なのでモデル上の厳密な最適解と TOP n を保証できる。
- 純粋関数の計算コアは `vp test` での単体テストが容易。

### Cons

- スコアモデルが実測とずれる可能性があり、モデル修正の追従が必要。
- カード増加でいずれ Web Worker / 枝刈りの実装が必須になる。
