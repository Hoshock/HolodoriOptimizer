# ADR-005: 表示ユニットスコアの探索は二段階の shortlist 評価を採用し、厳密探索を検証用に残す

- Date: 2026-09-09
- Status: Accepted

## Decision

通常の UI の編成探索は、**上限値による shortlist → 正確評価**の二段階で行う（`src/engine/optimize.ts`）。表示する候補 1 件の最終値は必ず正確な計算（`computeStaticPower` + `computeDisplayScoreBonus`）で求めるが、shortlist の前段で真の Top N を落とす可能性は 0 ではないため、**この探索は近似である**と位置づけて文書と UI の説明で「厳密な最適解」と言わない。品質を測るために、小規模データで全候補を正確評価する**厳密探索**（`src/engine/exactSearch.ts`）を検証経路として維持し、近似と突き合わせるテスト（`exactSearch.test.ts`）を持つ。将来は「安全な branch-and-bound」（上界が数学的に真値以上と保証できるものだけを使う）か、十分高速な厳密評価へ移行する。

## Context

表示スコアボーナスのモデルが 5 人共通の 200 秒タイムライン（[ADR-004](004-total-power-additive-model.md) の 2 回目の Update）になり、葉ごとの評価が重くなった。★5 73 枚のリーダーおまかせ探索（約 10 億通り）は葉ごとに正確評価すると 5 分を超え、UI として使えない。そこで総合力の上限 × スコアボーナスの「正規化なしの線形和」（タイムラインの正規化は必ず値を下げるので上界になる）で上位 `topN × SHORTLIST_FACTOR`（最小 `SHORTLIST_MIN` = 500）件に絞り、その候補だけを正確に評価して並べ直す形にしたところ、Node 単体計測でリーダー探索 ≈ 20 秒・固定リーダー ≈ 11 秒に収まった。

これにより [ADR-003](003-in-browser-typescript-optimizer.md) の「全探索なのでモデル上の厳密な最適解と TOP n を保証できる」は成り立たなくなったので、その部分をこの ADR で置き換える（ブラウザ内 TypeScript・Web Worker・純粋関数の方針は継続）。

却下した代替案: (1) 葉ごとの厳密評価を維持 — 数分待たせる UI は採れない。(2) 単調性の仮定を使った強い枝刈り（「発動頻度が高いほど必ず強い」「発動率は同じ比率で効く」など）— 実機で発動頻度の効果が単調でないことが確認されており（`docs/human/repro/display-score-20260913-frequency.md`。2026-09-13 のモデルはこの非単調性を再現するが、上界の根拠にできるほど式が確定していない）、未確定の単調性に依存する上界は真値以上を保証できない。(3) shortlist を十分大きくして実質厳密に近づける — 速度の利点が消え、近似であること自体は変わらない。(4) 事前計算した結果の埋め込み — 対話的な条件変更（固定・除外・ボード・開花）に対応できない。

## Consequences

### Pros

- 実用速度でリーダーおまかせ探索ができる（数分 → 数十秒）。
- 結果に出る値は常に正確なエンジンの値で、内訳（総合力 6 項目・スコアボーナス 4 項目）と一致する。
- 近似の品質を厳密探索と比べて測れる。落ちた候補があればテストが具体例として示す。

### Cons

- Top N の保証がない。shortlist の上限値が正確な値の 1.0〜1.3 倍に収まる前提が崩れる編成（極端なスコアサポートの組合せなど）では、真の上位が漏れうる。
- 近似の品質は継続的な検証が必要で、テストのフィクスチャが実データの分布を代表しているとは限らない。
- 厳密探索は小規模専用（`EXACT_SEARCH_MAX_EVALUATIONS` = 20 万評価で打ち切る）ため、実データ 73 枚での厳密な突き合わせはできない。

**Update (2026-09-30):** 上の Context の「正規化なしの線形和で shortlist（最小 500 件）」は、ボードを開けたアカウントで**真の上位を落としていた**ので置き換えた。線形和は同時候補の正規化 `max(1, Σp)` を無視するため、青ボードで発動率・頻度を上げたアカウントでは正確な値の 1.3 倍近くまで緩み、上限値の緩い編成が上位 500 件を埋めた。実データでボードを開けたランダムなアカウント 40 通り（プール 18〜23 枚）のうち 9 通りで、おまかせ探索の 1 位が厳密探索の 1 位に届かなかった。利用者に見える症状は「リーダーと水着こよりを固定して探したときより、メンバーを全部おまかせにしたときのユニットスコアが低い」（おまかせの探索空間は固定の探索空間を含むので、探索が厳密なら起こらない）。変更点: (1) 上限を、メンバーごとの発動候補の秒に同じ正規化（`Σ up×p / max(1, Σp)`、スコア UP は最大値）を当てた合計にした（メンバーの追加・削除で発動候補の秒だけ更新するので葉のコストは小さい）。赤の全員のスコアサポートの増分も `(X/100) × E_blue` の E_blue をこの上限で抑える（以前の「E_blue ≤ 100 として X をそのまま採る」は E_blue が 100 を超えうるので上限になっていなかった）。(2) shortlist は最小ヒープで持ち、最小件数を 200,000 に増やした。(3) 正確評価は上限値の高い順に行い、上位 topN 件の正確な値が次の候補の上限値以上になったら打ち切る。shortlist に入らなかった編成の上限値は最下位の上限値以下なので、これで**厳密な上位 topN 件であることを証明**できる（`certified`）。証明できなければ、上限値が topN 件目の正確な値を超える編成をすべて集め直して 2 パス目で評価する（組合せが `CERTIFY_MAX_LEAVES` = 600 万通りを超える探索は 2 パス目を行わず、従来どおり近似）。(4) 上限値が正確な値以上であることは `optimizeShortlist.test.ts` が、`shortlistSize` を 100 に絞って実データの厳密探索と突き合わせて確認する。**代償**: 探索が遅くなった（ボードを開けたアカウントで 34 枚プール 0.3 秒 → 約 2 秒、50 枚 約 2 秒 → 約 6 秒、全 81 枚のおまかせ 約 20 秒 → 約 1 分）。81 枚のおまかせは 2 パス目を行わないので、依然として近似（shortlist が大きいので取りこぼしは起きにくいが証明はしない）。
