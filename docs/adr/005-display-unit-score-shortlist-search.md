# ADR-005: 表示ユニットスコアの探索は二段階の shortlist 評価を採用し、厳密探索を検証用に残す

Date: 2026-09-09

## Status

Accepted

## Decision

通常の UI の編成探索は、上限値で候補を shortlist に絞ってから正確に評価する二段階で行い（`src/engine/optimize.ts`）、この探索を近似と位置づけて、文書でも UI でも「厳密な最適解」とは言わない。品質を測るために、小規模データで全候補を正確に評価する厳密探索（`src/engine/exactSearch.ts`）を検証経路として残し、近似と突き合わせるテスト（`exactSearch.test.ts`）を持つ。

## Context

表示スコアボーナスのモデルが 5 人共通の 200 秒タイムラインになり（[ADR-004](004-total-power-additive-model.md) の Update）、葉ごとの評価が重くなった。★5 73 枚のリーダーおまかせ探索（約 10 億通り）を葉ごとに正確に評価すると 5 分を超え、UI として使えない。総合力の上限 × スコアボーナスの正規化なしの線形和（タイムラインの正規化は必ず値を下げるので上界になる）で上位 `topN × SHORTLIST_FACTOR`（最小 500）件に絞り、その候補だけを正確に評価して並べ直すと、Node 単体の計測でリーダー探索 ≈ 20 秒・固定リーダー ≈ 11 秒に収まった。表示する候補の最終値は必ず正確な計算（`computeStaticPower` + `computeDisplayScoreBonus`）で求めるが、shortlist の段で真の Top N を落とす可能性は 0 ではない。

これで [ADR-003](003-in-browser-typescript-optimizer.md) の「全探索なのでモデル上の厳密な最適解と TOP n を保証できる」は成り立たなくなったので、その部分をこの ADR で置き換える（ブラウザ内 TypeScript・Web Worker・純粋関数の方針は続ける）。将来は、上界が真値以上だと数学的に保証できるものだけを使う安全な branch-and-bound か、十分に速い厳密評価へ移る。

外した案:

- 葉ごとの厳密評価を続ける — 数分待たせる UI は採れない。
- 単調性の仮定（「発動頻度が高いほど必ず強い」「発動率は同じ比率で効く」など）を使う強い枝刈り — 実機で発動頻度の効果が単調でないことが分かっている（`docs/ai/repro/display-score-20260913-frequency.md`。2026-09-13 のモデルはこの非単調性を再現するが、上界の根拠にできるほど式は確定していない）。未確定の単調性に頼る上界は真値以上を保証できない。
- shortlist を十分大きくして実質厳密に近づける — 速さの利点が消え、近似であることも変わらない。
- 事前計算した結果を埋め込む — 対話的な条件変更（固定・除外・ボード・開花）に応えられない。

## Consequences

### Pros

- 実用的な速さでリーダーおまかせ探索ができる（数分 → 数十秒）。
- 結果に出る値は常に正確なエンジンの値で、内訳（総合力 6 項目・スコアボーナス 4 項目）と一致する。
- 近似の品質を厳密探索と比べて測れる。落ちた候補があれば、テストが具体例として示す。

### Cons

- Top N を保証できるのは、末尾の Update の取りこぼし検証（2 パス目）が働く規模に限る。当初の「上限値は正確な値の 1.0〜1.3 倍に収まる」という前提は、青ボードを開けたアカウントで崩れていた。
- 近似の品質は継続して検証する必要があり、テストのフィクスチャが実データの分布を代表しているとは限らない。
- 厳密探索は小規模専用（`EXACT_SEARCH_MAX_EVALUATIONS` = 20 万評価で打ち切る）で、実データ 73 枚での厳密な突き合わせはできない。

**Update (2026-09-30):** 正規化なしの線形和の上限は、青ボードで発動率・頻度を上げたアカウントで正確な値の 1.3 倍近くまで緩み、真の上位を落としていた（症状は「全部おまかせのほうが、メンバーを固定して探すよりユニットスコアが低い」）。そこで上限に同時候補の正規化 `max(1, Σp)` を入れ、shortlist の最小件数を 200,000 に増やし、上限値の高い順に正確に評価して上位 topN 件が厳密だと証明できなければ 2 パス目で集め直す形にした（`certified`。仕組みは `optimize.ts` と `optimizeShortlist.test.ts`）。代償として探索は遅くなり（ボードを開けたアカウントで 34 枚 0.3 秒 → 約 2 秒、50 枚 約 2 秒 → 約 6 秒、全 81 枚のおまかせ 約 20 秒 → 約 1 分）、組合せが `CERTIFY_MAX_LEAVES`（600 万通り）を超える探索は 2 パス目を行わないので、81 枚のおまかせは今も近似である。
