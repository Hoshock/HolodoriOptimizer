# ADR-015: 「最適化」は 1 つの入口で ボード → コネクト → 頻度 を選んで行い、頻度マスも反映する

- Date: 2026-10-08
- Status: Accepted（頻度の段の資材と「最適化順」は [ADR-016](016-true-ranking-proxy-boards.md)、画面の名前と条件の並びは [ADR-017](017-one-ui-for-everyone.md) で置き換え）

[ADR-014](014-board-connect-optimize-frequency-off.md) の「入口は ボードの最適化 と 頻度の最適化 の 2 つ」「頻度の最適化は反映の機能を持たない」を置き換える。ボードの最適化を頻度マス OFF で行うこと、ボード → コネクトの周回、ボードPt・資材・コネクトの明示解放の決定（ADR-012 / ADR-013）は変えない。

## Decision

- **入口は「最適化」の 1 つ**（結果詳細・ユニット詳細の下端）。シートのオプションで「ボードを最適化する」「コネクトを最適化する」「頻度を最適化する」（独立した ON/OFF。既定は全部 ON、最後の 1 つは外せない）と「ユニットのみ変更する」を選ぶ。頻度を選んだときだけ、頻度の選び方（期待値重視 / 理論値重視 / ユニットスコア重視。既定は理論値重視）を選ぶ。旧「発動頻度の最適化」のシートは廃止し、メンバーごとの頻度の固定（固定再探索）はこのシートへ移す。**同日の追記**: シートは**開いただけでは計算しない設定のページ**にし（ユーザー指示「最適化ボタンを押したら設定ページに飛ばすだけ」）、計算は下端の「最適化を実行」だけで行う。結果は ボード / コネクト / 頻度 のタブで見るだけにし、頻度の固定はオプションの中で**頻度マスの数（おまかせ / 0〜3）**で選ぶ（実効 % はコネクトも同じ実行で変わると実行する前に決まらないため）。「ユニットのみ変更する」は**ボードとコネクトの両方**にかかる（ADR-014 でコネクトをユニットのみに固定していたのを、統合前の「コネクトの最適化」と同じく全ホロメンも選べる形へ戻した — 同日ユーザー確認）。
- **順序は ボード（頻度マス OFF）→ コネクト → 頻度**。頻度の段（`src/engine/frequencyStage.ts`）は前の段の盤面から、メンバーごとに頻度マスの部分集合（最大 8 通り）を候補にする。
  - **経路は前の段の盤面から追加のボードPt が最小のもの**（頻度マスは枝の端なので、盤面が決まれば経路は 1 つに決まる）。そのため**頻度マスも推奨として反映する**（ADR-014 の「経路が一意でないので反映しない」は、盤面を先に決めることで解消した）。
  - **ホロメンランクの Pt は超えない**。足りない候補は、その経路を必須にしたまま、そのホロメンの 4 色のマスから「外して失う表示ユニットスコア ÷ 空く Pt」が小さいものを順に外して空ける（色を問わず優先度の低いところから回す — 2026-10-08 ユーザー指示「色全体を見て優先度の高いところに割り振った方がいい」）。空けられない候補は取らない。どの頻度マスにも届かないメンバーは「届かない」と出す。
  - **キューブ・コアキューブは不足してよい**（同ユーザー指示「頻度マスをあける資材分は足が出てもいい」）。余りは前の段の余りから頻度の段の増減を引いた値で、**負は不足**。反映すると余りのリソースは負のまま登録し（`board-resources` は負を読める）、リソースの画面で不足として見せる。シートは本文の先頭に不足を出し、反映の確認に一言を添える。
  - **選び方**: 期待値重視 / 理論値重視はライブ側のモデル（`liveFrequencyOptimizer.ts`）で全組合せから選び、同じ発動頻度・発動率になる候補どうしは表示ユニットスコアの高いほうを採る。ユニットスコア重視は表示ユニットスコアを 1 人ずつ・2 人同時に替えて上がらなくなるまで回す（近似。出発点は頻度マスなしと届く最大の 2 つ）。旧 `frequencyUnitScore.ts`（青だけを差し替える全探索）は、Pt を空けるために他の色も変わる候補を評価できないので廃止した。
- **推奨のユニットスコアは頻度マス込みの値を出す**（2026-09-30 の「頻度の最適化ではユニットスコアの値を出さない」は、最適化の推奨として最終的な値を見たい — 2026-10-07 / 10-08 ユーザー指示 — ので置き換える。表示ユニットスコアの頻度依存は `W_blue` を通る近似で、脚注にそう書く）。「現在」は、頻度を選んだときは登録そのまま（頻度マス込み）、選ばないときは ADR-014 のとおり頻度マスを外した登録の値。
- **頻度を選ばないときは、ボードとコネクトの段は登録の頻度マス（とそこまでの経路）を残したまま行う**（同日の追記。ユーザー指示「頻度を最適化するオプション外すと何でユニットスコアの現在変わるんだ」）。ADR-014 の「頻度マスをすべて OFF にする」は頻度の段を選んだときだけになり、「現在」はいつも登録そのまま（頻度マス込み）の値にする。反映しても登録の頻度マスは外れない。
- **所持リソースは色ごとに考慮を外せる**（同日の追記。ユーザー指示）。外した色はボードの段で制限なしとして選び、余りは登録の値から出す（負 = 不足）。ホロメンランクの Pt は常に守る（ランクは集めて増やせないが、資材は集められる）。
- **結果一覧の「最適化順」**（同日の追記。ユーザー指示「非同期で裏側で真のランキングを計算させておきたい」）: 探索の上位 30 件に同じ計算（頻度はユニットスコア重視）を裏でかけ、そろったら最適化後のユニットスコアの順に並べ替えられる。探索そのものの順位づけは変えない。
- 計算は 1 つの Worker（`optimizeWorker.ts` → `optimizePlan.ts` の `planOptimize`）。結果は（曲, 範囲, 対象, 頻度の選び方, 固定）ごとにキャッシュする。

## Context

2026-10-07〜08 のユーザー指示。ボードの最適化を頻度マス OFF にしたことで、手元で頻度マスまで開けた値（旧計測 1,801,136）よりツールの値（1,722,800）が約 4% 低く見え、最終的なユニットスコアが分からなくなった。ボードの最適化のあとで頻度マスを足す 2 段は、ボードの段が Pt・資材を使い切るので届かない編成が出る（記録の編成は資材内では 1 つも足せず、資材の不足を許すと 1,797,805 — `docs/ai/tmp/pending.md`）。資材の不足は許し、Pt はゲームで超えられないので、他のマスを外して空ける形にした。

## Consequences

### Pros

- 1 回の操作で、ボード・コネクト・頻度まで決めた最終的なユニットスコアの試算と、その盤面の反映ができる。
- Pt が足りないときも、色をまたいで優先度の低いマスから外して頻度マスへ回せる。

### Cons

- 期待値重視 / 理論値重視は P/T/S を見ないので、Pt を空けるために外したマスのぶん表示ユニットスコアが下がる案を選ぶことがある（モデルを混ぜない — `.claude/rules/engine-structure.md`）。
- 頻度の段は前の段の盤面を固定して足すので、ボードと頻度を同時に選ぶ最適とは一致しない（近似）。
- 反映で余りのリソースが負になりうる（不足をユーザーが集めるまで、次の最適化の総量は投入済み + 負の余りになる）。
