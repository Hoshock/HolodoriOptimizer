# ADR-004: 総合力はゲーム画面の内訳を再現する加算モデルで計算し、表示ユニットスコアと実曲期待スコアを分離する

- Date: 2026-09-08
- Status: Accepted

## Decision

ユニット編成の静的な強さは、ゲームのユニット編成画面に表示される「総合力」を再現するモデル（`src/engine/power.ts`）で計算する。総合力 = メンバーパラメータ + 衣装スキル + ホロメンボード効果 + パッシブスキル + メモリー効果 + メンバー強化ボーナス の 6 項目を、素のメンバーパラメータ（開花後・ホロメンボード前の本体値）を基準に別々に求めて加算し、割合効果の端数は切り上げる。探索の順位づけは 総合力 × 実曲期待値の倍率（アクティブ・SP・黄・イベント — `src/engine/live.ts`）とし、ゲームの表示「ユニットスコア」（総合力 × (1 + スコアボーナス) × 固定係数）と実曲の期待スコアは別モデルとして型・関数・UI で混ぜない。実機値に合わせるための場当たりの補正定数は入れず、一致しない項目は「どの段階から何点ずれるか」をテストとドキュメントに明記する。

## Context

ADR-003 が採用したコミュニティ解析モデル（赤 → パッシブ → 衣装を順に掛ける連鎖乗算、基準はカード詳細値）は、2026-09-08 のユーザー実機観測（同じメンバー 5 枚でリーダー 2 通りの総合力内訳 6 項目・メンバー別表示値・青ボード変更 2 例）と合わなかった。実機では各項目が独立に計算されて加算され、衣装 +50% の効果はカード詳細値の合計でなく素値合計の 50% に一致し、パッシブ「◯◯2人の」は条件に合う全員でなく対象パラメータの高い 2 人にだけ効いていた（パッシブ 20340・メモリー 7359・赤 41190・強化ボーナス 8709 / 7161 が加算モデルで完全一致）。却下した代替案: (1) 連鎖乗算モデルの維持 — 実機と構造が違い、順位も歪む。(2) 実機値に合わせる補正係数の導入 — ユーザーが明示的に禁止（構造の理解より当てはめになる）。(3) 表示ユニットスコアの係数 K ≈ 2.03734 の定数化 — スコアボーナス 4 項目（アクティブ 77.0% / ボード / パッシブ / SP 46.0%）の内部式が未確定で、係数の桁・丸めも未確定のため、総合力までを再現し表示ユニットスコアは出さない。(4) 実曲期待値モデル（`live.ts`）の削除 — 曲別最適化の目的（実際の楽曲で高得点を出す編成）は表示ユニットスコアの再現とは別なので残す。

## Consequences

### Pros

- ゲーム画面の値と直接突き合わせられるので、モデルの検証と修正が実測ベースで進む（ゴールデンテスト `src/engine/power.test.ts`）。
- 探索の高速評価器と詳細表示が同じ中核関数（`passiveParamBonus` / `staticPowerTotals`）を通り、乖離がテストで検出できる。
- メモリー・メンバー強化ボーナスをユーザー入力（Step 0）で受け、アカウントの現状に合った総合力を出せる。

### Cons

- 切り上げの単位（メンバー × パラメータか合計か）は最も合う仮説で、0/1凸の素値の復元（2凸値 ÷ 1.1）に ±1 の誤差があるため合計で数点ずれる（pending.md「赤割合効果の丸め単位」）。
- 表示ユニットスコアとスコアボーナスは未再現で、ゲーム画面の大きい数字（例 1,660,900）とツールの数字は直接比べられない（表示ユニットスコアはその後 docs/human/display-score.md で外側の式まで確定。内部式は pending.md「5カテゴリの内部式」）。
- 加算モデルは葉ごとの計算量が増え（切り上げがメンバー × パラメータ単位）、探索は以前より遅い。

**Update (2026-09-08):** 表示ユニットスコアの係数 K を定数化しない方針（却下案 3）は、同日のユーザー指示「多少ズレてもいいから別エージェントが言ってた仮定で実装して」で変更した。`src/engine/displayScore.ts` に引き継ぎメモの仮定（200 秒の仮想タイムライン・発動確率 55/45/35・青の乗除・スコアサポート倍率・SP の単純式・K = 2.03734）をそのまま実装し、実機とのずれを `displayScore.test.ts` に明記して「試算」として表示する。同日の追加指示「結果の値は最終的なユニットスコア値にしろ」で、結果の値と探索の順位づけもこのユニットスコア（曲を指定したときは黄・イベントのスコアボーナスを掛ける）に切り替えた。曲長に基づく実曲期待値（`live.ts`）は内訳として残すが順位づけには使わない。総合力との分離は変わらない。

**Update (2026-09-08、2 回目):** 表示ユニットスコアのモデルは同日の 2 回目の引き継ぎ（実機 20 ケース）で `src/engine/displayScore.ts` を作り直し、係数 K = 2.03734 は ceil で 20 ケース全一致したため「確定」として持つ（却下案 3 の懸念だった桁・丸めは解消）。スコアボーナスは 5 人共通の 200 秒タイムライン（発動確率 55/46/37 で重みづけ）で計算し、アクティブ ±0.1・SP ±0.5 まで再現、青ボードとパッシブのスコアサポートは仮説のまま（合計 −2.6〜+0.9pt）。信頼度の区分と残るずれはテストとファイル冒頭に明記する（場当たりの補正定数は入れない方針は変えない）。探索は、葉ごとのタイムライン評価が 73 枚で 5 分を超えたため、総合力の上限 × スコアボーナスの線形上限（正規化は必ず値を下げる）で上位 shortlist（topN × 50、最小 500）を集め、その候補だけを正確に評価して並べ直す近似に変えた（`optimize.ts`）。上限値は正確な値の 1.0〜1.3 倍なので真の上位が漏れる可能性はごく小さいが 0 ではなく、詳細表示の値は常に正確。順位づけの値 = ユニットスコア（試算）× (1 + 黄) × (1 + イベント)。
