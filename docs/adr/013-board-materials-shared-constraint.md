# ADR-013: キューブ・コアキューブは「ホロメンボードの最適化」だけの、アカウント共有の資材制約にする

- Date: 2026-10-07
- Status: Accepted

[ADR-012](012-board-points-rank-model.md) の「各色キューブ・コアキューブは無限扱い」を、ホロメンボードの最適化に限って置き換える（ADR-012 のほかの決定 — ボードPt の予算・コネクトの明示解放・Pt 最小の手動の経路 — は変えない）。

## Decision

- **マス別のキューブ・コアキューブの消費量を外部 master 由来の表として持つ**（`src/data/boardMaterials.ts`。HolodoriDB コミット `e83a4eb03baf974c434eb0ddfa1cd1d2385dad11` の `SkillTreeNode.json` consumptions。実機未確認）。ボードPt から推測しない（R-034 と R-050 は同じ 4 Pt で資材が違う）。非中心のコネクトマスは 0 / 0。ユーザー入力の「余り」（`board-resources`）とは混ぜない。
- **資材は色 × キューブ/コアキューブの 8 種で、アカウント全体で共有する**（ホロメンごとの別財布にしない。色をまたぐ変換はない）。ボードPt はこれまでどおりホロメンごと。
- **「リソース」の登録値は、いまのボードを開けた上での余り**（総所持量ではない）。再配分できる総量 = **いまのボードへ投入済みの資材（解放済みマスから逆算）+ 余り**。マスを外すと素材は全額返る（ゲーム仕様）ので、投入済みの分は再配分できる。`scope = unit` は、変えてよいホロメン（リーダー・メンバー）の投入済み分 + 余りだけを再配分し、ユニット外が使っている分は回収しない。`scope = all` は全ホロメンの投入済み分 + 余り。余りが未登録（null）の項目は制限なし、0 は「余りが 0 個」。
- **制約は「ホロメンボードの最適化」だけ**。手動でボードを開ける操作（通常マス・コネクト・すべて解放）は資材で制限せず、手動の編集で余りを自動で増減もしない（余りはユーザーがゲームの実際の値を登録する入力）。
- **最適化は、ホロメンのボードPt の残りと共有の資材の残りの両方に収まる候補だけを採る**。探索の出発点（必須のマスだけ / 登録している状態）ごとに資材の残りを数え直す（登録から出発する run は余り、必須だけから出発する run は回収した分も使える）。
- **資材に上限がある色では、Pt 最小の経路だけを見ない**。実グラフに、Pt 最小の経路では資材が足りず、Pt が少し多くても資材が少なく済む別の経路でないと届かないターゲットがある（緑 G-018 / G-021: +3 Pt・cube +200 で core 50 を避ける）。`BoardGraph.planUnlockRoutes` が Pt・cube・core の非劣な経路をすべて返し、予算に収まるものを評価する。手動の `planUnlock`（Pt 最小）は変えない。
- **推奨を反映するときは、ボード・コネクトの解放・余りのリソースを同じ推奨としてまとめて登録する**（`BoardPlanResult.remainingAfter` = 総量 − 推奨でのアカウント全体の使用量。負にしない。総量を増減させない）。結果のキャッシュのキーに余りの登録値を含める。

## Context

2026-10-07 のユーザー指示。ゲームではマスを開けるのにボードPt に加えて色ごとのキューブ・コアキューブが要り（2026-10-04 報告）、消費量の表が master から揃った。ユーザー構想は「いまの解放状態から必要な量を逆算し、余りも含めて全体で最適化する」。

## Consequences

### Pros

- 余りの個数を前提にした、実際に開けられる範囲の推奨が出る。ユーザーの余りで試すと、資材無制限の推奨より低い（ユニット外も含めて全て変更の 1 回目で 1,915,524 → 1,702,541 の例。ツール上の計算）。
- 手動操作とデータの保存形式は変わらない。

### Cons

- 資材の表は外部 master 由来で実機未確認。余りが実際の所持と違えば結果も合わない。
- 資材を絞った探索も貪欲法で、最大を保証しない（資材を絞った方が制限なしより高く出る例がある — `pending.md` 8）。
- キューブ・コアキューブ以外（ピース・クリスタル・ホロゴールド・Dream Rank 条件）は引き続き制約にしていない。
