# ADR-012: ホロメンボードは「ホロメンランク → ボードPt の予算」と「コネクトの明示解放」で扱う

- Date: 2026-10-04
- Status: Accepted

## Decision

- 各ホロメンに**ホロメンランク（1〜50。任意登録）**を持たせ、ランクまでに獲得した**累積ホロメンボードPt**を、そのホロメンの 4 色のボード全体で共有する**予算**にする。制約資源として扱うのはこのボードPt だけ（ピース・クリスタル・各色キューブ・コアキューブ・ホロゴールドは無限扱い。Dream Rank は常に 30 以上と仮定し、マスの Dream Rank 条件は無視する）。
- **ランク未登録は「ボードPt の制限なし」**（従来どおり）。0 を未登録の代わりに使わない。
- 通常マスの必要Pt は 1〜6（マス ID → cost の表を `src/data/boardPoints.ts` に 1 か所だけ置く）。**赤 / 青 / 黄のコネクトマスは各 1 Pt**、中心は 0 Pt で最初から解放済み。
- **コネクトマスは通常マスと同じく明示的な解放状態を持つ**（`src/storage/boardConnects.ts`）。**コネクト効果の配置（`connect-placements`）とは別の状態**で、「解放済みで配置なし」「直前まで解放して未解放」「解放済み・配置あり」の 3 状態を区別する。**「未解放なのに配置あり」は保存しない**（解放が外れると配置も外す — `src/composables/useBoards.ts`）。旧実装の「コネクトは常に通れる通路で、先のマスが解放されていれば解放扱い」という推定は撤去した。
- 自動で途中経路を開くときは**追加で必要なボードPt が最小の経路**を選ぶ（マス数ではなく Pt。Dijkstra、同コストは ID 順で固定）。コネクトを横断する経路ではコネクトの 1 Pt も合算し、コネクトも解放する。
- ランク登録済みで予算が足りない解放は、**操作全体を拒否して何も変えない**（途中までは開けない）。解除は常にできる。すでに予算を超えている登録は**自動では削除せず**、超過を表示する（新規の解放は不可・解除は可）。
- **ホロメンボードの最適化**（`src/engine/boardOptimize.ts`）: 固定した編成に対し、ランクの予算の範囲で**表示ユニットスコア**（コネクトの最適化と同じ `teamEvaluator` の経路）が高くなる解放マスを選ぶ。コネクトの配置は変えず、配置のあるコネクトは必ず解放済み（1 Pt を予算に含む）。選び方は**近似**（ターゲットのマスに必要な未解放の経路一式を 1 つの解放プランとして、増分 ÷ 追加Pt（と増分）で遅延評価の貪欲法）で、最大を保証しない。**ランク未登録でもスコアに効かないマスは開けない**（効くマスと、そこへ届く経路・コネクトだけ）。推奨は表の行から**ボードの図（追加 = そのマスの色が点滅、解除 = 丸の右上から左下への斜線）**で確かめて反映する。

## Context

2026-10-04 のユーザー指示。実機ではホロメンごとにボードを開ける量がホロメンランクで決まり、コネクトマスの直前まで開けてもコネクト自身は勝手に開かない。ツールは「どこまででも開けられる」前提で、コネクトは常に通れる通路として扱っていたため、現在のランクで実現できる範囲のボードや、ランクに合わせたボードの最適化を扱えなかった。

数値（ランクごとの獲得Pt・マスの必要Pt・G-025 の存在）は HolodoriDB の公開 master 差分（コミット `e83a4eb03baf974c434eb0ddfa1cd1d2385dad11` の `CharacterLevel.json` / `SkillTreeNode.json` / `SkillTreeNodePosition.json` / `SkillTreePoint.json` / `LangSkillTreePoint_Jpn.json`）から取った**外部解析データ（external master-derived）**で、**実機の目視確認済みではない**（ADR-009 の「外部解析」の段）。同じマス ID が複数の tree-model にあってもボードPt が食い違うものはなかった。

## Consequences

### Pros

- 現在のランクで実現可能な範囲に限定してボードを入力・最適化できる。
- コネクトの 3 状態を区別でき、解放マス数（通常マス + 解放済みのコネクト。最大 150 + 3 = 153）・使用Pt（最大 453）が推定なしで正確に数えられる。
- 経路選択が Pt 基準になり、マスごとに違うコストでも最小の追加Pt で開けられる。

### Cons

- ボードPt・ランクの表は外部マスタ由来で未確認。実機と食い違えば表だけ直す（正典は 1 か所）。
- 旧データにはコネクトの解放状態がないので、**初回の読み込みで推定して明示保存する**（A. コネクトを通らないと届かないマスが解放済み → 解放済み / B. 配置あり → 解放済み / C. 直前までで配置なし → 未解放）。C は実機では解放済みだった可能性があり、旧データからは判断できない（勝手に 1 Pt 消費した状態にしないほうを採った）。
- ボードの最適化は近似。貪欲法の取りこぼしを避けるため「登録している状態から出発した結果」「ゼロから選んだ結果」を比べ、登録を下回るときは登録を返すが、厳密な最適の保証はない。
- 発動頻度の最適化（`liveFrequencyOptimizer.ts`）は青のコネクトを**解放済みとして扱う**（頻度マスの個数を比べる別の責務。コネクトの解放はボードの最適化が持つ）。
