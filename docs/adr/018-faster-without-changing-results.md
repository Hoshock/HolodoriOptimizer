# ADR-018: 計算は値を変えずに速くし、重い計算は Worker を何本か立てて分担する

- Date: 2026-10-08
- Status: Accepted

[ADR-003](003-in-browser-typescript-optimizer.md)(ブラウザ内の TypeScript で全探索)と [ADR-005](005-display-unit-score-shortlist-search.md)(shortlist + 厳密検証)、[ADR-016](016-true-ranking-proxy-boards.md)(「組み直すと」の 3 段)の計算の中身は変えない。速くするための変更で、探索・組み直しプラン・「組み直すと」の結果(候補・並び・推奨の盤面と配置・スコア)は 1 点も変えない。

## Decision

- **組み直しプランの評価は覚えた値を使い回す**(`request.ts` の `createTeamScorer`)。最適化の各段は編成 1 つのユニットスコアを数千回測る。全ホロメンにまたがる量(緑・黄)は鍵(依頼の順のホロメン・その色のマス・配置の中身)が前と同じなら作り直さず、変わったときは探索と同じ関数を同じ並びで呼ぶ。赤はリーダーのホロメンの分だけ作る。カードの解決と評価の結果は入力が同じなら使い回し、同じ盤面を 2 回測らない。6 枚が決まった編成の評価は探索の入口を通さず、探索の正確な評価と同じ `scoreTeam` を直接呼ぶ。カードの数値表現(発動候補の秒の表など)はカードごとに覚える。覚えた値は評価器ごと捨て、保存はしない。
- **さがすの総当たりは、葉ごとにまず全リーダーグループをまとめた上限 1 つで足切りする**。各成分をグループの最大で取るので、どのグループの上限よりも小さくならない(足切りの結果は同じ)。
- **さがすは Worker を何本か立てて分担する**(`useOptimizer` → `worker.ts` / `searchWorkerHandler.ts`)。組合せの 1 枚目のプール内の添字の余りで分け、分担ごとに上限値の上位を集める。全体の上位はそれらの和に必ず入るので、UI が全体の上位を選んで分担ごとの件数を返し、各 Worker が自分の分を正確に評価し、UI がまとめる。取りこぼしの検証(2 パス目)も同じ手順。Worker から UI へは並べ替えの鍵(上限値・番号)だけを渡し、候補の中身は Worker が持つ。
  - **同点の決め方を、見つけた順から番号に替えた**。上限値が同じ候補は「組合せの辞書順の番号 × クラス数 + クラス」の小さい順、結果の並びは順位づけの値 → 上限値 → 番号 → クラスの中のリーダーの順(`compareRanked`)。分担すると見つける順が本数で変わるので、見つけた順で決めていた同点(shortlist の境目と、同じ値の候補の並び)を決め直した。
- **「組み直すと」の 3 段も Worker を何本か立てて配る**(`useTrueRanking` → `rankingWorker.ts`)。見込みのボード・見込みでの探索・最適化は、どれも互いに独立した仕事の集まり。仕事は 1 件ずつ空いた Worker へ渡し、段の切れ目で全部の結果を仕事の並びの順にまとめる。
- **Worker の本数は端末のコア数 − 1**(画面の描画に 1 つ残す。分からなければ 1 本、上限 6 — `workerCount`)。

## Context

2026-10-08 にユーザーのアカウント出力(`reported`)と 2026-09-15 のスナップショットで測ると、組み直しプラン 1 回が約 3 秒、「組み直すと」が約 13 分(見込みのボード 84 件 4.7 分・見込みでの探索 48 秒・最適化 126 件 7.5 分)、さがすの全カードが約 3.3 分だった(このリポジトリの開発環境の 1 コア。ツール上の計算)。

時間の大半は計算のやり直しだった。組み直しプランの 1 回の評価の約半分は、変えていない全ホロメンのコネクト倍率・緑・赤・黄の作り直しで、評価の約 3 割はすでに測った盤面の測り直しだった。全カードのさがすは、約 24 億通りの組合せを 1 つずつ見る部分が約 7 割、候補の正確な評価が約 3 割(評価のたびにカードの表を作り直していた)。

WASM への書き直しは採らなかった。時間の大半は同じ計算のやり直しで、言語を変えても残る。書き直す量に比べて得が小さい。

## Consequences

### Pros

- 結果を変えずに速くなる(2026-10-08、同じ環境で変更の前後を比べた。4 コアで Worker は 3 本):
  - 組み直しプラン(1 本の計算): 4 通りの設定 × 3 編成で、推奨の盤面・配置・スコアの全体が変更前と一致し、合計 36.1 秒 → 10.9 秒(既定の設定は約 3 秒 → 約 0.8 秒)。
  - さがす: 4 通りの条件と全カードで、上位 30 件の候補と並びが変更前と一致した。ブラウザの実測は「いまの育成で」2.3 秒 → 1.3 秒。
  - 「組み直すと」: 変更前は開発環境の 1 コアで約 13 分、変更後はブラウザの実測(Worker 3 本)で 1 分 36 秒。
- 本数を変えても同じ結果になることをテストで固定した(`searchPartition.test.ts`・`useOptimizer.test.ts`・`useTrueRanking.test.ts`。覚えた値を使う評価は `teamScorer.test.ts` で 6 枠固定の `runOptimize` と突き合わせる)。

### Cons

- Worker ごとにデータと shortlist を持つので、本数ぶんメモリを使う(上限 6 本)。
- さがすの手順(数える → 上位を選ぶ → 分担ごとに評価してまとめる → 要れば 2 パス目)が、`optimize.ts` の `searchInProcess` と `useOptimizer` の 2 か所にある。片方を変えたらもう片方も変え、テストで 1 本の結果と突き合わせる。
- 2 コア以下の端末では Worker が 1 本で、並列の分は速くならない。iPhone の Safari で実際に何本が同時に動くかは未確認。
- 同点の候補の並びは、変更前と違うことがありうる(見つけた順で決めていたものを番号で決め直したため)。上の比較では差は出なかった。
