# ADR-007: 発動頻度マスの最適化は表示ユニットスコアと別の「ライブ・アクティブ」エンジンで行う

- Date: 2026-09-09
- Status: Superseded by [ADR-015](015-optimize-with-frequency-stage.md)（頻度の最適化は最適化の最後の段になり、専用の画面は廃止。ライブ側のモデルを表示側と分ける方針と目的関数の定義はそのまま `liveFrequencyOptimizer.ts` が持ち、規則は `.claude/rules/engine-structure.md`）

## Decision

「青ホロメンボードのアクティブスキル発動頻度マスを誰に何個開けるべきか」を答える機能は、表示ユニットスコアのエンジン（`src/engine/power.ts` + `src/engine/displayScore.ts`）とは**別のモデル**として `src/engine/liveSkillTimeline.ts`（実数時刻の発動タイムライン）と `src/engine/liveFrequencyOptimizer.ts`（目的関数と全探索）に置く。依存の向きは片方向で、この 2 ファイルは `displayScore.ts` を参照しない（基礎発動確率も共有せず `LIVE_ACTIVE_PROBABILITY` として独自に持つ）。

**目的関数はユーザーに見せる 2 つだけ**（`FrequencyOptimizationMode`）。どちらも同じセグメント列（発動候補の集合が一定な区間）の上で、区間ごとの値を時間で積分して評価区間長で割る:

- `"expected-score"`（期待値重視）: 各スキルの発動確率を考慮し、**実際に発動した中で最も高いスコア UP だけが有効**という前提の期待値（`segmentExpectedScore`）。時間平均は `averageExpectedActiveScorePercent`
- `"perfect-score"`（理論最大重視）: **発動抽選がすべて成功した前提**で、その区間に有効になる最大のスコア UP（`segmentPerfectScore`）。時間平均は `averagePerfectActivationScorePercent`

期待カバレッジ・構造カバレッジ・空白（合計 / 最長）は**補助指標**として計算・表示するだけで、おすすめを決める第 3・第 4 のモードにはしない。tie-break は「主目的関数 → 追加解放数が少ない → 期待カバレッジが大きい → 最大空白が短い → 発動頻度マスの合計が少ない」の順で、補助指標が主目的関数より優先されることはない（順序の唯一の定義は `compareFrequencyPlans`）。

モデルの仮説（どちらもライブ最適化専用で、表示側とは別物）:

- 発動頻度 +f% → 周期 ÷ (1 + f/100)（`effectiveInterval`）。整数秒への丸め・量子化は入れない
- 発動率 +r% → min(1, 発動確率 × (1 + r/100))（`effectiveActivationProbability`）。式は表示側（`blueActivationProbability`）と同じ形になったが（2026-09-13 の Update）、**定数も関数も共有しない** — 評価対象（実ライブの発動 vs 表示欄の評価器）が別で、片方の反証でもう片方を動かさないため
- 基礎発動確率は 低 37 / 中 46 / 高 55%【外部情報】。同じ値だが定数は共有しない
- ライフ・コンボ条件つきのスコア UP は満たされているとみなす（編成条件はこの編成で判定する）
- リーダー枠のアクティブは発動しない。ホロメンボードはマスの表記値の合計で、コネクトマスの増幅は含まない（未確認）

探索は「各メンバーの合法な発動頻度候補の直積」の全探索（近似・greedy なし）。候補は `[0, 4, 8, 12]%` を仮定せず、`src/data/blueBoard.ts` の連結性（`unlockNode` の 0-1 BFS）で**現在の解放マスから実際に到達できる状態**を列挙する — 頻度マスまでの経路も解放されるので追加解放数と発動率 UP が候補ごとに変わる（`enumerateFrequencyCandidates`）。解放は戻せないので候補は必ず現在の状態を含む。

評価区間は曲を指定していればその演奏時間、指定がなければ UI で秒数を指定でき、既定は**全曲の演奏時間の中央値**（`medianSongDurationSeconds`。データ由来で、ゲーム仕様の定数ではない）。180 秒・200 秒のような値をゲーム仕様としてハードコードしない。

「省素材案」（最高値との差が 0.1 ポイント以内の案のうち追加解放数が最小のもの）は**ゲーム仕様ではなくこのツールの推薦ポリシー**として `FREQUENCY_RECOMMEND_POLICY` に置き、UI でもその旨を脚注に書く。

## Context

ADR-006 で「実際に曲をプレイしたときのライブスコアは未解明・未実装」と決め、順位づけは編成画面の表示ユニットスコアの再現に一本化した。一方でユーザーの実際の意思決定には「青ボードの発動頻度マスを開ける価値があるか」という別種の問いがあり、これは**編成画面の数字を上げる問題ではなく、ライブ中の発動タイミングの問題**である。表示スコアボーナスのモデルでこれに答えるのは不適切で、ホロメンボード効果欄・パッシブ欄の算出式は未解明の帰属モデル（当時の pending「5カテゴリの内部式」。現在は pending.md「`W_blue` の発動頻度側の正規化」）であり、実機でも発動頻度 0 → 4 → 8 → 12% でボード欄が 4.6 → 4.7 → 4.4 → 5.0 と単調でない。未解明の近似式を目的関数にすると、モデルの粗さがそのまま「何マス開けるべきか」の答えを歪める。

主指標を 2 つに絞ったのは、カバレッジ系の指標がスコア UP の大きさを見ないため（「+20% で 100% カバー」が「+150% で 70% カバー」に勝ってしまう）。「上振れを見る」用途にはカバレッジではなく理論最大スコア（`perfectActivationScoreIntegral`）を使う。

却下した代替案: (1) `displayScore.ts` のボード欄の式を最大化する — 未解明の近似を最適化することになり、実機の非単調性も再現できない。(2) 各人 `[0, 4, 8, 12]%` の固定値だけで探索する — 連結性の制約（頻度マスに届くまでの経路と、そこに含まれる発動率マス）を無視するので追加コストの比較にならない。(3) 期待カバレッジ・構造カバレッジも最適化モードとして並べる — 主指標が 4 つになって選べず、スコア UP を見ない指標が最適解を歪める。(4) 実ライブスコアのエンジンとして作る — 譜面・コンボ・SP の発動位置が未解明なので、いまはアクティブスキルの発動タイミングだけに責務を限る。

## Consequences

### Pros

- 「未解明の表示スコアボーナスの逆解析」と「発動頻度の投資判断」が別のファイル・別の型・別の定数に分かれ、片方の仮説を差し替えても他方が動かない。
- 候補列挙がボードの連結性に基づくので、「追加で何マス必要か」が実際の育成コストとして読める（頻度 1 マス目は経路ぶんで 6〜11 マス必要になることが多い）。
- 目的関数が 2 つで、平均（期待値）と上振れ（理論最大）という意味の違いがユーザーに説明できる。実データでも両者の答えが分かれる（検算した編成では フブキ 3 マス / ロボ子 2 マス と フブキ 2 マス / ロボ子 3 マス に分かれた）。
- 全探索なのでモデル上の厳密な最適解で、Python の独立実装との突き合わせで数値まで一致を確認できた。

### Cons

- 発動頻度・発動率の反映式と基礎発動確率は仮説のままで、実機のタイムスタンプで検証していない（実機で確認する手段が乏しい）。値の意味は「試算」の域を出ない。
- 表示スコアボーナス側と発動確率の定数・反映式が二重管理になる（意図的な分離だが、実機で式が判明したときは両方を見直す必要がある）。
- 評価区間の長さで結果が変わるため、曲を指定しないときの答えは「中央値の曲での答え」にすぎない。
- コネクトマスの増幅を含まないので、コネクトの内容が判明したら候補の実効値が変わる。

**Update (2026-09-10):** Decision の「解放は戻せないので候補は必ず現在の状態を含む」は前提が誤りで、候補は発動頻度マス 3 つ（葉）の ON / OFF の全組合せにした（現在 12% でも 0 / 4 / 8% を比べる）。コストは「新しく開けるマス数」のまま（2026-09-16 に「外すと素材は返る」が実機で分かり、この値はこれから払う素材の上限になった）。

**Update (2026-09-13):** 表示側の発動率を乗算型へ変えた結果、式の形はライブ側と同じになったが、モジュール分離（`live*.ts` から `displayScore.ts` を import しない）と定数の非共有は維持する — 片方の反証でもう片方を動かさないため。

**Update (2026-09-14):** Decision の「ホロメンボードはマスの表記値の合計で、コネクトマスの増幅は含まない」は現在のものではない。現在の状態と全候補に同じ倍率表（`src/data/connect.ts`）を当てる（モジュール分離は維持）。

**Update (2026-09-16):** 3 つ目の目的関数「ユニットスコア重視」（表示ユニットスコアを最大にする）を足した。候補の畳み方は「解放マスの集合が同じ」だけ — 同じ +4% でも経路で拾う P/T/S が違う（ライブ側は P/T/S を見ないので畳み方が違い、モデルを混ぜない理由がもう 1 つ増えた）。この 3 つ目と専用の画面はその後 [ADR-015](015-optimize-with-frequency-stage.md) の頻度の段に置き換わった。

**Update (2026-10-10):** 補助指標（期待カバレッジ・最大空白）とスコアUP は画面に出さなくなった（組み直しプランの発動頻度のタブ — ユーザー指示「期待カバレッジなどの情報はここには出さない」）。計算と tie-break（`compareFrequencyPlans`）での使い方は変えない。
