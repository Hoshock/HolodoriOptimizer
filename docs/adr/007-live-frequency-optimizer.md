# ADR-007: 発動頻度マスの最適化は表示ユニットスコアと別の「ライブ・アクティブ」エンジンで行う

Date: 2026-09-09

## Status

Superseded by [ADR-015](015-optimize-with-frequency-stage.md)（頻度の最適化は最適化の最後の段になり、専用の画面は廃止。ライブ側のモデルを表示側と分ける方針と目的関数の定義はそのまま `liveFrequencyOptimizer.ts` が持ち、規則は `.claude/skills/engine-structure/`）

## Decision

「青ホロメンボードの発動頻度マスを誰に何個開けるか」は、表示ユニットスコアのエンジン（`power.ts` + `displayScore.ts`）とは別のモデル（`src/engine/liveSkillTimeline.ts` の発動タイムラインと `src/engine/liveFrequencyOptimizer.ts` の目的関数・全探索）で、ボードの連結性から到達できる候補を全探索して答える。目的関数はユーザーに見せる「期待値重視」（`expected-score`）と「理論最大重視」（`perfect-score`）の 2 つだけにし、カバレッジ・空白は補助指標にとどめる。

## Context

[ADR-006](006-actual-live-score-separate-engine.md) で実ライブスコアは未解明・未実装とし、順位づけを表示ユニットスコアの再現に一本化した。一方で「発動頻度マスを開ける価値があるか」は、編成画面の数字を上げる問題ではなく、ライブ中の発動タイミングの問題である。表示スコアボーナスのボード欄・パッシブ欄の式は未解明の帰属モデルで、実機でも頻度 0 → 4 → 8 → 12% でボード欄が 4.6 → 4.7 → 4.4 → 5.0 と単調でない。未解明の近似式を目的関数にすると、モデルの粗さが「何マス開けるか」の答えをそのまま歪める。そこで依存は片方向にし、ライブ側の 2 ファイルは `displayScore.ts` を参照せず、基礎発動確率も `LIVE_ACTIVE_PROBABILITY` として別に持つ。

ライブ側の仮説（表示側とは別物）: 発動頻度 +f% は 周期 ÷ (1 + f/100)、発動率 +r% は min(1, 発動確率 × (1 + r/100))、基礎発動確率は 低 37 / 中 46 / 高 55%【外部情報】。ライフ・コンボ条件つきのスコア UP は満たされているとみなし、リーダー枠のアクティブは発動せず、ボードはマスの表記値の合計でコネクトの増幅は含めない（未確認）。

2 つの目的関数は、発動候補の集合が一定な区間ごとの値を時間で積分し、評価区間の長さで割る。期待値重視は、各スキルの発動確率を考え、実際に発動した中で最も高いスコア UP だけが効くとした期待値。理論最大重視は、発動抽選がすべて成功したとして、その区間で効く最大のスコア UP。カバレッジ系を主目的にしないのはスコア UP の大きさを見ないからで（「+20% で 100% カバー」が「+150% で 70% カバー」に勝ってしまう）、上振れを見たいときは理論最大を使う。補助指標は tie-break でも主目的関数より先に見ない（順序の定義は `compareFrequencyPlans`）。

候補（`src/data/blueBoard.ts` の連結性で現在の解放マスから到達できる状態）は頻度マスへ届くまでの経路も開くので、追加で開けるマス数と発動率 UP が候補ごとに変わる。解放は戻せないので、候補は必ず現在の状態を含む。評価区間は、曲を指定すればその演奏時間、指定がなければ UI で秒数を決められ、既定は全曲の演奏時間の中央値（データ由来で、ゲーム仕様の定数ではない）とし、180 秒・200 秒のような値をゲーム仕様としてハードコードしない。「省素材案」（最高値との差が 0.1 ポイント以内で、追加の解放が最も少ない案）はゲーム仕様ではなくこのツールの推薦ポリシーとして `FREQUENCY_RECOMMEND_POLICY` に置き、UI の脚注にもそう書く。

外した案:

- `displayScore.ts` のボード欄の式を最大化する — 未解明の近似を最適化することになり、実機の非単調性も再現できない。
- 各人 `[0, 4, 8, 12]%` の固定値だけで探す — 頻度マスに届くまでの経路（とそこに含まれる発動率マス）を無視するので、追加コストを比べられない。
- 期待カバレッジ・構造カバレッジも最適化モードとして並べる — 主指標が 4 つになって選べず、スコア UP を見ない指標が最適解を歪める。
- 実ライブスコアのエンジンとして作る — 譜面・コンボ・SP の発動位置が未解明なので、いまはアクティブの発動タイミングだけに責務を限る。

## Consequences

### Pros

- 未解明の表示スコアボーナスの逆解析と、発動頻度への投資判断が、別のファイル・型・定数に分かれる。片方の仮説を差し替えても他方は動かない。
- 候補をボードの連結性から作るので、「追加で何マス要るか」を実際の育成コストとして読める（頻度の 1 マス目は経路ぶんで 6〜11 マス要ることが多い）。
- 平均（期待値）と上振れ（理論最大）という意味の違いをユーザーに説明できる。実データでも答えが分かれる（検算した編成では フブキ 3 マス / ロボ子 2 マス と フブキ 2 マス / ロボ子 3 マス）。
- 全探索なのでモデル上の厳密な最適解で、Python の独立実装と数値まで一致した。

### Cons

- 反映式と基礎発動確率は仮説のままで、実機のタイムスタンプで検証していない（確かめる手段が乏しい）。値は試算の域を出ない。
- 表示側と発動確率の定数・反映式が二重管理になる（意図した分離だが、実機で式が分かったら両方を見直す）。
- 評価区間の長さで結果が変わり、曲を指定しないときの答えは「中央値の曲での答え」にすぎない。
- コネクトの増幅を含まないので、コネクトの内容が分かると候補の実効値が変わる。

**Update (2026-09-10):** 「解放は戻せないので候補は必ず現在の状態を含む」の前提は誤りで、候補は発動頻度マス 3 つ（葉）の ON / OFF の全組合せにした。コストは「新しく開けるマス数」のままで、2026-09-16 に外すと素材が返ると実機で分かってからは、これから払う素材の上限という意味になった。

**Update (2026-09-13):** 表示側の発動率も乗算型になり、式の形はライブ側と同じになったが、モジュールの分離と定数の非共有は続ける（片方の反証でもう片方を動かさないため）。

**Update (2026-09-13):** Context と外した案に書いた「実機の非単調性(4.6 → 4.7 → 4.4 → 5.0)は再現できない」は撤回した。同時候補の正規化 `max(1, Σp)` と projective 配分を合わせると、自由係数なしで再現できる(`docs/ai/display-score.md`)。ライブ側を表示側と分ける決定は変えない。

**Update (2026-09-14):** 「ボードはコネクトの増幅を含めない」は変わり、現在の状態と全候補に同じ倍率表（`src/data/connect.ts`）を当てる。モジュールの分離は続ける。

**Update (2026-09-16):** 3 つ目の目的関数「ユニットスコア重視」（表示ユニットスコアを最大にする）を足した。候補を畳んでよいのは解放マスの集合が同じときだけで（同じ +4% でも経路で拾う P/T/S が違い、P/T/S を見ないライブ側とは畳み方が違う）、この 3 つ目と専用の画面はその後 [ADR-015](015-optimize-with-frequency-stage.md) の頻度の段に置き換わった。
