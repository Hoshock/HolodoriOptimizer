# ADR-024: ティア表は探索の限界貢献で評価し、事前計算のデータを同梱する

- Date: 2026-10-09
- Status: Accepted

## Decision

サイドメニューに「ティア表」（`TierSheet.vue`。カード一覧の上）を置き、★5 全枚をリーダーとメンバーの 2 つの表に分けて SS / S / A / B / C / D の段で見せる。一覧は細いカードタイルだけで、押すと 1 枚の評価画面（`TierCardSheet.vue`）へ移る。

- **評価の正典は探索そのもの**: 前提は さがすの「全カード」と同じ（★5 全枚・開花最大・4 色ボード全解放・曲なし・コネクトなし・アカウント補正なし）。カード 1 枚の価値は「そのカードを固定して残りをおまかせで探した最良のユニットスコア ÷ 全体の最良」（限界貢献の比）。観点は メンバー固定 / メンバー固定で そのカードだけ 0凸 / リーダー固定 の 3 つで、表の段はメンバー固定・リーダー固定の比で決め、0凸の比とリーダー固定 84 通りの最良編成への採用数は説明文に使う。カードの数値を足し合わせる独自の点数は作らない。
- **段の下限は比の固定値**（`TIER_THRESHOLDS`。SS 99.5% / S 99% は共通、A 以下は メンバー 98.4% / 97.5% / 96%、リーダー 98.3% / 97.1% / 96.6%）で、順位の割合では決めない。画面では「比」と言わず、最高ユニットスコアと「全体の最高との差」（点と %）で言い、最高スコアのときの編成はカードの並び（リーダー + メンバー 5 人）で見せる（2026-10-09 ユーザー指示「わかりやすく、かつ定量性も大事」）。2026-10-09 の分布（メンバー 92.9〜100%、リーダー 95.7〜100%。全体の最良 2,029,661）で メンバー SS 7 / S 12 / A 18 / B 28 / C 12 / D 7 枚、リーダー SS 4 / S 10 / A 17 / B 29 / C 15 / D 10 枚になる値。リーダーは衣装スキルだけの差なので幅を狭くする。SS は「全体の最良にほぼ届く」カードだけ（メンバーは最良編成の 5 枚と、84 通りのリーダーの最良編成の半数近くに入る 2 枚）。
- **事前計算して `src/data/tierList.json` に同梱する**（`pnpm tier` = `scripts/tier/build.mjs`。CPU の数の子プロセスで分担し、1 枚 9〜53 秒 × 84 枚 × 3 観点）。画面は開いても計算しない。入力の指紋（`tierFingerprint`: ★5 カード・ホロメン・ボードのマス・`TIER_MODEL_VERSION`）をデータに入れ、`tier.test.ts` が現在の指紋と比べて作り直しを求める。評価の式（エンジン）を変えたら `TIER_MODEL_VERSION` を上げる。
- 1 枚ごとの評価画面は **総評（1〜2 文）→ 評価軸の表（項目 / 内容 / ★5 の中の順位）**（`src/ui/tier.ts`。長い説明文は「意味不明」なので表にする — 2026-10-09 ユーザー指示）。軸はメンバー 8 つ（最高ユニットスコア・全体の最高との差・採用数・0凸のまま・素のパラメータ・パッシブ・アクティブ・SP）、リーダー 3 つ（最高ユニットスコア・全体の最高との差・衣装スキル）。アクティブ・SP の順位は表示モデルの寄与の式、パッシブだけは効果の大きさの目安（評価には使わない。衣装スキルは条件・対象で効き方が違い目安が比と食い違うので順位を付けない）。総評で「控えめ」とは言わない（比と矛盾して読める）。

## Context

ユーザーの依頼は「ユニットスコアあげる上で重要なカードの Tier を作成したい。星5のみ。様々な観点から評価して今あるツールの計算を元に」「評価の高いカードはそれぞれなぜ高いのか説明文を出すこと。評価ランク分けは必要に応じて適切に増減させていい」「リーダーとメンバーで Tier 表を分ける」（2026-10-09）。

計測（単一スレッド）: 全カード前提のおまかせ探索 116 秒（23.7 億通り）、メンバー 1 枚固定 9 秒、リーダー固定 53 秒。84 枚 × 3 観点で約 100 分なので、画面で計算する形（Worker で数分待たせる）は現実的でなく、データは ★5 のカードが増えたときにしか変わらないので事前計算が合う。

却下した代替案: (1) スキルの数値から独自の点数を作る — ツールの計算（探索）と別の正典ができ、点数の重みが恣意的になる。(2) 全体のおまかせ探索の上位 N 件への出現回数 — 上位は同じ数枚の組み替えで埋まり、C / D を分けられない。(3) 順位の割合で段を切る（上位 10% を S など）— 段の意味が「最良にどれだけ近いか」でなくなり、カードが増えると段が動く。(4) 画面で Worker 計算 — 上記のとおり遅い。

## Consequences

### Pros

- 段の根拠が探索の結果そのものなので、さがすの結果と矛盾しない。説明文に最良編成のリーダー・採用数という具体が出せる。
- 開いた瞬間に出る（計算なし）。データが古くなればテストが落ちる。

### Cons

- ★5 を足す・エンジンの式を変えるたびに `pnpm tier`（4 コアで約 25 分）が要る。
- 前提が「全カード・開花最大・全解放」なので、自分のアカウントでの価値（所持・開花・ボード）とは違う。説明文の 0凸の比で開花依存の目安だけ出す。
- 探索は shortlist の近似なので、比はわずかに取りこぼしうる（さがすと同じ）。

## Update（2026-10-09: 段は採用率で決める）

同日のユーザー指示「最高ユニットスコア編成はツール探索で調べればわかるから重視しない。強いという実感を定量的に評価したい。強ければ現実的な編成の多くで使われるはず」で、段の根拠を限界貢献（固定した最高 ÷ 全体の最高）から**採用率**へ替えた。限界貢献は「置き換えが効くか」を測っていて、噛み合う相手が 1 枚あれば高く出る（独立レビューの指摘: 分布が 92.9〜100% に圧縮され、A 以下の境は分布に合わせた値で意味づけが弱い。リーダー 84 通りの最高編成への採用数は、条件なしの衣装スキルを持つリーダーの枚数に偏る）。

- **仮想アカウント法**: ★5 から所持数 20〜50 枚（一様）のアカウントを均衡配置で作る（1 ラウンド = 84 枚をシャッフルして塊に切る。全カードが各ラウンドにちょうど 1 回入る）。それぞれで「全カード」と同じ前提のおまかせの探索を回し、最高編成を記録する。採用率 = 持っていたアカウントのうち最高編成に入った割合（メンバー / リーダー別）。設計は `ACCOUNT_DESIGN`（ラウンド 1,100・種 20261009 → 3,034 件。残りを範囲に収める切り方のため所持数は小さい側に偏り平均約 30 枚）。**リーダーは、選ばれたカードと同じ衣装スキル（構造）を持つ所持カード全部に数える** — この前提では赤ボードが全員同じなので同じ衣装スキルのリーダーは探索で同点になり、どれが 1 位かは候補の並び順で決まるだけ（独立レビューの指摘: 同じ衣装の 2 枚を持つ 482 件すべてで並び順の先頭が勝ち、6 枚の段がずれていた）。
- **ラウンド数は統計で決めた**: 採用率 p の 95% 信頼区間の半幅を最大の p = 0.5 で 3 pt 以内にするには n ≥ 0.25 × (1.96 / 0.03)² ≈ 1,068。均衡配置なら n = ラウンド数。
- 段の下限は採用率の固定値（`TIER_THRESHOLDS`。メンバー SS 45% / S 30% / A 20% / B 10% / C 3%、リーダー SS 20% / S 10% / A 3% / B 1% / C 1 度でも選ばれる）。2026-10-09 の分布（メンバー最高 59.8%・平均約 17%、リーダー最高 26.5%・平均約 3%。メンバーは 5 枠を所持 20〜50 枚で争う）の切れ目に置いた値で、メンバー SS 8 / S 7 / A 13 / B 15 / C 17 / D 24 枚、リーダー SS 4 / S 8 / A 13 / B 14 / C 12 / D 33 枚（衣装スキル単位の計上後）。
- 限界貢献の 3 観点（固定した最高・0凸・リーダー固定）はデータに残し、評価画面の表と「最高スコアの編成」に使う。段には使わない。
- レビューで直したこと: 衣装スキル・パッシブに順位を付けない（目安が探索の結果と食い違う）、素のパラメータを「強み」と言わない（★5 の値は 5 種類で差 0.8%）、0凸の順位は落差の順、同じ衣装スキルのカードの枚数を出す、リーダーがメンバーと同じカードでもよいことを脚注に書く。
- 却下した代替案: ランダムな編成の 1 枠にカードを入れ替えて平均寄与を測る — 弱い編成に偏り「現実的」でない。各リーダーの上位 N 件への出現 — 上位は同じ数枚の組み替えで埋まる。
